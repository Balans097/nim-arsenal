## 1. Обзор

### 1.1. Что такое Nimony

**Nimony** — реализация **Nim 3**, работа над которым в настоящее время ведётся. Это предрелизная версия; подходит тем, кто готов при необходимости написать часть стандартной библиотеки самостоятельно. Все базовые конструкции языка стабилизированы и работают должным образом.

Главные цели версии 3, достигаемые за счёт переписывания фаз компилятора, повторного использования кода, рефакторингов и портирования:

1. **Инкрементальная перекомпиляция.**
2. **Нет forward-объявлений** для процедур и типов.
3. **Явные циклические зависимости модулей.**
4. **Типизированные обобщения** (проверяются при определении, а не только при инстанцировании).
5. **Нет проблем порядка фаз:** деструкторы и другие `=hooks` больше не вызываются раньше, чем синтезированы (в Nim 2 это сбивало пользователей с толку).

Ориентиры Nimony как фронтенда: малое потребление памяти, инкрементальность, хороший инструментарий (компилятор продолжает работу после ошибки; «найти все использования» и «перейти к определению» работают надёжнее, потому что обобщения и макросы тоже типизируются), эффективная работа с кодом, активно использующим обобщения, вычисления над типами и макросы, и резкое сокращение числа багов благодаря «Minimal Redundancy Internal Representation»: у каждого факта ровно один путь доступа, поэтому внутренние структуры не могут рассинхронизироваться.

### 1.2. Отличия Nim 3 от Nim 2 («хорошее»)

| Тема | Что изменилось | Выгода |
| --- | --- | --- |
| Nil | Явные аннотации `nil ref/ptr T`; обычные указатели не могут быть `nil` | Нет падений на null-указателях во время выполнения (раздел 6) |
| Обобщения | `proc mygeneric[T: <Концепт>](...)` | Больше проверок на этапе компиляции |
| `case` в `object` | Новый синтаксис | Встроенное сопоставление с образцом |
| async/await | Основаны на continuation: вместо `async` — `passive`, вместо `await` — ничего | Проблема «цвета функции» (раздел 14) |
| `spawn` | Часть цикла событий, объединённого с многопоточностью | Единая модель |
| Исключения | Переработанные аннотации | Более быстрый код |
| Эффекты | Система эффектов опциональна | Нет ошибок «GC safety» |
| `ref` | По умолчанию атомарный подсчёт ссылок | Понятие «isolation» не нужно или почти не нужно |
| `string` | Новая реализация, **без завершающего нуля** | Быстрые срезы, меньше памяти; нет неявного `cstring` без копии |
| Макросы | Заменены плагинами компилятора с другим API | Раздел 13 |
| Мультиметоды | Удалены; остаётся одиночная диспетчеризация | Проще |
| Циклические импорты | Только через явный `import (path / module) {.cyclic.}` | Явность |
| Регистр идентификаторов | Nimony **чувствителен к регистру**; `{.feature: "ignoreStyle".}` возвращает частичную нечувствительность Nim 2 по модулю | Простота реализации |
| `break` | Непомеченный `break` выходит только из цикла, никогда из `block`; из блока — `break <имя>`. `{.feature: "anonBlockBreaks".}` возвращает поведение Nim 2 | Предсказуемость |
| Побочные эффекты | `func`, `iterator`, `converter` по умолчанию `noSideEffect`; `proc` по умолчанию `sideEffect`; вывода (inference) нет; переопределение явными `.noSideEffect`/`.sideEffect` | Явные правила (раздел 8.5) |
| Перегрузка по `var T` | Убрана; доступ к элементам полиморфен по мутабельности | Меньше дублирования |

**Пример: полиморфный accessor** (авторское пояснение к оригиналу).

```nim
# Nim 2: два перегруженных аксессора
func `[]`(x: var Container): var Element
func `[]`(x: Container): lent Element

# Nimony: один полиморфный
func `[]`(x: Container): var Element
```

Компилятор отслеживает, разрешена ли запись в место вида `a[i].x.z`: она разрешена, если `a` мутабельно. Так всегда работала встроенная индексация массивов, теперь это распространено на пользовательские контейнеры. Заодно система типов знает, может ли доступ изменить размер контейнера: для изменения размера по-прежнему нужен `var`-параметр.

В целом Nim 3 в одном строже, чем Nim 2, а в другом снисходительнее.

### 1.3. Чего пока нет («плохое»)

- **Совместимой с Nim системы исключений.** Вместо неё своя, на основе перечисления `ErrorCode` (раздел 10).
- **Проверка `range` — только статическая.** Значение, привязанное к `range[lo..hi]`, несёт доказательное обязательство `lo <= value <= hi`; движок контрактов либо доказывает его, либо код отвергается. Проверок во время выполнения не генерируется, новых динамических ошибок нет. Более узкий диапазон — подтип более широкого (`range[2..5]` подходит к `range[0..10]`), литерал вне диапазона отвергается, значение под подходящим guard принимается:

```nim
var x: range[0..10] = 20          # ошибка: литерал вне диапазона

proc ok(a: int) =
  if a in 0..10:
    var x: range[0..10] = a       # принимается: доказано guard-условием
```

- **Система эффектов Nim:** `tags` игнорируются (несовпадения тегов в Nim 3 должны давать предупреждения, которые можно сделать ошибками); `raises: []` — новое значение по умолчанию и игнорируется; `raises: <список>` отображается в `.raises` (позже нужно переделать под совместимую систему исключений); `gcsafe` игнорируется.
- **Closure-итераторов** (в смысле Nim 2). Для пауз и возобновления служат passive-процедуры.
- **Неявных обобщений:** процедуры без `[T]`, где вместо него используется тип-класс вроде `SomeInt`, не поддерживаются.

## 2. Установка и конфигурация

### 2.1. Сборка из исходников

Нужен Nim версии 2.0 или новее (`nim --version`, например 2.3.1).

```
git clone https://github.com/nim-lang/nimony.git
cd nimony
nim c -r src/hastur/hastur build all
```

Использование и первая программа:

```
nimony c <program.nim>
```

```nim
import std / syncio

echo "Hello from Nimony!"
```

**Про парсер.** Nifler (инструмент, читающий `.nim`) собирается на `compiler/parser.nim` самого Nim, а не на парсере установленного компилятора: стандартная библиотека Nimony использует синтаксис (`concept of`), неизвестный ни одному релизу. Этого файла нет в репозитории: при первой сборке он берётся из локального git-checkout Nim (если там есть нужный коммит, закреплённый в `src/nifler/nimparser/upstream.commit`), иначе скачивается одним HTTPS-запросом. Последующие сборки используют копию на диске. Без сети и без checkout сборка сообщает об этом и откатывается на парсер установленного компилятора, что нормально для `devel`.

### 2.2. Режим `--compat`

С флагом `--compat` Nimony полностью поддерживает `nim.cfg` и конфигурацию NimScript. Это «грязная унаследованная система», для новых проектов её использование не рекомендуется. Вместо неё предлагается **args-конфигурация**, спроектированная с учётом инструментов.

### 2.3. Args-конфигурация

| Файл | Назначение |
| --- | --- |
| `nimony.args` | Аргументы командной строки, обрабатываются как переданные вручную |
| `nimony.paths` | Каждая строка — запись `--path` (вынесено отдельно, потому что критично для инструментов) |
| `$cc.args` | Аргументы для C-компилятора; `$cc` — ключ, извлечённый из `--cc` |
| `$linker.args` | Аргументы для линкера; ключ из `--linker`; без `--linker` линкует C-компилятор |

Правила:

- `.args`-файлы обрабатываются **до** реальной командной строки, поэтому она может их переопределить.
- В `.args` перевод строки — просто пробельный символ; строки, начинающиеся с `#`, — комментарии; действуют правила POSIX: пробелы внутри кавычек сохраняются, кавычки убираются.
- Файлы ищутся в каталоге `<program>.nim`, а если не найдены — в родительских. **Используется только первый найденный файл**, слияния нет: ни человеку, ни инструменту не нужно «мержить» конфигурации.

**Пример (авторский).** Кросс-компиляция под ARM:

```
# nimony.args
--cc:"/usr/bin/arm-linux-gnueabihf-gcc -Wall"
```

```
# arm-linux-gnueabihf-gcc.args
-O2
-mcpu=cortex-a7
```

### 2.4. Опции `--cc` и `--linker`

`--cc` принимает префикс команды, от простого `gcc` до `/usr/bin/arm-linux-gnueabihf-gcc -Wall`. Из него извлекается ключ для имени `.args`-файла:

- `/usr/bin/gcc` → `gcc.args`
- `/usr/bin/arm-linux-gnueabihf-gcc` → `arm-linux-gnueabihf-gcc.args`
- `/usr/bin/x86_64-w64-mingw32-gcc.exe -Wall` → `x86_64-w64-mingw32-gcc.args`
- `/usr/local/bin/clang` → `clang.args`

Жёстко заданного списка компиляторов нет, поэтому естественно поддерживаются C++ и LLVM-бэкенд.

`--linker`: без него для линковки используется исполняемый файл C-компилятора, читаемый файл — `$cc.linker.args`. С ним используется указанный файл, конфигурация берётся из `$linkerName.linker.args` (для `--linker:gold.exe` это `gold.linker.args`).

### 2.5. Среда выполнения: `-d:useLibc` и родственные

По умолчанию стандартная библиотека Nimony **не зависит от libc**: память выдаёт собственный аллокатор (региональный, поверх `mmap`), ввод-вывод идёт напрямую в ОС. С C-бэкендом libc всё равно линкуется, и библиотека обращается к ней там, где безлибный вариант невозможен или приближён. Три define возвращают libc:

| Define | C-бэкенд (`nimony c`) | Нативный бэкенд (`nimony n`) |
| --- | --- | --- |
| `-d:useLibc` | mimalloc как аллокатор, libc для ввода-вывода | Linux: линкуется libc; на других ОС игнорируется |
| `-d:useMimalloc` | mimalloc как аллокатор | игнорируется |
| `-d:useLibcIo` | libc для ввода-вывода | игнорируется |

Нативный бэкенд обычно не линкует libc вообще. На Linux он пишет статический автономный (freestanding) исполняемый файл, который не может привязать внешний символ. `nimony n -d:useLibc` на Linux строит программу **с libc**:

- nifasm пишет перемещаемый объектный файл, программу доделывает системный линкер (`--linker`; по умолчанию `clang`), поэтому можно подключать внешние объекты из `{.compile.}` и `{.link.}`. Программа с любой из этих прагм **требует** `-d:useLibc` на Linux и сообщает об этом, если флага нет.
- Каждая `importc`-процедура вызывает libc, тогда как автономная сборка превращает известные (`write`, `exit`, ...) в прямые системные вызовы.
- Потоки — pthreads, thread-local переменные лежат в статическом TLS-блоке libc.
- `main` вызывается C-рантаймом и возвращается в него, поэтому буферы C stdio сбрасываются при выходе.

Аллокатор и слой ввода-вывода остаются собственными. Исполняемый файл — обычная динамически слинкованная non-PIE программа. На macOS нативный бэкенд всегда линкуется с libSystem, на Windows — через таблицы импорта, так что переключатель там ничего не меняет.

## 3. Архитектура компилятора

### 3.1. Фазы

Вся реализация использует **NIF** — формат данных для обмена между фазами. Типичный проход работает с потоком токенов NIF и не строит деревьев. Токенный поток принуждает к принципиальному подходу: поддерево по замыслу нельзя «забыть обойти».

| № | Фаза | Инструмент |
| --- | --- | --- |
| 1 | Чистый разбор: Nim → диалект NIF | nifler |
| 2 | Семантика, этап 1: поиск символов, типизация, раскрытие шаблонов и макросов | nimsem |
| 3 | Семантика, этап 2: вывод эффектов (**ещё не реализован**) | nimsem |
| 4 | Вставка разыменований и проверка мутаций | nimsem |
| 5 | Встраивание итераторов | shoggoth |
| 6 | Лямбда-лифтинг | shoggoth |
| 7 | Вставка dup | shoggoth |
| 8 | Преобразование управляющих выражений в операторы (устранение `expr`/`StmtListExpr`) | shoggoth |
| 9 | Вставка деструкторов | shoggoth |
| 10 | Отображение встроенных (`new`, `+`) на «compiler procs» | shoggoth |
| 11 | Трансляция обработки исключений | shoggoth |
| 12 | Генерация кода Leng | shoggoth |
| 13 | Удаление мёртвого кода по всей программе | shoggoth |
| 14 | Необязательно: оптимизация Leng, включая инлайнинг между модулями (только `--opt:speed` и `--opt:size`) | shoggoth |
| 15 | Генерация C или LLVM (lengc) либо нативного кода (arkham + nifasm) | lengc / arkham |

### 3.2. Инструменты

- `nifler` — разбирает `.nim`; умеет вычислять конфигурацию Nim (`nim.cfg`, NimScript), чтобы `nimsuggest` получал точные `--path` без импорта компилятора как библиотеки.
- `nimsem` — семантическая проверка.
- `nimony` — драйвер, планирует всё (через `nifmake`).
- `shoggoth` — понижение (lowering) одного модуля (`shoggoth c`, проходы в `src/hexer/`), удаление мёртвого кода (`shoggoth dl`/`shoggoth de`), оптимизация (`shoggoth opt`, проходы в `src/lengc/shoggoth/`).
- `hastur` — драйвер сборки и тестов (`bin/hastur`).

### 3.3. NIF

NIF — текстовый формат общего назначения для построения компиляторов, «JSON для компиляторов». Почти классический Lisp, но:

1. Отдельное пространство имён для **тегов** («встроенных») и идентификаторов исходного кода. Поддерживаются и очень высокоуровневый, и близкий к машинному код.
2. **Информация о строках** путешествует через все фазы; хранится как разница между родителем и потомком, поэтому текст компактен.
3. **Определение и использование символа** синтаксически различаются: «найти определение», «найти все использования», «встроить этот фрагмент» реализуются очень просто.
4. Дополнительный формат **Nif-index** для ленивой загрузки символов по требованию — важнейшая часть инкрементальной компиляции.

### 3.4. NIF как основа для вычислений на этапе компиляции и плагинов

Идея общая: **скомпилировать код в машинный и запустить его, а вход-выход передать через NIF**.

- **Вычисление на этапе компиляции.** Отдельного интерпретатора нет. Фрагмент превращается в NIF (например `.p.nif`), прогоняется через весь конвейер (nimsem, shoggoth, lengc, cc, link), получается исполняемый файл, он запускается, результат подхватывается. То есть CT-вычисление — «настоящая» компиляция и запуск; особенность лишь в том, что «программа» — крошечный фрагмент.
- **Плагины.** Исходник с `{.plugin.}` компилируется в самостоятельный исполняемый файл (с `-d:nimonyPlugin`). При вызове компилятор пишет вход в `.in.nif`, запускает плагин, плагин пишет `.out.nif`, компилятор разбирает его обратно в основную компиляцию.

### 3.5. Hexer

Задача hexer — «опустить» высокоуровневый Nim до низкоуровневого, без замыканий, итераторов и автоматического управления памятью. Планируется поддерживать только схему ARC/ORC. Ключевая идея — разбить задачу на понятные подзадачи:

1. Вставка dup/copy (может давать странные конструкции вроде `while (;let tmp = f(); tmp.value)`).
2. Преобразование управляющих *выражений* в *операторы* (`if`/`case` больше не дают значений).
3. Вставка деструкторов: значения уже связаны с временными переменными, поток управления упрощён, поэтому `=destroy(x)` в точках выхода из областей видимости ставится легко.

Кроме того hexer отображает встроенные в рантайм Nim, встраивает итераторы, убирает замыкания (лямбда-лифтинг), вставляет разыменования и «передачу по ссылке», транслирует исключения в поддерживаемую Leng обработку ошибок и генерирует итоговый Leng-код.

### 3.6. Генератор Leng

Основная задача — «расширение» (expansion), то есть бэкендные операции над несколькими NIF-файлами сразу:

- копирует используемые импортированные символы в текущий NIF-файл (повторяя до неподвижной точки, пока чужих символов не останется);
- `importc`-символы заменяются на `.c`-варианты и могут вызывать вставку `(incl "file.h")`;
- типы Nim преобразуются в типы Leng;
- типы и процедуры переносятся на верхний уровень.

## 4. Основы языка

### 4.1. Лексика и синтаксис

Nimony основан на Nim 2.0, поэтому действуют все его правила лексики и синтаксиса (от раздела lexical analysis до grammar в руководстве Nim). **Главное исключение — чувствительность к регистру**: идентификаторы различаются по регистру, как в большинстве современных языков (причина — простота реализации, в будущем может измениться).

**Пояснение.** В Nim 2 `fooBar`, `foobar` и `foo_bar` были одним идентификатором. В Nimony это три разных имени. При портировании используйте точный регистр объявления или `{.feature: "ignoreStyle".}` для модуля.

### 4.2. Модули

Программа состоит из модулей; модуль — файл с кодом и может делать `import`. Единственное исключение — `system`: он импортируется всегда и содержит встроенные имена (`int`, `string` и т. д.). Имя модуля разрешает неоднозначность: если и `system`, и `foreign` содержат `delay`, то `system.delay` указывает на нужный.

### 4.3. Порядок вычисления

Порядок вычисления сейчас **не определён** (причина — простота реализации). Не полагайтесь на порядок побочных эффектов в аргументах вызова.

```nim
# авторский: плохо, результат зависит от порядка вычисления
proc next(): int = ...
let pair = (next(), next())   # какой next() выполнится первым — не гарантировано
```

### 4.4. Константы и константные выражения

Константа — символ, связанный со значением константного выражения. Константные выражения зависят только от: литералов, встроенных операторов, ранее объявленных констант и вызова подпрограммы, если аргументы вычислимы на этапе компиляции. Для произвольных вычислений на этапе компиляции есть сложный движок, ограничения которого пока не документированы.

```nim
import std/[strutils]
const
  roundPi = 3.1415
  constEval = contains("abc", 'b')    # вычисляется на этапе компиляции
```

См. раздел 16.9: каждый вызов «настоящего» CT-вычисления стоит порядка нескольких секунд.

## 5. Типы данных

У каждого выражения один тип, выведенный компилятором; вывод проверяется на соответствие явно заданному типу:

```nim
var x: int = 1          # тип литерала 1 (int) совместим с int
type Coord = (int, int) # новый тип — кортеж из двух int
```

### 5.1. Целочисленные типы

| Тип | Размер | Диапазон | Суффикс | Описание |
| --- | --- | --- | --- | --- |
| `int` | как указатель | как `int32` или `int64` | — | Знаковое; использовать по умолчанию |
| `int8` | 8 бит | -128..127 | `'i8` |  |
| `int16` | 16 бит | -32 768..32 767 | `'i16` |  |
| `int32` | 32 бита | -2 147 483 648..2 147 483 647 | `'i32` |  |
| `int64` | 64 бита | ±9,22·10^18 | `'i64` |  |
| `uint` | как указатель | 0..`high(uint)` | `'u` | Беззнаковое |
| `uint8` | 8 бит | 0..255 | `'u8` |  |
| `uint16` | 16 бит | 0..65 535 | `'u16` |  |
| `uint32` | 32 бита | 0..4 294 967 295 | `'u32` |  |
| `uint64` | 64 бита | 0..18 446 744 073 709 551 615 | `'u64` |  |

**Важно:** все беззнаковые операции **заворачиваются** (wrap around); переполнений у них нет.

**Автоматические преобразования.** В выражениях с разными целыми типами меньший приводится к большему. *Сужающее* преобразование (`int32 -> int16`) отличается от *расширяющего* (`int16 -> int32`); неявными бывают только расширяющие:

```nim
var myInt16 = 5i16
var myInt: int
myInt16 + 34     # тип int16
myInt16 + myInt  # тип int
myInt16 + 2i32   # тип int32
```

### 5.2. Вещественные типы

| Тип | Размер | Описание | Суффикс |
| --- | --- | --- | --- |
| `float` | 64 бита | IEEE 754 двойной точности; по умолчанию | — |
| `float32` | 32 бита | одинарная точность | `'f32` |
| `float64` | 64 бита | двойная точность | `'f64` |

Арифметика следует IEEE. **Целые и вещественные не преобразуются друг в друга автоматически.** Исключения IEEE (invalid, division by zero, overflow, underflow, inexact) игнорируются. На этапе семантики компилятор вычисляет с максимальной точностью, поэтому `0.09'f32 + 0.01'f32 == 0.09'f64 + 0.01'f64` — истина.

### 5.3. Логический тип

`bool` принимает `true` и `false`; условия в `while`, `if`, `elif`, `when` должны быть `bool`. Выполняется `ord(false) == 0 and ord(true) == 1`. Определены `not, and, or, xor, <, <=, >, >=, !=, ==`; `and` и `or` вычисляются **по короткой схеме**. Размер — один байт.

```nim
while p != nil and p.name != "xyz":
  # p.name не вычисляется, если p == nil
  p = p.next    # p имеет тип `nil Node`
```

### 5.4. Символьный тип

`char` — один байт. Поэтому он не может представлять UTF-8-символ целиком, только его часть.

### 5.5. Перечисления (enum)

Значения упорядочены:

```nim
type
  Direction = enum
    north, east, south, west

assert ord(north) == 0
assert ord(Direction.west) == 3   # допускается квалификация именем типа
```

Порядковые значения можно задавать, но **по возрастанию**. Поле без значения получает значение предыдущего плюс 1. Допускаются «дыры»:

```nim
type
  TokenType = enum
    a = 2, b = 4, c = 89    # дыры допустимы
```

Такой enum уже не порядковый: его нельзя использовать как индекс массива, для него недоступны `inc`, `dec`, `succ`, `pred`.

Оператор `$` для enum встроенный; результат можно задать строками:

```nim
type
  MyEnum = enum
    valueA = (0, "my value A"),
    valueB = "value B",
    valueC = 2,
    valueD = (3, "abc")
```

Имена значений enum **перегружаются**, как подпрограммы: если у `T` и `U` есть член `foo`, то `foo` — выбор между `T.foo` и `U.foo`; тип выбирается по контексту, неоднозначность — статическая ошибка:

```nim
type
  E1 = enum
    value1, value2
  E2 = enum
    value1, value2 = 4

const
  Lookuptable = [
    E1.value1: "1",
    value2: "2"          # квалифицировать не нужно, известно, что это E1.value2
  ]

proc p(e: E1) =
  case e                 # неоднозначность снимается в `case`
  of value1: echo "A"
  of value2: echo "B"

p value2
```

**Пояснение.** Итерация `for e in MyEnum:` в Nimony пока не работает; пишите `for e in low(MyEnum)..high(MyEnum):` (раздел 16.10).

### 5.6. Строки (`string`)

Все строковые литералы имеют тип `string`. Длина — встроенный `len`. Строки — **значения**: присваивание копирует или перемещает (зависит от контекста), семантики ссылки нет. Сравнение лексикографическое, доступны все операторы сравнения. Индексируются как массивы (нижняя граница 0). В отличие от массивов, их можно использовать в `case`:

```nim
case paramStr(i)
of "-v": incl(options, optVerbose)
of "-h", "-?": incl(options, optHelp)
else: write(stdout, "invalid command line option!\n")
```

По соглашению строки — UTF-8, но это не навязывается (из двоичных файлов — просто последовательность байтов). `s[i]` — i-й *char*, а не i-й *символ Unicode*. Конкатенация — `&`. Строка **не заканчивается нулём**: см. 5.7 и 16.5.

### 5.7. `cstring`

`cstring` («compatible string») — родное представление строки для бэкенда. Для C это указатель на нуль-терминированный массив, совместимый с `char*`; главное назначение — связь с C. `s[i]` — i-й *char* **без проверки границ** (небезопасно). Для получения `string` служит `$`:

```nim
var cstr: cstring = cstring"hello"
var newstr: string = $cstr
```

Литералы `cstring` изменять нельзя:

```nim
var x = cstring"literals"
x[1] = 'A'            # НЕВЕРНО!!!
```

Если `cstring` получен из обычной (не read-only) памяти, его можно менять, предварительно вызвав `prepareMutation`:

```nim
var x = "123456"
prepareMutation(x)    # вызвать перед изменением строки
var s: cstring = cstring(x)
s[0] = 'u'            # допустимо
```

`cstring` можно использовать в `case`, как строки.

### 5.8. Массивы

Массив — контейнер фиксированного размера из элементов одного типа. Длина — константное выражение. Индексировать можно любым порядковым типом. Объявление: `array[size, T]` или `array[lo..hi, T]`. Конструктор `[]`: тип элементов выводится по первому, остальные должны неявно к нему приводиться. Допустимы явные индексы:

```nim
type
  Values = enum
    valA, valB, valC

const
  lookupTable = [
    valA: "A",
    valB: "B",
    valC: "C"
  ]
```

### 5.9. `seq`

Последовательности создаются конструктором `[]` с оператором `@` либо встроенной `newSeq`. `seq` можно передавать в параметр типа `openArray`.

```nim
type
  IntArray = array[0..5, int]   # массив, индексируемый 0..5
  IntSeq = seq[int]
var
  x: IntArray
  y: IntSeq
x = [1, 2, 3, 4, 5, 6]          # [] — конструктор массива
y = @[1, 2, 3, 4, 5, 6]         # @ превращает массив в seq

let z = [1.0, 2, 3, 4]          # тип z: array[0..3, float]
```

Нижняя граница — `low()`, верхняя — `high()`, длина — `len()`. Для `seq` и `openArray` `low()` всегда 0. Добавить элемент — `add()`, удалить и получить последний — `pop()`. Доступ к i-му — `x[i]`.

### 5.10. `openArray`

`openArray` — **срез** непрерывного контейнера (массива или `seq`). Он не владеет данными, поэтому использовать его нужно осторожно; чаще всего — параметр процедуры. Индексируется от 0 до `len(A)-1`. У `array` и `seq` есть конвертеры, позволяющие передавать их без явных действий:

```nim
proc testOpenArray(x: openArray[int]) = echo repr(x)

testOpenArray([1,2,3])    # array
testOpenArray(@[1,2,3])   # seq
```

### 5.11. `UncheckedArray`

`UncheckedArray[T]` — массив без проверки границ; полезен для собственных контейнеров гибкого размера. Транслируется в C-массив неопределённого размера:

```nim
type
  MySeq = object
    len, cap: int
    data: UncheckedArray[int]
```

Порождает примерно такой C-код:

```c
typedef struct {
  NI len;
  NI cap;
  NI data[];
} MySeq;
```

### 5.12. `varargs`

`varargs` — прагма для `importc`-процедур (типичный пример — `printf`) и для шаблонов. В шаблоне аргументы распаковываются через `unpack()`:

```nim
template concat(): string {.varargs.} =
  var res = ""
  for a in unpack():
    res.add a
  res
```

`echo` в Nimony тоже на `varargs`:

```nim
template echo*() {.varargs} =
  for a in unpack(): stdout.write a
  stdout.writeLine()
```

### 5.13. Кортежи и объекты

Переменная кортежа или объекта — гетерогенный контейнер с именованными *полями*. У кортежа есть ещё и лексикографический *порядок* полей. Кортежи задуманы как типы хранения с минимумом абстракций; конструктор `()`, порядок полей должен совпадать с определением. Кортежи **эквивалентны**, если совпадают поля, их типы, порядок **и имена**.

```nim
type
  Person = tuple[name: string, age: int]
var person: Person
person = (name: "Peter", age: 30)
assert person.name == "Peter"
person = ("Peter", 30)         # то же, но менее читаемо
assert person[0] == "Peter"
```

Кортеж из одного безымянного поля пишется с завершающей запятой (она допустима для любого кортежа):

```nim
proc echoUnaryTuple(a: (int,)) =
  echo a[0]

echoUnaryTuple (1,)
```

Выравнивание полей совместимо с C-компилятором. В секции `type` кортеж можно задать и отступами:

```nim
type
  Person = tuple
    name: string
    age: Natural
```

Объекты умеют больше: наследование и скрытие полей от других модулей. Объекты с наследованием несут информацию о типе во время выполнения, оператор `of` (аналог `instanceof` в Java) определяет тип.

```nim
type
  Person = object of RootObj
    name*: string    # * — поле видно из других модулей
    age: int         # без * — скрыто

  Student = ref object of Person
    id: int

var
  student: Student
  person: Person
assert(student of Student) # true
assert(student of Person)  # тоже true
```

В отличие от кортежей, разные объектные типы **никогда не эквивалентны**: они номинальные, кортежи — структурные. Объекты без предка неявно `final` и не несут скрытой информации о типе; новые корни задаются прагмой `inheritable`.

```nim
type
  Person = object        # final-объект
    name*: string
    age: int

  Student = ref object of Person   # Ошибка: наследование только от не-final объектов
    id: int
```

Присваивание копирует каждый компонент; переопределить копирование можно хуками (раздел 9).

### 5.14. Конструкторы объектов

`T(fieldA: valueA, fieldB: valueB, ...)`, где `T` — `object` или `ref object`:

```nim
type
  Student = object
    name: string
    age: int
  PStudent = ref Student
var a1 = Student(name: "Anton", age: 5)
var a2 = PStudent(name: "Anton", age: 5)
var a3 = (ref Student)(name: "Anton", age: 5)
var a4 = Student(age: 5)       # не все поля обязательны, порядок любой
```

В отличие от кортежей, объекты требуют имён полей. Для `ref object` неявно вызывается `system.new`. (Для not-nil полей инициализация обязательна — раздел 6.)

### 5.15. Вариантные объекты: `case` в объекте

```nim
type
  ShapeKind = enum
    Circle, Rectangle, Triangle

  Shape = object
    case kind: ShapeKind
    of Circle:
      radius: float
    of Rectangle:
      width, height: float
    of Triangle:
      a, b, c: float

proc area(s: Shape): float =
  case s.kind
  of Circle:
    PI * s.radius * s.radius
  of Rectangle:
    s.width * s.height
  of Triangle:
    # формула Герона
    let p = (s.a + s.b + s.c) / 2
    sqrt(p * (p - s.a) * (p - s.b) * (p - s.c))

var circle = Shape(kind: Circle, radius: 5.0)
var rect = Shape(kind: Rectangle, width: 3.0, height: 4.0)
echo area(circle)   # 78.54...
echo area(rect)     # 12.0
```

Дискриминант (`kind`) — порядковый тип, обычно enum. Секция `case` должна быть **исчерпывающей** (или иметь `else`). При конструировании указываются только поля выбранного варианта: `Shape(kind: Triangle, a: 3.0, b: 4.0, c: 5.0)`. `case` может быть вложен среди других полей:

```nim
type
  NodeType = enum
    Leaf, Branch
  Node = object
    id: int
    case nodeType: NodeType
    of Leaf:
      value: string
    of Branch:
      children: seq[Node]
```

### 5.16. Значения по умолчанию у полей

Поля объекта могут иметь константное значение по умолчанию. Оно применяется при явной инициализации: объектный конструктор, `default(T)` для `object`; конструктор или `new` для `ref object`.

```nim
type
  Foo = object
    a: int = 2
    b: float = 3.14
    c: string = "I can have a default value"
  Bar = ref object
    a: int = 2
    b: float = 3.14

block:
  let x = Foo()
  assert x.a == 2 and x.b == 3.14
  let y = default(array[1, Foo])
  assert y[0].a == 2
  let z = default(tuple[x: Foo])
  assert z.x.a == 2
block:
  let y = new Bar
  assert y.a == 2
```

### 5.17. Множества (`set`)

Математическое множество. Базовый тип — порядковый ограниченного размера: `int8`–`int16`, `uint8`/`byte`–`uint16`, `char`, `enum`. Для литералов со знаковыми целыми базовый тип лежит в `0 .. DefaultSetElements-1` (сейчас 2^8); максимальная длина диапазона `MaxSetElements` (сейчас 2^16). Множества — быстрые битовые векторы; больший тип вызывает ошибку:

```nim
var s: set[int64]   # Ошибка: set слишком большой; используйте `std/sets`
```

Конструктор `{}` (пустое множество совместимо с любым конкретным), включает элементы и диапазоны:

```nim
type
  CharSet = set[char]
var
  x: CharSet
x = {'a'..'z', '0'..'9'}    # буквы a–z и цифры
```

| Операция | Смысл |
| --- | --- |
| `A + B` | объединение |
| `A * B` | пересечение |
| `A - B` | разность |
| `A == B` | равенство |
| `A <= B` | A — подмножество B (или равно) |
| `A < B` | строгое подмножество |
| `e in A`, `e notin A` | принадлежность |
| `contains(A, e)` | то же, что `e in A` |
| `incl(A, e)` | `A = A + {e}` |
| `excl(A, e)` | `A = A - {e}` |

Для больших множеств есть `HashSet` (`import std/sets`).

### 5.18. Distinct-типы

`distinct` — новый тип на основе базового, **несовместимый** с ним: это не отношение подтипа. Явные преобразования туда и обратно допустимы. Distinct порядковый, если порядковый базовый тип.

```nim
# авторский
type Meters = distinct float
type Seconds = distinct float

func `+`(a, b: Meters): Meters = Meters(float(a) + float(b))

let d = Meters(3.0) + Meters(4.0)
# let bad = Meters(1.0) + Seconds(2.0)   # ошибка: типы несовместимы
```

**Пояснение.** В Nimony `$` и операторы для distinct **не заимствуются автоматически**: `$aDistinct` пишите как `$Base(x)`, а заимствованные через `{.borrow.}` операторы лучше объявлять как `func` (разделы 8.5 и 16.1).

### 5.19. Процедурный тип

Процедурный тип — внутри указатель на процедуру. Как и другие указательные типы, **по умолчанию не может быть `nil`** (для допускающего nil: `nil proc (...)`). Процедурный тип — не замыкание: лишь `proc (...) {.closure.}` может хранить процедуру с захваченным окружением (раздел 8.3).

Совместимость процедурных типов зависит от соглашения о вызове:

```nim
proc printItem(x: int) = ...

proc forEach(c: proc (x: int) {.cdecl.}) =
  ...

forEach(printItem)   # НЕ компилируется: соглашения о вызове различаются
```

| Соглашение | Описание |
| --- | --- |
| `nimcall` | По умолчанию для `proc` Nim; то же, что `fastcall`, если C-компилятор его поддерживает |
| `stdcall` | stdcall Microsoft (`__stdcall`) |
| `cdecl` | Как у C-компилятора; под Windows `__cdecl` |
| `safecall` | safecall Microsoft; «safe» — все аппаратные регистры сохраняются в стеке |
| `inline` | Вызывающий должен встроить код. Nim сам не встраивает, а генерирует `__inline`; это подсказка, компилятор может игнорировать её и встраивать не помеченные процедуры |
| `noinline` | Запрещает бэкенду встраивание |
| `fastcall` | Что означает `__fastcall` у конкретного C-компилятора |
| `thiscall` | thiscall Microsoft, методы C++ классов на x86 |
| `syscall` | Как `__syscall` в C; для прерываний |
| `noconv` | Без явного соглашения; нужно, потому что Nim по умолчанию использует `fastcall` |

Большинство соглашений актуально лишь для 32-битной Windows. `closure` **не** соглашение о вызове в Nimony, а прагма, дающая процедуре или типу скрытое окружение.

### 5.20. Отношения между типами

**Равенство типов.** Структурная эквивалентность для большинства типов; именная — только для объектов, перечислений, distinct и обобщённых типов.

**Подтип.** Если объект `a` наследует `b`, то `a` — подтип `b`. Отношение продолжается на `var`, `ref`, `ptr`: если `A` — подтип `B` (оба `object`), то `var A` — подтип `var B`, `ref A` — подтип `ref B`, `ptr A` — подтип `ptr B`. Одна из этих косвенностей обязательна при присваивании подтипа родителю (иначе «срезка объекта»).

**Неявная приводимость** `a` к `b`, если алгоритм возвращает true:

```nim
proc isImplicitlyConvertible(a, b: PType): bool =
  if isSubtype(a, b):
    return true
  if isIntLiteral(a):
    return b in {int8, int16, int32, int64, int, uint, uint8, uint16,
                 uint32, uint64, float32, float64}
  case a.kind
  of int:     result = b in {int32, int64}
  of int8:    result = b in {int16, int32, int64, int}
  of int16:   result = b in {int32, int64, int}
  of int32:   result = b in {int64, int}
  of uint:    result = b in {uint32, uint64}
  of uint8:   result = b in {uint16, uint32, uint64}
  of uint16:  result = b in {uint32, uint64}
  of uint32:  result = b in {uint64}
  of float32: result = b in {float64}
  of float64: result = b in {float32}
  of seq:
    result = b == openArray and typeEquals(a.baseType, b.baseType)
  of array:
    result = b == openArray and typeEquals(a.baseType, b.baseType)
    if a.baseType == char and a.indexType.rangeA == 0:
      result = b == cstring
  of cstring, ptr:
    result = b == pointer
  of string:
    result = b == cstring
  of proc:
    result = typeEquals(a, b) or compatibleParametersAndEffects(a, b)
```

Здесь `typeEquals` — равенство типов, `isSubtype` — подтип; `compatibleParametersAndEffects` пока не специфицирована. Для `range`: пусть `a0`, `b0` типа `T`, `A = range[a0..b0]` — тип аргумента, `F` — тип параметра. Неявное преобразование `A` в `F` существует, если `a0 >= low(F) and b0 <= high(F)` и оба типа знаковые или оба беззнаковые.

**Явная приводимость** `a` к `b`:

```nim
proc isIntegralType(t: PType): bool =
  result = isOrdinal(t) or t.kind in {float, float32, float64}

proc isExplicitlyConvertible(a, b: PType): bool =
  result = false
  if isImplicitlyConvertible(a, b): return true
  if typeEquals(a, b): return true
  if a == distinct and typeEquals(a.baseType, b): return true
  if b == distinct and typeEquals(b.baseType, a): return true
  if isIntegralType(a) and isIntegralType(b): return true
  if isSubtype(a, b) or isSubtype(b, a): return true
```

Отношение расширяется пользовательским `converter`:

```nim
converter toInt(x: char): int = result = ord(x)

var
  x: int
  chr: char = 'a'

x = chr          # неявное преобразование
echo x           # => 97
x = chr.toInt    # явная форма
```

Преобразование `T(a)` — L-значение, если `a` — L-значение и `typeEqualsOrDistinct(T, typeof(a))`. **Совместимость при присваивании:** `b` можно присвоить `a`, если `a` — l-value и `isImplicitlyConvertible(b.typ, a.typ)`.

## 6. Ссылки, nil и владение

### 6.1. `ref` и `ptr`

Ссылки — способ задать отношение «многие к одному»: несколько ссылок указывают на одно место в памяти (*aliasing*). Различают *отслеживаемые* (traced, `ref`) и *неотслеживаемые* (untraced, `ptr`, они же «указатели») ссылки. Traced указывают на объекты управляемой ккуч, untraced — на память, выделенную вручную или где-то ещё; они **небезопасны**, но для низкоуровневых операций неизбежны. `ptr T` неявно приводится к `pointer`.

**По умолчанию `ref`, `ptr`, `pointer` и `cstring` не могут быть `nil`.** Компилятор проверяет это статически.

Пустые скобки `[]` разыменовывают ссылку, `addr` возвращает адрес (небезопасно). Операторы `.` и `[]` выполняют неявное разыменование:

```nim
type
  Node = ref NodeObj
  NodeObj = object
    le, ri: nil Node
    data: int

var n = Node()
n.data = 9
# n[].data писать не нужно, более того — не рекомендуется
```

Рекурсивные кортежи недопустимы (`type MyTuple = tuple[a: ref MyTuple]`), как и `T = ref T`. Анонимный объект: `ref object` / `ptr object`:

```nim
type
  Node = ref object
    le, ri: nil Node
    data: int
```

Новый traced-объект создаётся объектным конструктором; для неотслеживаемой памяти — `alloc`, `dealloc`, `realloc`.

### 6.2. Not-nil по умолчанию

Обычный `ref T` или `ptr T` не может быть `nil`; компилятор отвергает присваивание `nil` и неинициализированное значение:

```nim
type
  Node = ref object
    data: int

var n: Node       # Ошибка на уровне модуля: нет значения по умолчанию
var m: Node = nil # Ошибка: нельзя присвоить nil not-nil типу
```

### 6.3. Типы без значения по умолчанию

not-nil указатель — единственный «листовой» тип, у которого нет значения в обнулённой памяти (обнулённая память читается как `nil`, что тип и запрещает). Всё, что из него построено, наследует это: элемент массива, слот кортежа, поле объекта без собственного значения.

```nim
type
  Node = ref object
    data: int
  Pair = object
    n: Node
    count: int

var a: array[8, Node]   # Ошибка: у `array[8, Node]` нет значения по умолчанию
var p: Pair             # Ошибка: у Pair тоже, через поле `n`
var q = default(Node)   # Ошибка: `default` тоже ничего не вернёт
```

Правило действует на **уровне модуля**, где память глобальной переменной просто обнуляется: глобальную переменную можно прочитать из другого модуля и потока, поэтому анализ потока управления поручиться за неё не может. У **локальной** переменной нет обязанностей при объявлении — `var r: Node` допустимо, пока запись достигает её до первого чтения, что проверяет анализ инициализации:

```nim
proc p(): Node = Node(data: 1)

proc ok =
  var r: Node           # нормально
  r = p()
  echo r.data

proc notOk =
  var r: Node
  echo r.data           # Ошибка: нельзя доказать, что r инициализирован
```

По той же причине `newSeq[T](n)` и `setLen` требуют `T` со значением по умолчанию; `shrink` и `add` — нет.

### 6.4. Допускающие nil типы: префикс `nil`

```nim
type
  Node = ref object
    data: int
    next: nil Node  # может быть nil

var x: nil ptr int = nil
var y: nil ref int = nil
var z: nil cstring = nil
var t: nil pointer = nil
```

Для `nil`-типов компилятор требует, чтобы каждое разыменование было защищено проверкой на nil; отслеживание идёт через поток управления:

```nim
proc process(x: nil ref int) =
  if x != nil:
    echo x[]  # OK, защищено
  # echo x[]  # Ошибка: x может быть nil

var node: nil Node = nil
if someCondition():
  node = Node(data: 42)

if node != nil:
  echo node.data  # OK после проверки
```

### 6.5. Непроверяемые указатели: `unchecked`

Для низкоуровневого кода и FFI префикс `unchecked` полностью отключает отслеживание nil. Применим к `ref`, `ptr`, `pointer`, `cstring` и процедурным типам:

```nim
type
  MemFile = object
    mem: unchecked pointer
    size: int
```

Подходит, когда указатель может быть nil и вы сами ведёте проверки (FFI) или когда действует инвариант вроде «`x.status == Success` влечёт `x.field != nil`», пока недоступный системе типов.

### 6.6. Процедурные типы и итераторы

Процедурные типы подчиняются тем же правилам:

```nim
var callback: proc (x: int) # должна быть инициализирована допустимой процедурой

var optCallback: nil proc (x: int) = nil # nullable
if optCallback != nil:
  optCallback(42)
```

Тип итератора — пара указателей, как любое замыкание, и подчиняется тому же правилу:

```nim
type It = iterator (): int

var run: It                 # Ошибка: нет значения по умолчанию
var maybeRun: nil It = nil  # nullable значение-итератор
```

### 6.7. Портирование: feature `lenientnils`

Прагма `{.feature: "lenientnils".}` восстанавливает классическое поведение Nim для модуля: `ref`, `ptr`, `pointer`, `cstring` и `proc`-типы допускают nil:

```nim
{.feature: "lenientnils".}

var x: ref int = nil   # OK в этом модуле
var y: ptr int = nil
```

Предназначена для **постепенного портирования**. Новый код должен использовать явные `nil T`.

### 6.8. Частые шаблоны

Узлы деревьев и списков обычно имеют nil-допускающие дочерние указатели:

```nim
type
  Node = ref object
    data: int
    left, right: nil Node

proc depth(n: nil Node): int =
  if n == nil: return 0
  return 1 + max(depth(n.left), depth(n.right))
```

Дескрипторы ресурсов отслеживают освобождение через nil-допускающий указатель:

```nim
type
  MyResource = object
    handle: nil ptr Handle

proc `=destroy`(x: MyResource) =
  if x.handle != nil:
    freeHandle(x.handle)

proc `=wasMoved`(x: var MyResource) =
  x.handle = nil
```

### 6.9. Владеющие ссылки (`owned`)

Конструктор типа `owned` — статически проверяемая аннотация *единоличного владения* для двух счётчиковых дескрипторов: `ref T` и замыканий (RFC #575). Код, который не пишет `owned`, им не затрагивается.

`owned X` значит: это место хранит единственное *владеющее* ребро к ячейке. Может существовать сколько угодно обычных (счётных) ссылок на ту же ячейку — они удерживают её живой, когда владелец уйдёт. Представление во время выполнения то же, что у `X`, поэтому модули с этой возможностью и без неё совместимы.

| Операция | Смысл |
| --- | --- |
| `owned X` в `X` | неявно, даёт счётную ссылку |
| `X` в `owned X` | ошибка, если значение не свежее |
| копия `owned`-места | ошибка: переместите или преобразуйте в неvладеющую |
| объектный конструктор | даёт `owned ref T` при `ownedRefs` |
| value-тип с `owned`-полем | только перемещаемый (move-only) |
| `owned`-параметр | заимствован, как любой другой `ref`-параметр |
| `sink owned`-параметр | принимает владение |

Свежие значения (объектные конструкции, `new`, лямбды, `nil`) ещё не имеют другого владельца и потому могут инициализировать `owned`-место. С `{.feature: "ownedRefs".}` объектная конструкция ещё и *типизируется* как `owned`: `let a = Node()` делает `a` владельцем, а `let b = a` — ошибка копирования (кроме последнего чтения `a`). Без feature `a` — обычная счётная ссылка.

```nim
type
  Node = ref object
    next: owned nil Node
    data: int

proc sum(list: nil Node): int =
  result = 0
  var it = list           # счётная; держит узел живым
  while it != nil:
    result += it.data
    it = it.next
```

`owned`-параметр — обычный параметр владеющего типа: вызываемый может читать и писать через него, но не переприсвоить; владельцем остаётся вызывающий. Владение передаётся только `sink owned`-параметру:

```nim
proc rename(n: owned Node; data: int) =
  n.data = data            # ok: запись через ссылку
  let u: Node = n          # ok: счётная ссылка

proc append(list: Node; n: sink owned Node) =
  list.next = n            # ok: `n` владеет ячейкой и передаёт это дальше
```

Без `sink` присваивание `list.next = n` было бы копией `owned`-места и отвергается. `owned` отвергается на `seq` и `string`, они и так уникальны.

Владеющие рёбра — move-only, поэтому образуют лес: цикл обязан содержать хотя бы одно не-`owned` ребро. Тип, все ссылки которого `owned` или `.cursor`, не участвует в циклах и остаётся вне сборщика циклов `--mm:orc` и `--mm:yrc`. `owned`-замыкание обещает ацикличное окружение; это проверяется там, где замыкание формируется:

```nim
type
  Widget = ref object
    onChange: owned proc () {.closure.}  # не делает Widget циклическим

proc label(w: Widget; s: string) =
  w.onChange = proc () {.closure.} = echo s   # ok: захватывает только строку
```

Проверку можно обойти, записав владеющее ребро через невладеющий алиас в owned-поддерево; результат — утечка, а не порча памяти. `-d:nimOwnedStrict` превращает невладеющую ссылку, пережившую владельца, в фатальную ошибку времени выполнения («dangling references exist»); без него такая ссылка удерживает объект живым, что безопасно.

## 7. Выражения, операторы и разрешение имён

### 7.1. Поиск идентификатора

Идентификатор обозначает не одно объявление, а **выбор символов** (*symbol choice*) — все видимые под этим именем объявления. Поиск только *собирает* кандидатов; какой из них имеется в виду, решают разрешение перегрузки и дизамбигуация.

Кандидаты собираются уровень за уровнем, от самой внутренней области наружу. Самый внешний уровень — **верхняя область самого модуля вместе со всем, что в него импортировано**: `import` — не отдельный механизм поиска и не граница затенения; он лишь задаёт «расстояние» области, по которому ранжирует правило Module-of-origin (7.2).

Продолжать ли обход за пределы уровня, определяет *вид* найденных там объявлений, а не модуль:

- **Неперегружаемые** объявления — `let`, `var`, `const`, `type`, параметр подпрограммы, обобщённый параметр, поле объекта, `result`, метка блока — **затеняют**: найдя одно, обход останавливается.
- **Перегружаемые** — proc, func, converter, template, macro, iterator и **поле enum** — никогда не затеняют, а накапливаются в выборе, в том числе через `import`.

```nim
# модуль m:
type Color* = enum
  red, green

# вызывающий:
import m
proc red() = discard
proc paint(c: Color) = discard

paint(red)   # `red` — выбор {локальная процедура, m.Color.red};
             # тип параметра выбирает поле enum
```

Собранный выбор разрешается в таком порядке:

1. **Контекст.** В вызове кандидата выбирает разрешение перегрузки. В любой позиции, где ожидается тип (аргумент, `x: T = p`, поле конструктора, ветка `case`), кандидата выбирает дизамбигуация.
2. **Расстояние области.** Если контекст не сузил выбор до одного, побеждает ближайшее объявление: внутренняя область побеждает внешнюю, а собственное объявление модуля — импортированное.

```nim
type E = enum A, B

block:
  type E = enum A, B
  let x = A       # `E.A` блока: ближе, и ничто другое не сужает
```

3. **Иначе — неоднозначность**, статическая ошибка. Она возможна только между кандидатами на *одном* расстоянии — прежде всего два разных модуля, экспортирующих одно имя; решается квалификацией имени.

Затенение и неоднозначность решаются именно в таком порядке: объявление, которое затеняет, убирает кандидатов до всего остального, поэтому `let` во внутренней области не может быть неоднозначным.

### 7.2. Разрешение перегрузки

В вызове `p(args)`, где `p` — выбор символов, разрешение перегрузки ищет лучшего кандидата. Если после всех проб несколько кандидатов подходят одинаково, неоднозначность сообщается при семантическом анализе.

**Первая проба: категории совпадений.** Пусть `f` — тип формального параметра, `a` — тип аргумента. Категории (по убыванию приоритета):

1. **Точное совпадение:** `a` и `f` одного типа.
2. **Совпадение литерала:** `a` — целый литерал значения `v`, `f` — знаковый или беззнаковый целый тип, и `v` в его диапазоне; либо вещественный литерал и вещественный тип.
3. **Обобщённое совпадение:** `f` — обобщённый тип (`[T]` или `[T: int|char]`).
4. **Подтип или поддиапазон:** `a` — `range[T]` и `T` точно совпадает с `f`; либо `a` — подтип `f`.
5. **Целочисленное преобразование:** `a` приводим к `f`, оба — целые или вещественные.
6. **Совпадение через преобразование:** `a` приводим к `f`, возможно через пользовательский `converter`.

У каждого операнда своя высшая категория. Если у кандидата больше совпадений более приоритетной категории, чем у всех остальных, он выбирается. Например, кандидат с одним точным совпадением побеждает кандидата с несколькими обобщёнными и нулём точных. Псевдокод:

```nim
for each matching category m in ["exact match", "literal match",
                                "generic match", "subtype match",
                                "integral match", "conversion match"]:
  if count(p, m) > count(q, m): return true
  elif count(p, m) == count(q, m):
    discard "continue with next category m"
  else:
    return false
return "ambiguous"
```

**Module-of-origin.** Подпрограмма из вызывающего модуля предпочитается импортированной. Это не отдельный постфильтр, а ещё одно измерение подтипизации в том же алгоритме. Концептуально у каждой подпрограммы есть неявный параметр типа `Scope`, а компилятор подставляет аргумент на каждом вызове:

- для **требования концепта** (фантомное объявление без реализации) аргумент типа `ConceptScope`;
- для подпрограммы из вызывающего модуля — `Scope = object of ConceptScope` (подтип, глубина 1);
- для импортированной — `ImportScope = object of Scope` (подтип, глубина 2).

То есть `import` трактуется как наследование между областями, в духе Eiffel. Требования концептов самые специфичные, поэтому выигрывают ничьи у локальных и импортированных кандидатов. Вызов, выбравший требование концепта, не исполняется как написано: компилятор откладывает его и **заново разрешает** при инстанцировании обобщения, когда конкретные типы позволяют выбрать реальную перегрузку. Следствия:

- при равных результатах по реальным аргументам побеждает локальный кандидат (импортированный на единицу дальше);
- локальный кандидат, требующий неявного преобразования, проигрывает импортированному с точным совпадением (категория «преобразование» после «подтипа»);
- локальный через подтип против импортированного с точным совпадением — неоднозначность (оба дают по единице расстояния подтипа);
- внутри обобщённого тела, параметр которого ограничен концептом, требование концепта выигрывает ничью и повторно разрешается при инстанцировании.

```nim
type
  Foo = concept
    func bar(x: Self): int

func bar[T](x: T): int = 1
func bar(x: float64): int = 2

func doBar[T: Foo](x: T): int = bar(x)

doBar(1.0'f64) # 2, не неоднозначно: внутри `doBar` `bar` привязан к требованию
               # концепта Foo, которое откладывает разрешение; при
               # инстанцировании побеждает `bar(x: float64)`
```

```nim
# модуль m:
proc which*(x: int): string = "imported-int"
proc which*(x: float): string = "imported-float"

# вызывающий:
import m
proc which(x: int): string = "local-int"

doAssert which(1) == "local-int"        # локальная выигрывает ничью
doAssert which(1.0) == "imported-float" # преобразование всё равно проигрывает области
```

**Вторая проба: структурное сравнение типов.** «Вложенность» обобщённых параметров задаёт отношение: `G[A[T]]` специфичнее `G[T]`, поэтому предпочитается.

**Примеры.**

```nim
proc takesInt(x: int) = echo "int"
proc takesInt[T](x: T) = echo "T"
proc takesInt(x: int16) = echo "int16"

takesInt(4) # "int"
var x: int32
takesInt(x) # "T"
var y: int16
takesInt(y) # "int16"
var z: range[0..4] = 0
takesInt(z) # "T"
```

При совпадении через подтипизацию учитывается глубина наследования:

```nim
type
  A = object of RootObj
  B = object of A
  C = object of B

proc p(obj: A) = echo "A"
proc p(obj: B) = echo "B"

var c = C()
p(c)   # не неоднозначно: вызывается 'B', B — подтип A, но не наоборот

proc pp(obj: A, obj2: B) = echo "A B"
proc pp(obj: B, obj2: A) = echo "B A"

# а это неоднозначно:
pp(c, c)
```

Для обобщённых совпадений предпочитается самый специализированный подходящий тип:

```nim
proc gen[T](x: ref ref T) = echo "ref ref T"
proc gen[T](x: ref T) = echo "ref T"
proc gen[T](x: T) = echo "T"

var ri: ref int
gen(ri) # "ref T"
```

### 7.3. Дизамбигуация перегрузки

Для вызовов выполняется разрешение перегрузки. Более слабая форма — **дизамбигуация** — действует, когда перегруженный символ используется там, где доступна дополнительная информация о типе:

- в вызове `q(..., p, ...)` — по типу соответствующего формального параметра `q` (если `q` перегружена, рассматривается декартово произведение);
- в объектном конструкторе `Obj(..., field: p, ...)` — по типу поля (аналогично для конструкторов массивов, множеств и кортежей);
- в объявлении `x: T = p` — по `T`;
- в ветке `case` — по типу селектора.

Ожидаемый тип может быть любым, не только `proc`: выбор между подпрограммой и полем enum разрешается ожидаемым enum так же, как выбор между двумя подпрограммами — ожидаемым `proc`. Если контекст оставляет несколько кандидатов, решает расстояние области (7.1); оставшаяся неоднозначность — ошибка компиляции.

### 7.4. Операторы и выражения-операторы

Операторы (statements) не производят значения, выражения — производят; некоторые выражения — операторы. Операторы делятся на **простые** (присваивание, вызов, `return`) и **сложные**; сложные всегда с отступами, что снимает проблему dangling else.

**Список операторов-выражений `(stmt1; stmt2; ...; ex)`.** Тип — тип `ex`; остальные операторы должны быть `void` (для этого есть `discard`). `(;)` не вводит новую область видимости.

**`discard`.** Вычисляет выражение ради побочных эффектов и отбрасывает результат; игнорировать возвращаемое значение без `discard` — статическая ошибка. Пустой `discard` — нулевой оператор:

```nim
proc p(x, y: int): int =
  result = x + y

discard p(3, 4)   # результат отбрасывается

proc classify(s: string) =
  case s[0]
  of SymChars, '_': echo "an identifier"
  of '0'..'9': echo "a number"
  else: discard
```

**`var`.** Объявляет и инициализирует переменные; через запятую можно перечислять переменные одного типа. При наличии инициализатора тип можно опустить. Компилятор требует инициализации локальных переменных перед использованием; проверку можно отключить прагмой `noinit`:

```nim
var
  a: int = 0
  x, y, z: int

var a {.noinit.}: array[0..1023, char]
proc returnUndefinedValue: int {.noinit.} = discard   # про неявный `result`
```

Анализ потока управления доказывает инициализацию:

```nim
proc p() =
  var x: MyObject
  if someCondition():
    x = a()
  else:
    x = a()
  use x        # допустимо: на обеих ветках x присвоен
```

**`let`.** Переменные одиночного присваивания; не l-values, нельзя передать в `var`-параметры, взять адрес и присвоить повторно. Значение обязательно при объявлении (кроме `importc` и т. п., где значение приходит из нативного кода). Разрешено объявление без значения, если каждый путь присвоит значение до использования.

**Идентификатор `_`.** В объявлениях определение с именем `_` в область не добавляется (вычисляется, но использовать нельзя), и имя можно переопределять сколько угодно:

```nim
let _ = 123
echo _       # ошибка
let _ = 456  # компилируется
```

**Распаковка кортежей.** В `var`, `let`, `const`; `_` игнорирует части:

```nim
proc returnsTuple(): (int, int, int) = (4, 2, 3)
let (x, _, z) = returnsTuple()

# примерно то же, что:
let
  tmpTuple = returnsTuple()
  x = tmpTuple[0]
  z = tmpTuple[2]

let (a, b, c) = (1, 2, 3)   # литерал кортежа раскрывается без временной переменной

proc returnsNestedTuple(): (int, (int, int), int, int) = (4, (5, 7), 2, 3)
let (x2, (_, y2), _, z2) = returnsNestedTuple()   # вложенная распаковка
```

**`const`.** Секция констант со значениями константных выражений. Значение каждой константы открывает свою область видимости, символы из него снаружи недоступны:

```nim
const foo = (var a = 1; a)
const bar = a   # ошибка
let baz = a     # ошибка
```

**`if`.** Условие, ветки `elif`, `else`. Новые области видимости начинаются сразу после ключевых слов `if`/`elif`/`else` и кончаются после соответствующей ветки *then*:

```nim
var name = readLine(stdin)

if name == "Andreas":
  echo "What a nice name!"
elif name == "":
  echo "Don't you have a name?"
else:
  echo "Boring name..."
```

**`case`.** Многовариантный выбор: выражение после `case` сравнивается со *списками срезов*; если не совпало ни с одним, выполняются завершающие `elif`/`else`. Для порядковых выражений, если не все значения покрыты, — статическая ошибка (подавить: `else: discard`). Допустимы порядковые типы, вещественные, строки и `cstring`; для непорядковых всегда нужен `else` (кроме `string`, которому он не нужен). Значение каждой ветки `of` — константное выражение. Как расширение, выражение в `of` может быть множеством или массивом — оно раскрывается в список элементов:

```nim
let line = readline(stdin)
case line
of "delete-everything", "restart-computer":
  echo "permission denied"
of "go-for-a-walk":
  echo "please yourself"
elif line.len == 0:
  echo "empty"           # необязательно, после веток `of`
else:
  echo "unknown command"

const
  SymChars: set[char] = {'a'..'z', 'A'..'Z', '\x80'..'\xFF'}

proc classify(s: string) =
  case s[0]
  of SymChars, '_': echo "an identifier"
  of '0'..'9': echo "a number"
  else: echo "other"
```

`case` не даёт l-value, поэтому следующий вариант не работает, а `result = ...` или `return` — работает:

```nim
proc getX(x: Foo): var seq[string] =
  # так не работает: case true of true: x.x else: x.x
  case true
  of true:
    result = x.x
  else:
    result = x.x
```

**`when`.** Как `if`, но: условие — константное `bool`; ветки не открывают область видимости; проверяются семантически (и переводятся) только ветки истинного условия — остальные нет (условия проверяются всегда). Условная компиляция:

```nim
when sizeof(int) == 2:
  echo "running on a 16 bit system!"
elif sizeof(int) == 4:
  echo "running on a 32 bit system!"
elif sizeof(int) == 8:
  echo "running on a 64 bit system!"
else:
  echo "cannot happen!"
```

**`return`.** Завершает подпрограмму; допустим в proc, func, method, converter, template (в шаблоне заставляет вернуться подпрограмму, в которую шаблон раскрыт). `return expr` — это `result = expr; return result`. `return` без выражения — `return result`, если есть тип возврата. Переменная `result` объявляется компилятором автоматически.

**`yield`.** Вместо `return` в итераторах: передаёт управление в тело цикла `for`; итерацию не завершает.

**`block`, `break`, `while`, `continue`.**

```nim
var found = false
block myblock:
  for i in 0..3:
    for j in 0..3:
      if a[j][i] == 7:
        found = true
        break myblock    # выход из блока (из обоих циклов)
echo found
```

Внутри именованного блока `break <имя>` выходит из него. **Непомеченный `break` никогда не покидает блок, только внутренний цикл**, поэтому `block` внутри цикла работает как обычная область видимости:

```nim
for i in 1..10:
  block:
    let x = compute(i)
    if x < 0:
      break        # выходит из цикла `for`, не из `block`
```

Непомеченный `break` вне цикла — ошибка. С `{.feature: "anonBlockBreaks".}` (входит в `"v2"`) он выходит из внутреннего цикла *или* блока, как в Nim 2. `while` открывает неявный блок; бесконечные циклы не ошибка. `continue` — сахар для вложенного блока:

```nim
while expr1:
  stmt1
  continue
  stmt2

# то же, что:
while expr1:
  block myBlockName:
    stmt1
    break myBlockName
    stmt2
```

**`using`.** Удобство, когда одни и те же имена параметров повторяются с одними типами:

```nim
using
  c: Context
  n: Node
  counter: int

proc foo(c, n) = ...
proc bar(c, n, counter) = ...

proc mixedMode(c, n; x, y: int) =
  # 'c' — Context, 'n' — Node, а 'x' и 'y' — int
```

Не применяется к `template` (параметры шаблонов по умолчанию `untyped`). Смешивание параметров из `using` с явно типизированными требует точки с запятой.

### 7.5. Выражения

**`if`-выражение** — аналог тернарного оператора, `else` обязателен: `var y = if x > 8: 9 else: 10`. **`when`-выражение** — то же для `when`.

**`case`-выражение:**

```nim
var favoriteFood = case animal
  of "dog": "bones"
  of "cat": "mice"
  elif animal.endsWith"whale": "plankton"
  else:
    echo "I'm not sure what to serve, but everybody loves ice cream"
    "ice cream"
```

Ветка может иметь побочные эффекты; при нескольких операторах значением служит последнее выражение.

**`block`-выражение** — значение даёт последнее выражение; в отличие от списка операторов-выражений открывает область видимости:

```nim
let a = block:
  var fib = @[0, 1]
  for i in 0..10:
    fib.add fib[^1] + fib[^2]
  fib
```

**Конструктор таблицы** — сахар для конструктора массива пар; пустая таблица `{:}` (в отличие от пустого множества `{}`):

```nim
{"key1": "value1", "key2", "key3": "value2"}
# то же, что:
[("key1", "value1"), ("key2", "value2"), ("key3", "value2")]
```

**Преобразования типов.** Синтаксически вызов с именем типа. Всегда безопасно: сбой, если не определим статически, приводит к ошибке. Часто предпочтительнее обычные процедуры (`$`, `toFloat`, `toInt`). Преобразование может разрешать перегрузку:

```nim
proc p(x: int) = echo "int"
proc p(x: string) = echo "string"

let procVar = (proc(x: string))(p)
procVar("a")
```

Преобразования в беззнаковые типы и между ними не проверяются и заворачиваются (ради совместимости при портировании алгоритмов с C).

**Приведения (`cast`)** — грубый механизм, интерпретирующий битовый шаблон как другой тип; нужны только для низкоуровневого кода и небезопасны. Целевой тип должен быть конкретным (тип-класс недопустим):

```nim
cast[int](x)

type Foo = int or float
var x = cast[Foo](1) # Ошибка: нельзя привести к неконкретному типу 'Foo'
```

В отличие от преобразований, `cast` не меняет битовый шаблон (кроме случая разных размеров: если целевой тип больше, остаток обнуляется). Аналог `reinterpret_cast`/`bit_cast` в C++.

**`addr`** возвращает адрес l-value; тип результата `ptr T`; адрес всегда untraced. Брать адрес объекта на стеке **небезопасно**: указатель может пережить объект. Для совместимости с C допускается брать адрес `let`-переменной, параметра и переменной цикла `for`:

```nim
let t1 = "Hello"
var t2: pointer = addr(t1)
echo cast[ptr string](t2)[]
```

### 7.6. Импорт, include, export и область видимости

**`import`** — список модулей либо один модуль с `except`-списком; допустим только на верхнем уровне; строковые литералы допустимы:

```nim
import std/strutils except `%`, toUpperAscii

# тогда не работает:
echo "$1" % "abc".toUpperAscii
```

`except`-список не проверяется на экспортированность (позволяет компилироваться против разных версий модуля).

**`include`** просто вставляет содержимое файла (для разбиения большого модуля): `include fileA, fileB, fileC`.

**Псевдонимы и пути:**

```nim
import std/strutils as su, std/sequtils as qu
echo su.format("$1", "lalelu")

import lib/pure/os, "lib/pure/times"
```

Имя модуля остаётся `strutils`, а не `lib/pure/strutils`, поэтому `lib/pure/strutils.toUpperAscii("abc")` недопустимо; `import lib/pure/strutils as strutils` бессмысленно.

**`from ... import`** — перечислить символы для использования без квалификации; `from module import nil` — импорт с обязательной полной квалификацией:

```nim
from std/strutils import `%`
echo "$1" % "abc"
echo strutils.replace("abc", "a", "z")   # полная квалификация всегда возможна
```

**`export`** — перенаправление символов, чтобы клиентам не нужно было импортировать зависимости:

```nim
# модуль B
type MyObject* = object

# модуль A
import B
export B.MyObject
proc `$`*(x: MyObject): string = "my object"

# модуль C
import A
var x: MyObject   # B.MyObject импортирован неявно
echo $x
```

Если экспортируется модуль, перенаправляются все его определения (можно исключить `except`-списком; при экспорте модуля указывается только его имя: `import foo/bar/baz; export baz`).

**Область видимости.** Идентификатор действует от объявления до конца блока. Во вложенном блоке можно переобъявить идентификатор; после выхода снова действует первое. В одном блоке переопределение недопустимо (кроме перегрузки). Поля кортежа/объекта действуют до конца определения, в обращениях к переменной такого типа и во всех потомках. Идентификаторы модуля действуют от объявления до конца модуля; из косвенно зависимых модулей идентификаторы **недоступны**; `system` импортируется автоматически.

Если модуль импортирует один идентификатор из двух модулей, он неоднозначен; разрешается: квалификацией `module.identifier`; вызовом как подпрограммы (разрешение перегрузки); использованием в контексте, где тип выводится.

```nim
# Module A
var x*: string
proc foo*(a: string) = echo "A: ", a

# Module B
var x*: int
proc foo*(b: int) = echo "B: ", b

# Module C
import A, B

foo("abc") # A: abc
foo(123)   # B: 123
let inferred: proc (x: string) = foo
foo("def") # A: def

write(stdout, x)   # ошибка: x неоднозначен
write(stdout, A.x) # без ошибки: есть квалификатор

proc bar(a: int): int = a + 1
assert bar(x) == x + 1 # без ошибки: подходит только B.x типа int

var x = 4
write(stdout, x) # не неоднозначно: x модуля C
```

Модули могут иметь одно имя, но квалифицировать идентификатор таким именем нельзя (ошибка неоднозначности) — назначьте псевдоним:

```nim
# Module A/C: proc fb* = echo "fizz"
# Module B/C: proc fb* = echo "buzz"
import A/C as fizz
import B/C

fizz.fb() # работает
# C.fb()  # Ошибка: неоднозначный идентификатор 'C'
```

## 8. Процедуры, замыкания, контракты

### 8.1. Процедуры (`proc`)

То, что другие языки называют методами или функциями, в Nim — **процедуры**. Объявление: идентификатор, параметры, тип результата, блок кода. Параметры перечисляются через запятую или точку с запятой; тип относится ко всем параметрам перед ним — до начала списка, точки с запятой или уже типизированного параметра.

```nim
# Только запятые
proc foo(a, b: int, c, d: bool): int

# Точка с запятой для наглядности
proc foo(a, b: int; c, d: bool): int

# Не скомпилируется: a без типа, ';' останавливает распространение типа
proc foo(a; b: int; c, d: bool): int
```

Параметр может иметь значение по умолчанию; оно **вычисляется заново при каждом вызове**:

```nim
proc foo(a: int; b: int = 47): int   # b необязателен, по умолчанию 47
```

Если процедура возвращает значение, в теле доступна неявно объявленная переменная `result`. Процедуры перегружаются:

```nim
proc toLower(c: char): char = # toLower для символов
  if c in {'A'..'Z'}:
    result = char(int(c) + (int('a') - int('A')))
  else:
    result = c

proc toLower(s: string): string = # toLower для строк
  result = newString(len(s))
  for i in 0..len(s) - 1:
    result[i] = toLower(s[i]) # вызывает toLower для символов; рекурсии нет!
```

Способы вызова:

```nim
proc callme(x, y: int, s: string = "", c: char, b: bool = false) = ...

callme(0, 1, "abc", '\t', true)       # позиционные аргументы
callme 0, 1, "abc", '\t'              # как команда: () не нужны (b=false)
0.callme(1, "abc", '\t', true)         # через точку
```

**Операторы** — подпрограммы со специальным символом в имени. С одним параметром — префиксные, с двумя — инфиксные (парсер различает по позиции). Постфиксные объявить нельзя: они встроены в грамматику. Любой оператор вызывается как процедура через обратные кавычки (поэтому параметров может быть больше двух):

```nim
proc `$`(x: int): string =
  result = intToStr(x)        # префиксный оператор

proc `*+`(a, b, c: int): int =
  result = a * b + c          # умножить и сложить

assert `*+`(3, 4, 6) == `+`(`*`(3, 4), 6)
```

**Строгие определения.** Каждая локальная переменная должна быть инициализирована до использования:

```nim
proc test =
  var s: seq[string]
  s.add "abc" # недопустимо!

proc test2 =
  var s: seq[string] = @[]
  s.add "abc" # допустимо!

proc test3(cond: bool) =
  var s: seq[string]
  if cond:
    s = @["y"]
  else:
    s = @[]
  s.add "abc" # допустимо: на каждом пути s присвоен
```

### 8.2. `var`-параметры, `var`-результат, `out`, проверка заимствований

**`var`-параметры.** Изменения видны вызывающему; аргумент должен быть l-value. Реализуются как скрытые указатели:

```nim
proc divmod(a, b: int; res, remainder: var int) =
  res = a div b
  remainder = a mod b

var x, y: int
divmod(8, 5, x, y) # изменяет x и y
assert x == 1
assert y == 3
```

Для нескольких результатов чище вернуть кортеж:

```nim
proc divmod(a, b: int): tuple[res, remainder: int] =
  (a div b, a mod b)

var (q, r) = divmod(8, 5)   # распаковка кортежа
```

**Примечание:** `var`-параметры никогда не нужны ради эффективности — не-`var` параметр компилятор вправе передать по ссылке сам.

**`var`-результат.** Подпрограмма может возвращать `var`-тип — l-value, которое вызывающий может изменить:

```nim
var g = 0

proc writeAccessToG(): var int =
  result = g

writeAccessToG() = 6
assert g == 6
```

Статическая ошибка, если указатель мог бы обратиться к месту за пределами времени жизни:

```nim
proc writeAccessToG(): var int =
  var g = 0
  result = g # Ошибка!
```

У итераторов `var`-тип может быть компонентой кортежа-результата: `iterator mpairs(a: var seq[string]): (int, var string)`. В стандартной библиотеке имя подпрограммы, возвращающей `var`, начинается с `m`.

Правило заимствования: если `result` не ссылается на место в куче (в `result = X` нет доступа через `ptr`/`ref`), он должен происходить от **первого параметра**:

```nim
proc forward[T](x: var T): var T =
  result = x # ok, происходит от первого параметра

proc p(param: var int): var int =
  var x: int
  result = forward(x) # Ошибка: место происходит от `x`, не от первого параметра,
                      # и живёт в стеке
```

Время жизни того, на что указывает `result`, привязано ко времени жизни первого параметра. В будущем возможен синтаксис `proc foo(other: Y; container: var X): var T from container`.

**Проверка заимствований (borrow checking).** Предотвращает два класса ошибок: **алиасинг в вызовах** и **изменение размера при итерации**.

*Алиасинг на месте вызова.* Изменяемые (`var`) аргументы не должны пересекаться с другими аргументами того же вызова:

```nim
proc take(a: var int, b: int) =
  a = b

proc swap(a: var int, b: var int) =
  let tmp = a; a = b; b = tmp

var x = 5
take(x, x)   # Ошибка: изменяемый аргумент пересекается с неизменяемым параметром
swap(x, x)   # Ошибка: изменяемый аргумент пересекается с изменяемым параметром
```

Проверка охватывает пути полей:

```nim
type Obj = object
  x, y: int

proc update(a: var int, b: Obj) =
  a = b.x

var o = Obj(x: 1, y: 2)
update(o.x, o)   # Ошибка
swap(o.x, o.y)   # OK: непересекающиеся поля
```

Классическая ловушка — контейнер по `var` вместе с его элементом. Если `T` велик, элемент передаётся по скрытому указателю, а процедура может сделать его висячим:

```nim
proc gotcha[T](s: var seq[T]; elem: T) =
  s.shrink 0  # освобождает буфер
  use elem    # elem — висячий указатель!

gotcha(myseq, myseq[0])  # Ошибка: изменяемый аргумент пересекается с неизменяемым
```

*Изменение заимствованных путей.* При итерации заимствуется базовый путь, и менять его нельзя:

```nim
proc addItem(s: var seq[int]; val: int) =
  s.add val

var s = @[1, 2, 3]
for x in s:
  addItem(s, x)  # Ошибка: 's' заимствован и не может изменяться
```

Правило — **исключение префикса**: если заимствован путь `a.b.c`, нельзя менять ни `a`, ни `a.b`, ни `a.b.c`; соседние поля доступны:

```nim
type Config = object
  elements: seq[int]
  name: string

var c = Config(elements: @[1, 2], name: "old")
for x in c.elements:
  c.name = "new"         # OK: соседнее поле
  # c.elements.add(x)    # Ошибка: 'c.elements' заимствован
```

*Прагма `establishesBorrow`.* Подпрограмма с ней объявляет, что её результат продолжает ссылаться на **первый параметр** после возврата; заимствование длится, пока живёт то, к чему привязан результат:

```nim
var s = @[1, 2, 3]
let view = toOpenArray(s)   # заимствует 's'
s.add 4                     # Ошибка: 's' заимствован и не может изменяться
echo view[0]
```

Аннотация нужна, потому что конструктор представления хранит в результате сырой указатель, а проверка заимствований на сыром указателе теряет путь. Объявление переносит информацию через границу вызова:

```nim
converter toOpenArray*[T](s: seq[T]): openArray[T] {.inline, establishesBorrow.} =
  openArray[T](a: rawData(s), len: s.len)

func toOpenArray*[T](x: ptr UncheckedArray[T]; first, last: int): openArray[T] =
  ...   # без `establishesBorrow`: время жизни — забота вызывающего
```

Представления, переданные прямо как аргументы, покрывает проверка алиасинга (`appendFirst(s, s)` — ошибка). Заимствование не должно пережить источник: сохранение его в глобальной переменной, в `result` или через `var`-параметр отвергается, если источник — локальная переменная. Заимствование из параметра или глобальной переменной допустимо:

```nim
var g: openArray[int]

proc escape =
  var a = [1, 2, 3]
  g = toOpenArray(a)   # Ошибка: заимствование 'a' выходит за пределы процедуры

proc slice(s: seq[int]): openArray[int] =
  result = toOpenArray(s)   # OK: 's' принадлежит вызывающему

proc outlivesSource =
  var view: openArray[int]
  block:
    var a = [1, 2, 3]
    view = toOpenArray(a)   # Ошибка: заимствование 'a' выходит за область
  discard view.len

proc fine =
  var s = @[1, 2, 3]
  var view: openArray[int]
  block:
    view = toOpenArray(s)   # OK: 's' переживает блок
  discard view.len
```

Вынести заимствование наружу может только ссылочный результат; чтение простого значения копирует его, и оно уходит свободно:

```nim
proc first(s: seq[int]): int =
  for x in s: return x   # OK: 'x' — копия, не представление
  return -1
```

**`out`-параметры.** Как `var`, но параметр обязан быть записан до использования:

```nim
proc myopen(f: out File; name: string): bool =
  f = default(File)
  result = open(f, name)
```

Обычно лучше возвращать результат, но API/ABI могут этому мешать. `out T` отображается в скрытый указатель. POSIX `stat`:

```nim
proc stat*(a1: cstring, a2: out Stat): cint {.importc, header: "<sys/stat.h>".}
```

Компилятор проверяет, что на каждом пути до возврата установлен каждый выходной параметр:

```nim
proc p(x: out int; y: out string; cond: bool) =
  x = 4
  if cond:
    y = "abc"
  # ошибка: не на каждом пути инициализирован 'y'
```

Нельзя передавать l-value супертипа в `out T`:

```nim
type
  Superclass = object of RootObj
    a: int
  Subclass = object of Superclass
    s: string

proc init(x: out Superclass) =
  x = Superclass(a: 8)

var v: Subclass
init v
use v.s # поле 's' так и не было инициализировано!
```

### 8.3. Замыкания

Замыкание — процедура, захватывающая переменные окружающей области. В отличие от Nim 2, замыкание **никогда не выводится**: и процедура, и процедурный тип, который её хранит, помечаются `.closure.`. Значение `.closure.`-процедуры — пара из указателя на процедуру и указателя на неявно передаваемое *окружение* (два машинных слова).

```nim
proc createCounter(): (proc(): int {.closure.}) =
  var count = 0
  result = proc(): int {.closure.} =
    inc count
    return count

let counter = createCounter()
echo counter() # 1
echo counter() # 2
echo counter() # 3
```

Без аннотации на литерале захват — ошибка, даже если цель присваивания уже `.closure.`-тип:

```nim
proc main =
  var n = 3
  # Error: cannot access local variable `n` from another routine;
  # mark the proc with `.closure`
  let cb: proc(): bool {.closure.} = proc(): bool = n > 0
  discard cb()
```

Замыкания захватывают переменные **по ссылке**, поэтому изменения видны всем экземплярам:

```nim
proc createAdder(x: int): (proc(y: int): int {.closure.}) =
  result = proc(y: int): int {.closure.} =
    return x + y

let add5 = createAdder(5)
let add10 = createAdder(10)
echo add5(3)  # 8
echo add10(3) # 13

proc createAccumulator(): (proc(x: int): int {.closure.}) =
  var total = 0
  result = proc(x: int): int {.closure.} =
    total += x
    return total

let acc = createAccumulator()
echo acc(5)  # 5
echo acc(3)  # 8
echo acc(7)  # 15
```

Захваченная переменная живёт в окружении, а не в стеке объявившей её подпрограммы: её время жизни — время жизни замыкания. Окружение — отслеживаемый `ref`, уничтожаемый обычным управлением памятью, когда исчезает последнее замыкание. Незамыкающая процедура неявно приводится к `.closure.`-типу с пустым окружением:

```nim
proc double(x: int): int = x * 2
proc apply(f: proc(x: int): int {.closure.}; v: int): int = f(v)
echo apply(double, 21) # 42
```

**Feature `autoclosures`.** Аннотировать каждый захватывающий литерал утомительно при портировании Nim 2. `{.feature: "autoclosures".}` восстанавливает неявное поведение для *объявлений подпрограмм*: proc, func, method или converter, вложенные в другую подпрограмму, помечаются `.closure.` неявно, независимо от захвата:

```nim
{.feature: "autoclosures".}

proc createCounter(): (proc(): int {.closure.}) =
  var count = 0
  result = proc(): int =   # неявно `.closure.`
    inc count
    return count
```

Feature не влияет на *процедурные типы*: `proc(): int` остаётся простым указателем, и лишь `proc(): int {.closure.}` хранит замыкание. Подразумевается мета-фичей `"v2"`.

*Итераторы.* Под этой feature анонимный литерал `iterator(): T = ...` неявно `.closure.` (именованный итератор — никогда), а `iterator(): T` как **тип** означает `iterator(): T {.closure.}`. Без feature неаннотированный тип итератора населён только `nil`. `.passive.` по-прежнему пишется явно.

```nim
{.feature: "autoclosures".}

func iter[T](s: seq[T]): iterator(): T =        # тип: неявно `.closure.`
  return iterator(): T =                        # литерал: неявно `.closure.`
    for x in s:
      yield x

func take[T](it: iterator(): T; n: int): iterator(): T =
  return iterator(): T =
    var k = 0
    for v in it():
      if k >= n: break
      yield v
      inc k

for x in take(iter(@[1, 2, 3, 4]), 2)():
  echo x # 1, 2
```

### 8.4. Анонимные процедуры и `do`

```nim
var cities = @["Frankfurt", "Tokyo", "New York", "Kyiv"]

cities.sort(proc (x, y: string): int =
  cmp(x.len, y.len))

# нотация do:
sort(cities) do (x, y: string) -> int:
  cmp(x.len, y.len)

# меньше скобок: метод + команда:
cities = cities.map do (x: string) -> string:
  "City of " & x
```

`do` пишется после скобок обычных параметров; процедурное выражение из блока `do` добавляется в вызов последним аргументом. `do` со списком параметров или прагм — анонимный `proc`, а `do` без параметров — обычный список операторов, что позволяет шаблонам получать блоки отступами:

```nim
import std/syncio

template myif(cond: bool; thenPart, elsePart: untyped) =
  if cond:
    thenPart
  else:
    elsePart

myif true:
  echo "bar"
do:
  echo "baz"
```

### 8.5. `func` и побочные эффекты

`func` — `proc`, по умолчанию `noSideEffect`; то же для `iterator` и `converter`. Обычный `proc` по умолчанию имеет побочные эффекты. Подпрограмма **без побочных эффектов** не обращается к глобальным и thread-local переменным и не вызывает подпрограмм с побочными эффектами. **Вывода `noSideEffect` нет.** Умолчания переопределяются явными `.noSideEffect` и `.sideEffect`:

```nim
proc pureComputation(x: int): int {.noSideEffect.} =
  x * x

func withSideEffect(x: int): int {.sideEffect.} =
  echo x  # допустимо благодаря явной аннотации
  x * x
```

### 8.6. Контракты

Подпрограмма может объявить предусловие прагмой `requires`; выражение может называть параметры, `result` (для `ensures`) и константы:

```nim
func `[]`*[T](s: seq[T]; i: int): var T {.requires: (i < s.len and i >= 0).} =
  s.data[i]
```

Контракт проверяется **на месте вызова**: компилятор подставляет аргументы вместо параметров и спрашивает, следует ли из известного на этом пути выполнение. Три ответа:

- **доказано** — ничего не происходит, контракт ничего не стоил;
- **неизвестно** — вызов сохраняет проверку времени выполнения, которую несёт вызываемая (`if not cond: panic`); её убирают `--boundchecks:off` и `-d:danger`;
- **нарушено** — известное на этом пути влечёт *отрицание* контракта: ошибка компиляции.

```nim
proc needsPositive(x: int) {.requires: x > 0.}

needsPositive(0)          # Error: contract violated: 0 < x
needsPositive(readInt())  # неизвестно: проверяется во время выполнения
```

«Неизвестно» — ответ по умолчанию, а не ошибка: индексирование `seq`/`string`/`openArray` *и есть* контракт, а доказатель пока не отслеживает длину контейнера через его построение (`var s = newSeq[int](4)` и затем `s[0]` — неизвестно). Надёжно доказывается: литералы и локальные переменные с известным значением; значение под подходящей защитой (включая `a and b` и `if i < 0 or i >= s.len: return`); `s.len`; диапазон переменной цикла `for`, взятый из `ensures` итератора; счётный цикл, индукционная переменная которого движется в одну сторону:

```nim
var i = 0
while i < s.len:
  use s[i]                # доказано: `i < s.len` — защита, `0 <= i` — инвариант
  inc i

iterator `..<`*[T: Ordinal](a, b: T): T {.inline,
    ensures: (a <= result and result < b).} = ...

for i in 0 ..< s.len:
  use s[i]                # доказано; проверка границ во время выполнения не нужна
```

Два модульных переключателя:

- `{.feature: "staticContracts".}` — каждый контракт, который несёт вызов в этом модуле, должен быть *доказан*. Сюда движется язык.
- `{.feature: "runtimeContracts".}` — вызовы вообще не оцениваются статически, только проверка во время выполнения. Побеждает, если заданы оба.

**Утверждения и допущения** в теле:

- `{.assert: cond.}` — утверждение, которое компилятор обязан **доказать**. Оценивается только при компиляции, ничего во время выполнения не порождается; недоказанное — ошибка при любых features, отключить нельзя. После него `cond` известно.
- `{.assume: cond.}` делает `cond` известным **без доказательства**. Это слово программиста: ложное допущение — неопределённое поведение.

```nim
proc get(s: seq[int]; i: int): int =
  if i >= 0 and i < s.len:
    {.assert: i + 1 <= s.len.}   # доказано из защиты
    result = s[i]

proc first(s: seq[int]): int =
  {.assume: s.len > 0.}          # слово вызывающего; ничего не проверяется
  result = s[0]
```

`assert` из `std/assertions` — другое: обычная проверка времени выполнения, отключаемая `-d:noAssertions` и `-d:danger`. Обязательство, которое выполняет только она, перестаёт быть доказуемым при её отключении — сборка тогда падает, а не теряет проверку. Такие утверждения формулируйте через `{.assert.}`.

### 8.7. Экспорт и синтаксис вызова

**Маркер экспорта.** Символ с `*` экспортируется из модуля:

```nim
proc exportedEcho*(s: string) = echo s
proc `*`*(a: string; b: int): string =
  result = newStringOfCap(a.len * b)
  for i in 1..b: result.add a

var exportedVar*: int
const exportedConst* = 78
type
  ExportedType* = object
    exportedField*: int
```

**Синтаксис вызова метода.** `obj.methodName(args)` вместо `methodName(obj, args)`; скобки можно опустить: `obj.len`. Работает для первого аргумента любого типа:

```nim
echo "abc".len          # то же, что echo len "abc"
echo "abc".toUpper()
echo {'a', 'b', 'c'}.card
stdout.writeLine("Hallo") # то же, что writeLine(stdout, "Hallo")
```

Конфликтует с явным обобщённым вызовом: `x.p[T]` всегда разбирается как `(x.p)[T]`. Нотация `[: ]`: `x.p[:T]` парсер переписывает в `p[T](x)`, а `x.p[:T](y)` — в `p[T](x, y)`.

**Командный синтаксис.** Подпрограммы без `()`, если вызов — оператор. Для выражений допустим один аргумент: `echo f 1, f 2` — это `echo(f(1), f(2))`. Метод + команда добавляют ещё аргумент:

```nim
proc optarg(x: int, y: int = 0): int = x + y
proc singlearg(x: int): int = 20*x

echo optarg 1, " ", singlearg 2  # печатает "1 40"

let fail = optarg 1, optarg 8   # Неверно: слишком много аргументов для команды
let x = optarg(1, optarg 8)     # обычный вызов с двумя аргументами
let y = 1.optarg optarg 8       # то же без скобок
assert x == y
```

В командном синтаксисе нельзя использовать сложные выражения (анонимные процедуры, `if`, `case`, `try`). Вызовы без аргументов требуют `()`, чтобы отличать вызов от значения первого класса.

### 8.8. Перегрузка оператора индексации

`[]` перегружается подпрограммой `[]`, присваивание по индексу — `[]=` (имеет приоритет над присваиванием результату `[]`):

```nim
type Foo = object
  data: seq[int]

proc `[]`(foo: Foo; i: int): int =
  result = foo.data[i]
proc `[]=`(foo: var Foo; i, val: int) =
  foo.data[i] = val

var foo = Foo(data: @[1, 2, 3])
echo foo[1] # 2
foo[1] = 5
echo foo.data # @[1, 5, 3]
```

Перегрузки нельзя применять к самим подпрограммам и типам: конфликт с синтаксисом обобщённых параметров (`foo[int](1, 2, 3)`, `Foo[int]`).

### 8.9. Методы

Процедуры всегда используют статическую диспетчеризацию. Методы — динамическую; объект должен быть ссылочным типом:

```nim
type
  Expression = ref object of RootObj ## абстрактный базовый класс
  Literal = ref object of Expression
    x: int
  PlusExpr = ref object of Expression
    a, b: Expression

method eval(e: Expression): int =
  quit "abstract method without override"

method eval(e: Literal): int = return e.x

method eval(e: PlusExpr): int =
  # опирается на динамическое связывание
  result = eval(e.a) + eval(e.b)

proc newLit(x: int): Literal = Literal(x: x)
proc newPlus(a, b: Expression): PlusExpr = PlusExpr(a: a, b: b)

echo eval(newPlus(newPlus(newLit(1), newLit(2)), newLit(4)))
```

Конструкторы — процедуры (статическое связывание), `eval` — метод. Динамическую диспетчеризацию подавляет `system.procCall` (аналог `super`):

```nim
type
  Thing = ref object of RootObj
  Unit = ref object of Thing
    x: int

method m(a: Thing) =
  echo "base"

method m(a: Unit) =
  procCall m(Thing(a))   # вызвать базовый метод
  echo "1"
```

**Пояснение.** Мультиметодов в Nim 3 нет: диспетчеризация идёт только по первому параметру.

### 8.10. Итераторы, `for` и конвертеры

`for` обходит элементы контейнера через `iterator`; как и `while`, открывает неявный блок. Переменные цикла объявлены до конца тела; типы выводятся из типа возврата итератора. `yield` связывает данные с переменными цикла и передаёт управление в тело; состояние итератора сохраняется между вызовами:

```nim
iterator items*(a: string): char {.inline.} =
  var i = 0
  while i < len(a):
    yield a[i]
    inc i

for ch in items("hello world"): # `ch` — переменная итерации
  echo ch
```

Компилятор генерирует код, как если бы написано `var i = 0; while i < len(a): var ch = a[i]; echo ch; inc i`. Если итератор возвращает кортеж, переменных итерации может быть столько же, сколько компонент (неявная распаковка).

**Конвертеры.** Как процедура, но расширяет отношение «неявно приводимо»:

```nim
type
  MyInt = distinct int

# плохой стиль: Nim — не C.
converter toBool(x: MyInt): bool = x != 0

if MyInt(4):
  echo "compiles"
```

Конвертер можно вызывать явно. **Неявное объединение конвертеров в цепочку не поддерживается:** при A→B и B→C неявного A→C нет.

## 9. Управление памятью: хуки и перемещение

### 9.1. Хуки времени жизни

**Типо-привязанный оператор** (type bound operator) — `proc` или `func`, имя которой начинается с `=`, но не является оператором (то есть не состоит только из символов, как `==`). Типо-привязанный оператор, объявленный для типа, действует на тип независимо от того, виден ли он в области (даже приватный). Это: `=destroy`, `=copy`, `=sink`, `=trace`, `=wasMoved`, `=dup`.

Эти операции **переопределяются**, а не перегружаются: реализация автоматически «поднимается» (lifting) на составные типы. Например, если у `T` переопределено присваивание, оно используется и для `seq[T]`. Привязываться они должны к номинальному типу. На типо-привязанных операциях основано *управление памятью по областям видимости*.

### 9.2. Пример: свой `seq`

```nim
type
  myseq*[T] = object
    len, cap: int
    data: unchecked ptr UncheckedArray[T] # \
      # unchecked ptr: `[]`, `[]=` опираются на инвариант len > 0 => data != nil

proc `=destroy`*[T](x: myseq[T]) =
  if x.data != nil:
    for i in 0..<x.len: `=destroy`(x.data[i])
    dealloc(x.data)

proc `=wasMoved`*[T](x: var myseq[T]) =
  x.data = nil
  x.len = 0

proc `=trace`[T](x: var myseq[T]; env: pointer) =
  # `=trace` объясняет сборщику циклов `--mm:orc`, как обходить граф объектов
  if x.data != nil:
    for i in 0..<x.len: `=trace`(x.data[i], env)

proc `=copy`*[T](a: var myseq[T]; b: myseq[T]) =
  if a.data == b.data: return          # самоприсваивание — ничего не делать
  `=destroy`(a)
  a.len = b.len
  a.cap = b.cap
  a.data = nil
  if b.data != nil:
    a.data = cast[typeof(a.data)](alloc(a.cap * sizeof(T)))
    for i in 0..<a.len:
      a.data[i] = b.data[i]

proc `=dup`*[T](a: myseq[T]): myseq[T] {.nodestroy.} =
  # оптимизированный вариант `=wasMoved(tmp); `=copy(tmp, src)`;
  # обязателен, если есть собственный `=copy`
  result = myseq[T](len: a.len, cap: a.cap, data: nil)
  if a.data != nil:
    result.data = cast[typeof(result.data)](alloc(result.cap * sizeof(T)))
    for i in 0..<result.len:
      result.data[i] = `=dup`(a.data[i])

proc `=sink`*[T](a: var myseq[T]; b: myseq[T]) =
  # присваивание-перемещение, необязательно; без него компилятор
  # использует `=destroy` и `copyMem`
  `=destroy`(a)
  a.len = b.len
  a.cap = b.cap
  a.data = b.data

proc add*[T](x: var myseq[T]; y: sink T) =
  if x.len >= x.cap:
    x.cap = max(x.len + 1, x.cap * 2)
    x.data = cast[typeof(x.data)](realloc(x.data, x.cap * sizeof(T)))
  x.data[x.len] = y
  inc x.len

proc `[]`*[T](x: myseq[T]; i: Natural): var T =
  assert i < x.len
  result = x.data[i]

proc `[]=`*[T](x: var myseq[T]; i: Natural; y: sink T) =
  assert i < x.len
  x.data[i] = y

proc createSeq*[T](elems: openArray[T]): myseq[T] =
  result = myseq[T](
    len: elems.len,
    cap: elems.len,
    data: cast[typeof(result.data)](alloc(result.cap * sizeof(T))))
  for i in 0..<result.len: result.data[i] = elems[i]

proc len*[T](x: myseq[T]): int {.inline.} = x.len
```

### 9.3. Хук `=destroy`

Освобождает память объекта и другие ресурсы. Переменные уничтожаются этим хуком при выходе из области видимости или перед возвратом из подпрограммы, где объявлены. Параметр — `var T` или `T` (`var` обычно не нужен):

```nim
proc `=destroy`(x: T)
# или
proc `=destroy`(x: var T)
```

Общий шаблон:

```nim
proc `=destroy`(x: T) =
  # сначала проверить, не перемещён ли 'x' куда-то (поле — `nil ptr`):
  if x.field != nil:
    freeResource(x.field)
```

### 9.4. Хук `=wasMoved`

Переводит объект в состояние «уничтожать нечего». Прототип: ` proc  `=wasMoved`(x: var T)`. Обычно какое-то nil-допускающее поле ставится в `nil`:

```nim
proc `=wasMoved`(x: var T) =
  x.field = nil  # field имеет тип `nil ptr`
```

### 9.5. Хук `=sink`

Перемещает объект: ресурсы забираются у источника и отдаются получателю. Источник приводится к значению по умолчанию (`wasMoved(x)`), чтобы его деструктор ничего не освободил. Если хука нет, компилятор использует комбинацию `=destroy` и `copyMem` — это эффективно, поэтому свой `=sink` нужен редко: достаточно `=destroy` и `=copy`.

```nim
proc `=sink`(dest: var T; source: T)

proc `=sink`(dest: var T; source: T) =
  `=destroy`(dest)
  wasMoved(dest)
  dest.field = source.field
```

`=sink` не обязан проверять самоприсваивание (см. 9.9).

### 9.6. Хук `=copy`

Обычное присваивание концептуально копирует. `=copy` вызывается для присваиваний, которые не удалось превратить в `=sink`:

```nim
proc `=copy`(dest: var T; source: T)

proc `=copy`(dest: var T; source: T) =
  # защита от самоприсваивания:
  if dest.field != source.field:
    `=destroy`(dest)
    wasMoved(dest)
    dest.field = duplicateResource(source.field)
```

`=copy` можно пометить `{.error.}` — тогда любое присваивание, которое привело бы к копии, запрещено на этапе компиляции (перед `{.error.}` нет `=`; собственное сообщение компилятор не выводит):

```nim
proc `=copy`(dest: var T; source: T) {.error.}
```

**Пример (авторский): тип только для перемещения.**

```nim
type
  Handle = object
    fd: nil ptr cint   # nil означает «ничего не принадлежит»

proc `=destroy`(h: Handle) =
  if h.fd != nil: closeFd(h.fd)

proc `=wasMoved`(h: var Handle) = h.fd = nil
proc `=copy`(a: var Handle; b: Handle) {.error.}

var a = openHandle()
# var b = a        # ошибка компиляции: копирование запрещено
var b = move(a)    # допустимо: a теперь «пуст»
```

### 9.7. Хук `=dup`

`=dup(x)` можно считать оптимизацией замены `wasMoved(dest); =copy(dest, x)`:

```nim
proc `=dup`(x: T): T

type
  Ref[T] = object
    data: nil ptr T
    rc: nil ptr int

proc `=dup`[T](x: Ref[T]): Ref[T] =
  result = x
  if x.rc != nil:
    inc x.rc[]
```

### 9.8. Хук `=trace`

Пользовательский **контейнер** может поддержать сборщик циклов хуком `=trace`. Если хука нет, циклические структуры, построенные через контейнер, могут утекать, но безопасность памяти не нарушается:

```nim
proc `=trace`(dest: var T; env: pointer)
```

`env` — внутреннее состояние сборщика; передавайте его во встроенные вызовы `=trace`.

### 9.9. Семантика перемещения

«Перемещение» — оптимизированное копирование. Если источник дальше не используется, копию можно заменить перемещением. Запись `lastReadOf(x)` значит, что `x` дальше не используется; свойство вычисляется статическим анализом потока управления, но может быть принудительным через `system.move`.

`system.ensureMove` спрашивает, способен ли анализ выполнить перемещение: `move` принуждает к нему и вызывает `=wasMoved`, а `ensureMove` — аннотация без операции во время выполнения; если безопасность не доказана, это статическая ошибка:

```nim
proc main(normalParam: string; sinkParam: sink string) =
  var x = "abc"
  # допустимо:
  let valid = ensureMove x
  # недопустимо:
  let invalid = ensureMove normalParam
  # допустимо:
  let alsoValid = ensureMove sinkParam
```

**`swap`.** Необходимость проверять самоприсваивание и уничтожать прежние объекты внутри `=copy`/`=sink` — довод считать `system.swap` отдельным встроенным примитивом, который просто обменивает каждое поле через `copyMem`. `swap(a, b)` **не** реализован как `let tmp = move(b); b = move(a); a = move(tmp)`. Следствия: объекты, содержащие указатели на один и тот же объект, моделью Nim не поддерживаются; `seq` могут использовать `realloc`.

**`sink`-параметры.** Чтобы переместить переменную в коллекцию, используют `sink`-параметры. Место, переданное в `sink`-параметр, не должно использоваться дальше; это проверяет статический анализ по графу потока управления. Если нельзя доказать, что это последнее использование, делается копия, и она передаётся в `sink`-параметр. `sink`-параметр *может* быть потреблён один раз в теле, но может и не потребляться вовсе: сигнатура `proc put(t: var Table; k: sink Key, v: sink Value)` должна быть возможна без перегрузок, а `put` может не забрать `k`, если ключ уже есть. `sink` задаёт аффинную, а не линейную систему типов.

Анализ ограничен локальными переменными; поля объектов и кортежей — отдельные сущности:

```nim
proc consume(x: sink Obj) = discard "no implementation"

proc main =
  let tup = (Obj(), Obj())
  consume tup[0]
  # ok, потреблён только tup[0], tup[1] жив:
  echo tup[1]
```

Иногда нужно явно `move` значение в конечную позицию:

```nim
proc main =
  var dest, src: array[10, string]
  # ...
  for i in 0..high(dest): dest[i] = move(src[i])
```

### 9.10. Правила переписывания

Ресурсы уничтожаются при выходе из области видимости.

| Исходное | Результат | Правило |
| --- | --- | --- |
| `var x: T; stmts` | `var x: T; try stmts finally: =destroy(x)` | destroy-var |
| `g(f(...))` | `g(let tmp; bitwiseCopy tmp, f(...); tmp)` с `finally: =destroy(tmp)` | nested-function-call |
| `x = f(...)` | `=sink(x, f(...))` | function-sink |
| `x = lastReadOf z` | `=sink(x, z); =wasMoved(z)` | move-optimization |
| `v = v` | ничего | self-assignment-removal |
| `x = y` | `=copy(x, y)` | copy |
| `f_sink(g())` | `f_sink(g())` | call-to-sink |
| `f_sink(notLastReadOf y)` | `(let tmp = =dup(y); f_sink(tmp))` | copy-to-sink |
| `f_sink(lastReadOf y)` | `f_sink(y); =wasMoved(y)` | move-to-sink |

Конструкция объектов и массивов трактуется как вызов функции с `sink`-параметрами. **Устранение деструкторов:** `=wasMoved(x)` с последующим `=destroy(x)` взаимно уничтожаются — реализации рекомендуется это использовать (текущая использует).

**Самоприсваивания.** `=sink` вместе с `=wasMoved` может справиться с самоприсваиванием, но тонко. Простое `x = x` нельзя превратить в `=sink(x, x); =wasMoved(x)` — потеряется значение `x`. Поэтому простые самоприсваивания — символы `x = x` и доступ к полю `x.f = x.f` — превращаются в пустой оператор. Сложный случай — вариант `x = f(x)`, например `x = select(rand() < 0.5, x, y)`:

```nim
proc select(cond: bool; a, b: sink string): string =
  if cond:
    result = a # перемещает a в result
  else:
    result = b # перемещает b в result

proc main =
  var x = "abc"
  var y = "xyz"
  # возможное самоприсваивание:
  x = select(true, x, y)
```

Переписывается в:

```nim
proc select(cond: bool; a, b: sink string): string {.nodestroy.} =
  if cond:
    result = a
    `=wasMoved`(a)
  else:
    result = b
    `=wasMoved`(b)
  `=destroy`(b)
  `=destroy`(a)

proc main {.nodestroy.} =
  var
    x: string
    y: string
  x = "abc"
  y = "xyz"
  `=sink`(x, select(true,
    let blitTmp = x
    `=wasMoved`(x)
    blitTmp,
    let blitTmp = y
    `=wasMoved`(y)
    blitTmp))
  echo [x]
  `=destroy`(y)
  `=destroy`(x)
```

Вручную можно убедиться, что преобразование корректно для самоприсваиваний.

### 9.11. Прагма `cursor`

Тип `ref` реализован теми же хуками, а значит и подсчётом ссылок. Поэтому циклические структуры нельзя освободить сразу. Прагма `cursor` разрывает циклы декларативно:

```nim
type
  Node = ref object
    left: Node              # владеющая ссылка
    right {.cursor.}: Node  # невладеющая ссылка
```

Это **не** `weak_ptr` из C++: поле `right` не участвует в подсчёте, это сырой указатель без проверок во время выполнения. Автоматический подсчёт ссылок также добавляет накладные расходы при обходе связных структур; `cursor` помогает их избежать:

```nim
var it {.cursor.} = listRoot
while it != nil:
  use(it)
  it = it.next
```

`cursor` вообще предотвращает пары конструирование/уничтожение и полезен и в других контекстах. Альтернатива — сырые `ptr`, но они неудобнее и опаснее для развития языка: позже компилятор сможет доказывать безопасность `cursor`, а для `ptr` он вынужден молчать.

### 9.12. Подъём хуков (hook lifting)

Хуки кортежа `(A, B, ...)` порождаются подъёмом хуков его компонент: копирование `x = y` — это `x[0] = y[0]; x[1] = y[1]; ...`, так же `=sink` и `=destroy`. Аналогично для значимых составных типов — `object` и `array`. Для `object` сгенерированные компилятором хуки можно переопределить: например, чтобы обходить структуру эффективнее или избежать глубокой рекурсии.

### 9.13. Прагма `nodestroy`

Подавляет вставку хуков. Нужна, чтобы специализировать обход объекта и избежать глубокой рекурсии:

```nim
type Node = ref object
  x, y: int32
  left, right: nil Node

type Tree = object
  root: Node

proc `=destroy`(t: Tree) {.nodestroy.} =
  # явный стек, чтобы не получить переполнение стека:
  var s: seq[Node] = @[t.root]
  while s.len > 0:
    let x = s.pop
    if x.left != nil: s.add(x.left)
    if x.right != nil: s.add(x.right)
    # освободить память явно:
    `=dispose`(x)
  # благодаря .nodestroy деструктор `s` тоже не вызывается неявно:
  `=destroy`(s)
```

Как видно, решение вряд ли достаточно и со временем должно быть заменено лучшим.

### 9.14. Копирование при записи (copy on write)

Строковые литералы реализованы как «copy on write»: при присваивании литерала переменной копия не создаётся, переменная указывает на литерал, а копия откладывается до первой записи:

```nim
var x = "abc"  # без копии
var y = x      # без копии
y[0] = 'h'     # копия
```

Абстракция ломается для `addr x`: неизвестно, будет ли адрес использован для изменений. Перед взятием адреса нужно вызвать `prepareMutation`:

```nim
var x = "abc"
var y = x

prepareMutation(y)
moveMem(addr y[0], addr x[0], 3)
assert y == "abc"
```

### 9.15. Неперегружаемые встроенные

Из-за простоты реализации нельзя перегружать (требуют особой семантической проверки): `declared, defined, definedInScope, compiles, sizeof, is, getAst, astToStr, procCall`. Они ближе к ключевым словам, но переопределение может *затенить* определение из `system`. Из них не следует писать в точечной нотации `x.f`: `declared, defined, definedInScope, compiles, getAst, astToStr` — так как `x` нельзя типизировать до передачи в `f`.

## 10. Обработка ошибок

Обработка ошибок в Nimony основана на стандартном перечислении `ErrorCode`, которое должно покрывать все возможные ошибки программы: `Success`, `Failure`, `OverflowError`, `IndexError`, `SyntaxError` и другие. Это обычный enum, поэтому его можно вернуть как результат:

```nim
proc problem(): ErrorCode = return Failure
```

Но его можно и «поднять» (`raise`), что влияет на поток управления вызывающего:

```nim
proc problem() {.raises.} = raise Failure
```

Подпрограмма, которая может поднять ошибку, **всегда** должна быть помечена `{.raises.}`. Обрабатывается ошибка оператором `try`:

```nim
try:
  problem()
except ErrorCode as e:
  echo "Error: ", e
```

**Пояснение.** Это не исключения Nim 2: нет раскрутки стека, а `raises` — часть сигнатуры, поэтому поток ошибок виден вызывающему и компилятору. Это и есть причина «более быстрого кода» в списке отличий (раздел 1.2).

### 10.1. Типы в `raises`

`{.raises.}` означает `{.raises: ErrorCode.}`. Единственный другой тип, который подпрограмма может поднять, — `ref`-объект, обычно наследник `Exception`:

```nim
type ParseError = ref object of Exception
  pos: int

proc parse(s: string): int {.raises: ParseError.} =
  raise ParseError(msg: "unexpected end", pos: s.len)
```

Ветка `except` — фильтр по типу: `except ErrorCode` ловит только значения `ErrorCode`, `except T` для `ref`-типа `T` ловит `T` и его подтипы, а голый `except:` ловит всё. Ветки пробуются по порядку. Всё, что поднимает вызов, должно быть поймано объемлющей веткой `except` либо совпадать с тем, что поднимает сама вызывающая подпрограмма (для `ref`-типа — её подтип). Ничто не преобразует `ErrorCode` в `ref`-исключение или обратно — это пишется явно:

```nim
proc lookup(t: Table[string, int]; key: string): int {.raises: ParseError.} =
  try:
    result = t[key]           # поднимает `KeyError`, это `ErrorCode`
  except ErrorCode:
    raise ParseError(msg: "unknown key " & key)
```

Голый `raise` внутри ветки `except` поднимает заново то, что эта ветка поймала.

### 10.2. Оператор `try`

Общая форма: `try <операторы> except <операторы> finally <операторы>`. Операторы после `try` выполняются последовательно, пока не поднята ошибка. При ошибке выполняется блок `except`. Независимо от ошибки выполняется блок `finally` — после `except`.

```nim
# читает две первые строки текстового файла с числами и складывает их
var f: File
if open(f, "numbers.txt"):
  try:
    var a = readLine(f)
    var b = readLine(f)
    echo "sum: " & $(parseInt(a) + parseInt(b))
  except ErrorCode as e:
    case e
    of OverflowError:
      echo "overflow!"
    of ValueError:
      echo "value error!"
    of IOError:
      echo "io error!"
    of SyntaxError:
      echo "syntax error!"
    of RangeError:
      echo "range error!"
    else:
      echo "unknown error! ", e
  finally:
    close(f)
```

### 10.3. `try` как выражение

Тип ветки `try` должен подходить к типам веток `except`, а ветка `finally` всегда `void`:

```nim
from std/strutils import parseInt

let x = try: parseInt("133a")
        except: -1
        finally: echo "hi"
```

Чтобы не плодить запутанный код, есть ограничение парсера: если `try` идёт после `(`, он должен быть записан в одну строку:

```nim
from std/strutils import parseInt
let x = (try: parseInt("133a") except: -1)
```

### 10.4. `defer`

`defer` — синтаксический сахар для секции `finally`. Код

```nim
proc p() =
  setup()
  try:
    use()
  finally:
    atLast()
```

можно записать так:

```nim
proc p() =
  setup()
  defer: atLast()
  use()
```

`defer` планирует блок на выход из текущей области — при нормальном завершении, ошибке или раннем `return`:

```nim
proc processFile(filename: string) =
  var f: File
  if open(f, filename):
    defer: close(f)  # будет вызван при выходе из процедуры
    if someError():
      return         # close(f) всё равно вызывается
```

Можно использовать в любой блочной области (процедуры, методы, итераторы). Несколько `defer` в одной области выполняются в обратном порядке (последний вошёл — первый вышел):

```nim
proc example() =
  defer: echo "third"
  defer: echo "second"
  defer: echo "first"
  echo "body"
  # Вывод: body, first, second, third
```

## 11. Концепты, обобщения, шаблоны

### 11.1. Секции типов

Секция начинается с `type` и содержит несколько определений. Определения могут быть рекурсивными и даже взаимно рекурсивными. Номинальные типы (`object`, `enum`) определяются только в секции `type`:

```nim
type # взаимно рекурсивные типы
  Node = ref object  # объект под управлением памяти (ref)
    le, ri: nil Node # левое и правое поддеревья (могут быть nil)
    sym: ref Sym     # листья содержат ссылку на Sym

  Sym = object       # символ
    name: string     # имя символа
    line: int        # строка объявления
    code: Node       # абстрактное синтаксическое дерево символа
```

**Пояснение.** Forward-объявлений не нужно: порядок определений в секции не важен.

### 11.2. Концепты

Концепт описывает ограничение: какие операции должен предоставлять тип, чтобы удовлетворять концепту:

```nim
type
  Comparable = concept
    proc `<=`(a, b: Self): bool
    proc `==`(a, b: Self): bool
    proc `<`(a, b: Self): bool
```

`Self` — сам определяемый концепт; нужен, чтобы избежать рекурсии: `proc <=(a, b: Comparable): bool` недопустимо. Концепт — **чисто компилятный** механизм, нужный для проверки типов обобщённого кода, а не механизм времени выполнения. Он **не** сопоставим с интерфейсом C#/Java.

**Когда тип удовлетворяет концепту.** Тип `A` удовлетворяет концепту, если каждое требование, прочитанное как вызов, разрешается для `A`. Для каждого требования `Self` заменяется на `A` в сигнатуре, и получившийся вызов разрешается обычными правилами разрешения перегрузки: работают неявные преобразования и подтипы, а обобщённый кандидат считается, только если `A` удовлетворяет его собственным ограничениям. Тип результата кандидата должен быть присваиваем типу возврата требования. Именно такую проверку позже выполняет инстанцирование обобщённого тела с `A`, так что тип, удовлетворяющий концепту, подходит любому обобщению, которое его требует.

Следствия:

- `int8` удовлетворяет `Stringable`, хотя `$` объявлен только для `int64`: вызов `$(x)` расширяет аргумент.
- Параметр `var Self` удовлетворяется только кандидатом с `var`-параметром, а простой `Self` нельзя передать в `var`-параметр.
- Требование `func` выполняют `func`, `proc` с `noSideEffect` и `template`; требование `proc` — всё это плюс `proc`.
- Требование `iterator` выполняет только итератор.
- Если вызову подходит несколько кандидатов, требование удовлетворено; неоднозначность решается при инстанцировании. (Эта мягкость — только при *проверке* соответствия; вызов внутри инстанцированного обобщённого тела использует обычное разрешение перегрузки, включая предпочтение `ConceptScope` из «Module-of-origin», 7.2.)
- Кандидат, чьё собственное ограничение — проверяемый концепт (например `proc <=[T: Orderable](x, y: T)` при проверке `Orderable`), не засчитывается: тип удовлетворяет концепту только выводом, не предполагающим вывод.
- Кандидаты ищутся по имени там, где их нашёл бы вызов: в модуле, объявляющем концепт; в модуле, объявляющем проверяемый тип (операции привязаны к типу тем, что живут в его модуле); и во всех модулях, видимых в месте проверки.

Концепт, наследующий через `concept of`, добавляет требования родителей к своим; все проверяются одинаково. «Модуль, объявляющий концепт» — это модуль концепта, в котором записано требование, а не проверяемого.

### 11.3. Атомы и контейнеры

Концепты бывают двух видов: **атомы** и **контейнеры**. Контейнер — обобщённый концепт вроде `Iterable[T]`; у атома нет обобщённых параметров (как у `Comparable`). Синтаксически концепт — список объявлений `proc` и `iterator`.

**Атомарные концепты:**

```nim
type
  Comparable = concept # без T, атом
    proc cmp(a, b: Self): int

  ToStringable = concept
    proc `$`(a: Self): string

  Hashable = concept
    proc hash(x: Self): int
    proc `==`(x, y: Self): bool

  Swapable = concept
    proc swap(x, y: var Self)
```

**Концепты-контейнеры.** Есть хотя бы один обобщённый параметр (чаще `T`). Первое синтаксическое использование параметра задаёт, как вывести и связать `T`; остальные использования проверяются на соответствие связанному:

```nim
type
  Indexable[T] = concept # есть T, коллекция
    proc `[]`(a: Self; index: int): var T # описываем, как вывести 'T'
    # а теперь можно использовать 'T', и он обязан совпасть:
    proc `[]=`(a: var Self; index: int; value: T)
    proc len(a: Self): int

  Dictionary[K, V] = concept
    proc `[]`(a: Self; key: K): V
    proc `[]=`(a: var Self; key: K; value: V)
```

Обычный синтаксис «`: ограничение`» добавляет ограничения параметрам: `Dictionary[K: Hashable; V] = concept ...`.

Вывод обобщённого параметра привязан к `Self`: именно `Self` связывает требование с проверяемым типом. Требование может опустить `Self`, но лишь когда каждый названный им параметр уже связан более ранним требованием:

```nim
type
  Findable[T] = concept
    iterator items(x: Self): T   # первое использование связывает `T`
    proc `==`(a, b: T): bool     # `Self` нет, но `T` уже связан
```

Требование, которое не называет `Self` и у которого не все параметры связаны, ничего не говорит о проверяемом типе и никогда не удовлетворяется — иначе кандидат связал бы свободный параметр с любым типом, который он назовёт, и любой тип удовлетворял бы концепту.

### 11.4. Обобщения

Обобщения параметризуют процедуры, итераторы или типы *типовыми параметрами*. Квадратные скобки либо вводят типовые параметры, либо инстанцируют обобщённую сущность. Пример — `find` для любого контейнера, удовлетворяющего `Findable`:

```nim
type
  Findable[T] = concept
    iterator items(x: Self): T
    proc `==`(a, b: T): bool

proc find[T; C: Findable[T]](x: C; elem: T): int =
  var i = 0
  for a in items(x):
    if a == elem: return i
    inc i
  return -1
```

Благодаря ограничению `C: Findable[T]` известно, что элемент `a` имеет тип `T` и `T` поддерживает `==`. На месте вызова `T` выводится из требований концепта: здесь `items` связывает его с типом элементов коллекции.

Концепт можно использовать только как ограничение типового параметра; `proc find[T](x: Findable[T]; elem: T)` не является обобщением по типу коллекции. Использование:

```nim
type
  MyCollection = object
    data: seq[int]

iterator items(x: MyCollection): int =
  for d in x.data: yield d

var myCollection = MyCollection(data: @[1, 2, 3, 4, 5])
echo find(myCollection, 3) # 2
```

Такие обобщения называются «проверяемыми» (checked generics): правила типизации проверяются и в точке определения, и в точке инстанцирования.

**Непроверяемые обобщения** (`{.untyped.}`) проверяются только при инстанцировании:

```nim
proc processUntyped[T](x: T): string {.untyped.} =
  when T is string:
    "String: " & x
  elif T is int:
    "Integer: " & $x
  else:
    "Unknown type: " & $x

echo processUntyped("hello")
```

**Ограничения вывода.** Типы `var T` и `typedesc[T]` нельзя вывести при инстанцировании:

```nim
proc g[T](f: proc(x: T); x: T) =
  f(x)

proc c(y: int) = echo y
proc v(y: var int) =
  y += 100
var i: int

g(c, 42)        # допустимо: T выводится как int
g(v, i)         # недопустимо: T не выводится как `var int`
g[var int](v, i) # тоже недопустимо: явное инстанцирование через `var int`
```

### 11.5. Шаблоны

Шаблон — простая форма макроса: механизм подстановки над абстрактными синтаксическими деревьями Nim. Обрабатывается на семантическом проходе. Вызывается тем же синтаксисом, что и процедура:

```nim
template `!=` (a, b: untyped): untyped =
  # определение есть в модуле system
  not (a == b)

assert(5 != 6) # компилятор переписывает в: assert(not (5 == 6))
```

Операторы `!=`, `>`, `>=`, `in`, `notin`, `isnot` на самом деле шаблоны: `a > b` → `b < a`; `a in b` → `contains(b, a)`; `notin` и `isnot` — очевидные.

«Типы» параметров шаблона — символы `untyped`, `typed`, `typedesc` («метатипы», допустимые только в определённых контекстах). Обычные типы тоже допустимы и означают, что ожидаются `typed`-выражения. Параметр метатипа `typedesc` (без аргумента) принимает любой тип и допустим только для шаблонов и макросов. Подпрограммы называют тип явным обобщённым параметром: `proc f[T](x: typedesc[T])`. Другие «голые» классы типов (`object`, `enum`) не могут быть типами параметров никакой подпрограммы — только ограничениями обобщённых параметров: `proc f[T: object](x: T)`.

**Блок кода в шаблон** передаётся последним аргументом после специального двоеточия:

```nim
template withFile(f, fn, mode, actions: untyped): untyped =
  var f: File
  if open(f, fn, mode):
    try:
      actions
    finally:
      close(f)
  else:
    quit("cannot open: " & fn)

withFile(txt, "ttempl3.txt", fmWrite):  # специальное двоеточие
  txt.writeLine("line 1")
  txt.writeLine("line 2")
```

Два `writeLine` привязываются к параметру `actions`. Параметр, принимающий блок, обычно должен быть `untyped`, потому что поиск символов откладывается до инстанцирования:

```nim
template t(body: typed) =
  proc p = echo "hey"
  block:
    body

t:
  p()  # ошибка: undeclared identifier: p
```

Ошибка из-за того, что тело `p()` типизируется до передачи в `body`, а типизация в Nim подразумевает поиск символов. С `untyped` тело не обязано типизироваться — код компилируется:

```nim
template t(body: untyped) =
  proc p = echo "hey"
  block:
    body

t:
  p()  # компилируется
```

### 11.6. Оператор `typeof`

```nim
var x = 0
var y: typeof(x) # y имеет тип int
```

Если `typeof` определяет тип результата вызова `c(X)`, где `c` — итератор, предпочитается интерпретация-итератор; это меняется вторым аргументом `typeOfProc`:

```nim
iterator split(s: string): string = discard
proc split(s: string): seq[string] = discard

# итератор предпочтителен, тип — `string`:
assert typeof("a b c".split) is string

assert typeof("a b c".split, typeOfProc) is seq[string]
```

### 11.7. Макросы

Макросы — альтернатива плагинам, существующая ради обратной совместимости с Nim 2. Макрос — подпрограмма, которая выполняется на этапе компиляции, получает аргументы как синтаксические деревья `NimNode` из `std/macros` и возвращает дерево, которое компилятор подставляет на место вызова. В отличие от шаблона (чисто лексическая подстановка) тело макроса — обычный код Nimony, который может исследовать, строить и комбинировать деревья.

Внутри каждый макрос компилируется в **отдельный исполняемый файл**, который компилятор запускает на каждом месте вызова. Конвейер тот же, что у плагинов: аргументы сериализуются в NIF, бинарник макроса их обрабатывает, результат разбирается обратно в компиляцию пользователя. Для автора макроса это прозрачно — `macro foo(...) = ...` в основном ведёт себя как в Nim 2 — но объясняет некоторые ограничения (тело макроса не может менять внутреннее состояние компилятора, должно быть самодостаточным и т. д.).

```nim
import std / [syncio, macros]

macro hello(): untyped =
  result = newCall("echo", [newStrLitNode("hello from macro!")])

hello()      # → печатает "hello from macro!"
```

Макрос может объявить тип результата `untyped`, но его переменная `result` в любом случае хранит `NimNode`: `untyped` лишь говорит компилятору не типизировать *выход* макроса до вставки в дерево вызывающего.

**Макросы, вызывающие макросы.** Вложенный вызов раскрывается на семантическом проходе *внешнего* макроса (как в Nim 2): к моменту компиляции бинарника внешнего макроса внутренний вызов уже заменён результатом:

```nim
import std / [syncio, macros]

macro buildLit(): untyped =
  result = newIntLitNode(42)

macro outer(): untyped =
  let x = buildLit()                # `buildLit()` раскрывается в 42 здесь
  result = newIntLitNode(x + 100)

echo outer()    # → 142
```

Действует та же оговорка, что в Nim 2: передача аргумента типа `NimNode` *выражением* (`outerMacro(newStrLitNode("hi"))`) **не** вычисляет `newStrLitNode("hi")` заранее — AST аргумента есть *вызов*, а не получившийся узел `StrLit`.

**Гигиенические ссылки на символы — `bindSym`.** `bindSym(name)` в теле макроса разрешает `name` в области *определения* макроса при компиляции и возвращает `NimNode` вида `nnkSym` (конкретный символ) либо `nnkOpenSymChoice`/`nnkClosedSymChoice` (список кандидатов). Если символ доходит до места вызова пользователя, компилятор считает его уже разрешённым, поэтому затенение имени у вызывающего не может его перенаправить:

```nim
import std / [syncio, macros]

macro nextOf(): untyped =
  let succSym = bindSym("succ")
  result = newCall(succSym, [newIntLitNode(41)])

echo nextOf()   # → 42 (system.succ, независимо от перегрузок у вызывающего)
```

Необязательный второй аргумент `bindSym`:

- `brClosed` (по умолчанию) — единственный символ разрешается в `nnkSym`, несколько — в `nnkClosedSymChoice`. Набор фиксирован в месте определения макроса.
- `brOpen` — та же форма, но при нескольких испускается `nnkOpenSymChoice`: семантика на месте вызова дополняет выбор видимыми там перегрузками.
- `brForceOpen` — всегда `nnkOpenSymChoice`, даже при единственном совпадении, чтобы дополнение на месте вызова происходило всегда.

Первый аргумент `bindSym` обязан быть строковым литералом. В плагинах `bindSym` тоже есть (раздел 13.4).

## 12. Прагмы и feature-флаги

Прагмы дают компилятору дополнительную информацию и команды без множества новых ключевых слов. Обрабатываются на лету при семантической проверке. Заключаются в `{.` и `.}`.

### 12.1. Прагма `feature`

Включает или восстанавливает особенности языка **по модулю**:

```nim
{.feature: "lenientnils".}
```

Слово «feature» намеренно нейтрально: особенность может начать как экспериментальная, стать умолчанием или со временем устареть, а имя прагмы останется прежним. Стадия жизненного цикла описана в документации самой особенности. Features действуют в модуле, где указаны, и **не передаются** импортирующим.

| Feature | Описание |
| --- | --- |
| `"lenientnils"` | `ref`, `ptr`, `pointer`, `cstring` и proc-типы допускают nil по умолчанию, как в Nim 2 (раздел 6.7) |
| `"autoclosures"` | Подпрограмма, вложенная в другую, неявно `.closure.`; захватывающие литералы не требуют аннотации; также анонимные литералы итераторов и тип `iterator(...)` как closure-итератор (8.3) |
| `"canraise"` | Позволяет процедурам без аннотации `raises` поднимать исключения |
| `"lenientconverters"` | Разрешает определять конвертеры для базовых типов вроде `int` (совместимость с Nim 2) |
| `"untyped"` | Шаблоны и обобщённые процедуры по умолчанию `.untyped` (совместимость с Nim 2) |
| `"earlymagics"` | Магические процедуры разрешаются до разрешения перегрузки (совместимость с Nim 2) |
| `"ignoreStyle"` | Правила нечувствительности к стилю Nim 2 |
| `"varToverloads"` | Перегрузка по `var T` (совместимость с Nim 2) |
| `"lenientFloats"` | Неявное сужение вещественных *значений* (именованных констант и выражений, не только литералов) до меньшего float. Выключено по умолчанию — теряется точность |
| `"lenientAliasing"` | Алиасинг вида `f(#[byvar]# x, x)` в вызовах (совместимость с Nim 2) |
| `"runtimeContracts"` | Контракты `.requires` проверяются только во время выполнения; ни одно место вызова в модуле не оценивается статически (8.6) |
| `"staticContracts"` | Каждый `.requires` на месте вызова должен быть *доказан* (8.6) |
| `"anonBlockBreaks"` | Непомеченный `break` покидает внутренний цикл *или* `block`, как в Nim 2 |
| `"assumeSync"` | Отключает проверку разделяемых глобальных переменных в модуле: иначе подпрограмма может обращаться к изменяемой глобальной только через `var`/`ptr`-параметр `.sync`-подпрограммы (атомики, блокировки) либо внутри `{.cast(assumeSync).}:`. Совместимость с Nim 2 |
| `"staticOverloads"` | Если две перегрузки различаются лишь тем, `static[T]` параметр или `T`, для константного аргумента предпочитать `static` вместо ошибки неоднозначности |
| `"ownedRefs"` | Объектные конструкторы дают `owned`: создатель ячейки — её владелец (6.9) |
| `"v2"` | мета-feature: включает все features, помогающие совместимости с Nim 2 |

**Пример (авторский): порт модуля Nim 2.**

```nim
# в начале старого модуля — всё, что нужно для «старого» поведения:
{.feature: "v2".}
# новый код постепенно переводите на явные `nil T`, `.closure.` и т. д.,
# убирая отдельные features по одной
```

### 12.2. Прагма `noreturn`

Помечает процедуру, которая никогда не возвращается.

### 12.3. Прагмы `intdefine`, `booldefine`, `strdefine`

Позволяют переопределить инициализатор константы из командной строки — так конфигурируют сборку, не правя исходник:

```nim
const
  bufSize {.intdefine.}: int = 4096
  verbose {.booldefine.} = false
  banner {.strdefine.} = "nimony"
```

`-d:bufSize=8192` (то же, что `--define:bufSize:8192`) скомпилирует `bufSize` как `8192`. Ключ, не заданный в командной строке, оставляет написанное значение, так что объявление остаётся собственной документацией. Ключ — имя константы; строковый литерал в аргументе называет другой ключ (так достигаются ключи с точками):

```nim
const chunk {.intdefine: "mylib.chunkSize".}: int = 256
```

Для `booldefine` голый `-d:key` означает `true`; допустимы `true`/`false`, `on`/`off`, `1`/`0`. `strdefine` принимает текст как есть. `intdefine` разбирает десятичное целое (возможны знак и разделители `_`), а результат проверяется на соответствие объявленному типу константы, как написанный литерал, — поэтому `-d:key=1000` в `int8` — ошибка, а не тихое усечение. `-d:key=value` также делает `defined(key)` истинным, как в Nim.

### 12.4. Прагмы `final`, `error`, `nodecl`, `header`

- **`final`** — тип объекта нельзя наследовать. Наследование доступно только для объектов, унаследованных от существующего (`object of SuperType`) или помеченных `inheritable`.
- **`error`** — *использование* символа (итератора, процедуры) вызывает статическую ошибку; особенно полезно, чтобы исключить копирование: ` proc  `=copy`(dest: var MyType, source: MyType) {.error.}`.
- **`nodecl`** — применимо почти к любому символу; полезно для совместимости с C:

```nim
var
  EACCES {.importc, nodecl.}: cint # притвориться переменной: Nim не знает её значение
```

- **`header`** — как `nodecl`, но в сгенерированный код добавляется `#include`:

```nim
type
  PFile {.importc: "FILE*", header: "<stdio.h>".} = ptr object
    # импорт C-типа FILE*; Nim воспримет его как новый указательный тип
```

Аргумент `header` — строковая константа с именем заголовка. Как обычно в C, системный заголовок берётся в угловые скобки `<>`; без скобок Nim заключит имя в `""` в сгенерированном C.

### 12.5. Прагмы `bycopy`, `byref`, `varargs`, `threadvar`

`bycopy` — к объекту или параметру: передавать тип по значению. `byref` — по ссылке (скрытый указатель); для параметра имеет приоритет, даже если тип помечен `bycopy`. Обычно компилятор сам решает по размеру типа; прагмы нужны при взаимодействии с C. Для `importc`-типов с `byref` такие параметры превращаются в указатели.

```nim
type
  Vector {.bycopy.} = object
    x, y, z: float
```

`varargs` применима к процедурам, процедурным типам и шаблонам (см. 5.12).

`threadvar` делает переменную thread-local; из-за ограничений реализации инициализировать её в секции `var` нельзя (каждая thread-local копируется при создании потока):

```nim
var checkpoints* {.threadvar.}: seq[string]
```

### 12.6. Прагмы `compile`, `link`

`compile` компилирует чужой C-, C++- или Objective-C-файл C-компилятором и линкует объектный файл в программу. Три формы, как в Nim 2:

```nim
{.compile: "logic.c".}
{.compile("fast.c", "-O3 -DUSE_SIMD").}   # дополнительные флаги для этого файла
{.compile: ("cfiles/*.c", "$1.o").}        # все подходящие файлы
```

Пути отсчитываются от файла с прагмой; `${path}` раскрывается в каталог файла. Язык определяется по расширению (`.cpp`, `.cc`, `.cxx`, `.c++` — C++; `.m` — Objective-C; `.mm` — Objective-C++; остальное — C). Исходник компилируется тем же компилятором и с теми же целевыми флагами, что и сгенерированный код, плюс `passC` и собственные флаги файла. В форме кортежа первая строка — шаблон, и только её имя файла может содержать `*` и `?`; если файлов нет — ошибка; `$1` во второй строке заменяется именем каждого совпадения (`util.c`) и называет его объект. Все аргументы — константные строковые выражения, поэтому пути и флаги можно вычислять при компиляции:

```nim
const simd = when defined(amd64): "-mavx2" else: ""
{.compile("fast.c", "-O3 " & simd).}
```

`passC` и `passL` принимают константные выражения так же. Объекты кэшируются между проектами; имя объекта включает хэш пути исходника, флагов файла и полной командной строки компилятора, поэтому два `util.c` в разных каталогах или один файл с разными флагами никогда не делят объект. Заголовки, которые включает исходник, **не отслеживаются**: правка одного заголовка не пересобирает файл.

`link` линкует готовый объектный файл или статическую библиотеку:

```nim
{.link: "vendor/fast.o".}
{.link: "vendor/libfast.a".}
```

Путь — от файла с прагмой; `.o` добавляется, если у имени нет расширения; отсутствие файла — ошибка. Линкуемые файлы идут после всех прочих объектов, так что статическая библиотека разрешает символы из любых из них. Файл, подключённый несколькими модулями, линкуется один раз; замена файла перелинковывает программу. Для линковки по имени (`-lfoo`) используйте `passL`.

С нативным бэкендом (`nimony n`) программа с `compile` или `link` завершается системным линкером вместе с libc. На Linux это запрашивается `-d:useLibc`: без него `nimony n` строит автономный исполняемый файл без libc, не способный подключить чужой объект, и сообщает об этом (см. 2.5).

### 12.7. Прагмы `build` и `bundle`

`build` — **не** способ компилировать чужие исходники (это `compile`), а механизм для генераторов кода, потребляющих собственное IR Nimony. Она направляет сгенерированное промежуточное представление модуля через *пользовательский бэкенд* — внешний инструмент, превращающий IR в специфичный артефакт (например, бинарник GPU-ядра):

```nim
{.build("nimony c", "deps/mybackend.nim").}
```

От двух до четырёх строковых аргументов:

1. **builder** — команда сборки инструмента из исходника (`"nim c"`, `"nimony c"`). Это обычная командная строка: первый токен — компилятор (ищется как любой инструмент: имя в `bin/` Nimony, иначе в `PATH`), остальное передаётся как есть (`"nimony c --path:../lib"` допустимо). `"nim c"` — для инструмента, зависящего от Nim 2, `"nimony c"` — для самохостного; перенос — замена одной строки. Builder должен принимать `-o:<path>`.
2. **tool** — путь к исходнику инструмента относительно файла с прагмой (как у `.plugin`).
3. Необязательная строка дополнительных **аргументов**, передаваемых при каждом вызове инструмента.
4. Необязательная строка **флагов линковки** на файл. В отличие от глобальной `.passL`, они относятся именно к этому модулю: прикрепляются к объекту модуля в манифесте линковки (например, `"-lvulkan"` для GPU-модуля). Сам шаг линковки не меняют — это дело прагмы `.bundle`.

`bundle` **заменяет финальный шаг линковки** пользовательским драйвером. Если *любой* модуль проекта задаёт `.bundle`, запускается этот инструмент вместо встроенного линкера, и ему передаётся *манифест* всего проекта: тип приложения (`console`/`gui`/`lib`/`staticlib`), все объектные файлы и маршрутизированные артефакты бэкенда (с видом и флагами на файл), глобальные флаги линковки. Драйвер сам решает, что слинковать, упаковать или игнорировать (например, слинковать объекты и встроить или отбросить артефакты `.spv`). Без `.bundle` встроенный шаг не меняется. Первый `.bundle` в проекте побеждает:

```nim
{.bundle("nimony c", "deps/mylinker.nim").}
```

Аргументы: **builder**, **tool** (исходник драйвера) и необязательные **аргументы** — разрешаются так же, как у `.build`.

Бэкенд-инструмент **не плагин**. Плагин работает внутри компилятора при семантическом анализе и переписывает синтаксическое дерево; бэкенд-инструмент — отдельная программа, запускаемая *после* генерации кода: читает IR модуля и пишет артефакт. Он *собирается* как плагин (по требованию), но *планируется* как инструмент: становится узлом графа сборки, поэтому пересобирается только при изменении входов и работает параллельно с остальной сборкой. Если исполняемый файл с именем инструмента уже есть в `bin/` Nimony (или это известный системный инструмент), он используется напрямую; иначе исходник компилируется по требованию. Прагма `build` — оператор уровня модуля: действует на весь модуль, каждый вызов инструмента получает IR модуля на вход и целевой артефакт на выход.

## 13. Плагины

Плагины — механизм метапрограммирования Nimony, заменяющий систему макросов Nim 2. Плагин — **отдельная программа на Nim**, которая на этапе компиляции преобразует деревья NIF. Плагины выполняются как внешние процессы и общаются с компилятором через NIF-файлы.

### 13.1. Виды плагинов

| Вид | Объявление | Область |
| --- | --- | --- |
| **Шаблонный** | `template foo(...) {.plugin: "path".}` | Вызывается на каждом месте вызова |
| **Цикловой (for-loop)** | `iterator foo(...) {.plugin: "path".}` | Переписывает цикл `for`, использующий итератор |
| **Модульный** | `{.plugin: "path".}` как оператор | Преобразует весь модуль |
| **Типовой** | `type T {.plugin: "path".} = ...` | Вызывается для каждого модуля, использующего `T` |
| **Импортный** | `import (path/foo) {.plugin: "v2".}` | Импортирует модуль `path/foo` **из плагина** `v2` |

Первые четыре используют один API (`plugins`) и модель выполнения. Импортные плагины отличаются (13.11).

### 13.2. Быстрый старт

Плагин заменяет шаблон без тела. Вместо

```nim
template generateEcho(s: string) = echo s
```

пишете:

```nim
# mymodule.nim
import std / syncio

template generateEcho(s: string) {.plugin: "deps/mplugin1".}

generateEcho("Hello, world!")  # печатает: Hello, world!
```

А в `deps/mplugin1.nim`:

```nim
import plugins

proc transform(n: NifCursor): NifBuilder =
  result = createTree()
  let info = n.info
  var arg = callArgs(n)
  result.withTree StmtsS, info:
    result.withTree CallS, info:
      result.addIdent "echo"
      result.takeTree arg

var inp = loadPluginInput()
saveTree transform(inp)
```

Плагин читает аргументы шаблона как дерево NIF из `paramStr(1)`, преобразует их и пишет результат в `paramStr(2)`.

**Пояснение (как мыслить плагином).** Шаблон подставляет текст; плагин получает *дерево* и обязан вернуть *дерево*. «Поток токенов» из раздела 3 здесь виден напрямую: вы идёте курсором вперёд (`inc`, `skip`, `takeTree`) и пишете выход билдером.

### 13.3. Классы тегов NIF

NIF идентифицирует каждый составной узел текстовым тегом (`call`, `proc`, `object`...). Для диспетчеризации плагины используют один из пяти enum-классов, делящих теги по синтаксической роли:

| Enum | Суффикс | Страж | Роль |
| --- | --- | --- | --- |
| `NimonyStmt` | `S` | `NoStmt` | Операторы (`CallS`, `VarS`, `ProcS`, `StmtsS`, `BlockS`...) |
| `NimonyExpr` | `X` | `NoExpr` | Выражения (`CallX`, `DotX`, `AddX`, `TrueX`, `NilX`...) |
| `NimonyType` | `T` | `NoType` | Типы (`ObjectT`, `ArrayT`, `IntT`, `RefT`...) |
| `NimonyPragma` | `P` | `NoPragma` | Прагмы (`InlineP`, `MagicP`, `PluginP`...) |
| `NimonyOther` | `U` | `NoSub` | Подструктуры (`ParamU`, `FldU`, `ElifU`, `OfU`, `StmtsU`, `PragmasU`...) |

Все пять enum делят одно пространство порядковых номеров (ordinal равен `TagId`), поэтому диспетчеризация — сравнение целых за O(1), а enum тривиально преобразуются в `TagId`. Полный список тегов — в разделе 18.2.

**Запрос о текущем узле.** У `NifCursor` для каждого класса есть метод: `n.stmtKind`, `n.exprKind`, `n.typeKind`, `n.pragmaKind`, `n.otherKind`; если текущий токен не из этого класса, возвращается страж:

```nim
case n.stmtKind
of CallS:
  # обработать вызов-оператор
of VarS, LetS:
  # обработать объявление переменной
of NoStmt:
  # не оператор — попробовать другой класс или пропустить токен насквозь
  result.takeTree n
else:
  result.takeTree n
```

**Один текст, разные классы.** Ряд тегов встречается в нескольких классах: `nil` — `NilX` как выражение и `NilU` как аннотация на типе указателя; `kv` — `KvX` как выражение «ключ-значение» и `KvU` как структурное поле; `and`, `or`, `not` — `NimonyExpr` в выражениях и `NimonyType` в ограничениях концептов. Чтобы различить, диспетчеризуйте сначала по родительскому контексту, затем вызывайте нужный метод.

**Построение.** `withTree` принимает любой из пяти enum прямо; опечатка — ошибка компиляции плагина, а не искажённое дерево во время выполнения:

```nim
result.withTree StmtsS, info:                 # NimonyStmt
  result.withTree CallX, info:                # NimonyExpr
    result.addIdent "echo"
    result.addStrLit "hello"
```

### 13.4. Как плагины компилируются и запускаются

1. Парсер (nifler) перечисляет все прагмы `.plugin` в deps-файле модуля, а сканер зависимостей разрешает путь относительно исходника со строковым литералом прагмы.
2. Плагин компилируется Nimony как узел графа сборки: nifmake собирает исполняемый файл ровно один раз, до всех компиляций модулей, которые могут его запускать, и пересобирает их при изменении исходника плагина. Файл кэшируется в nimcache. Если плагин дошёл до компилятора без узла в графе, он собирается по требованию — этот путь ничего не разделяет между процессами, так что параллельные компиляции безопасны.
3. На месте вызова компилятор записывает входное AST в `.nif` и запускает плагин подпроцессом.
4. Плагин читает вход, преобразует, пишет выход и завершается.
5. Компилятор читает выходной NIF и вставляет в AST.

Плагины **детерминированы**: тот же вход даёт тот же выход. Компилятор кэширует результаты; ключ кэша — входное дерево, поэтому плагин, читающий не упомянутый во входе файл, должен сообщить об этом через `dependsOn` (13.8). Входные файлы пишутся в *двоичной* форме NIF (bif); имена сохраняют `.nif`, а API определяет формат по заголовку, так что текстовый NIF тоже принимается. Посмотреть кэшированный вход: `tools/niftools bif2nif <file>`.

**Поиск плагина.** Путь в `.plugin: "path"` отсчитывается от каталога исходника со строковым литералом, а не от места вызова. Это важно, если прагма внутри импортируемого шаблона:

```nim
# /dirA/a.nim
template foo =
  {.plugin: "myplugin".}

# /dirB/b.nim
import ../dirA/a
foo()
```

Компилятор ищет `myplugin.nim` в `/dirA/` (и в путях стандартной библиотеки).

### 13.5. Шаблонные плагины

Вызывается при каждом вызове шаблона и получает только код, относящийся к вызову. Вход обёрнут в узел `StmtsS` с именем шаблона и аргументами. `callArgs` даёт ограниченный курсор по аргументам:

```nim
let input = loadPluginInput()
var args = callArgs(input)
# args указывает на первый аргумент
```

Можно принять и блок кода через `typed`-параметры; плагин получает весь блок как типизированный, проверенный NIF:

```nim
template renderTree(s: typed) {.plugin: "deps/mrender".}

renderTree:
  let x = 1
  echo x
```

**Осмотр типов: `needTypes`.** Аргументы-типы доходят до плагина проверенными, но развёрнуты лишь *структурные* типы:

| вызов | что видит плагин |
| --- | --- |
| `f(array[3, int])` | `(array (i 64) (rangetype (i 64) 0 2))` |
| `f(ptr int)` | `(ptr (i 64) (notnil))` |
| `f(tuple[a: int])` | `(tuple (kv a (i 64)))` |
| `f(Foo[int])` | `Foo.0.Iw3zqsv.mymod` |
| `f(MyDistinct)` | `MyDistinct.0.mymod` |

Номинальный тип (объект, enum, distinct, обобщённый экземпляр) — голый `Symbol`, и плагин не может его разрешить: он работает в своём процессе, а нужный модуль ещё проверяется. Поэтому плагин **спрашивает**: вернув `needTypes(syms)` как весь выход, он заставляет компилятор дописать эти объявления ко второму входу и запустить плагин снова:

```nim
var defs = loadTypeDefinitions()   # (stmts (type :Sym … )*), сначала пусто
...
if missing.len > 0:
  return needTypes(missing)
```

Ничего не отправляется без запроса. Запрашивайте целый уровень одним запросом — раунд стоит перезапуска. Обмен безопасен: повторный запрос уже выданного объявления — ошибка компиляции (цикл конечен по построению); символ, оказавшийся *типовой переменной*, получает ответ `(typevar …)`, а не молчание. Слот `<typevars>` обобщённого экземпляра содержит `(at <head> <args>...)`, откуда прямо получаются `genericHead` и `genericParams`. `lib/std/typetraits.nim` реализован так, без магии компилятора; плагин — `lib/std/deps/typetraits.nim`.

**Типы на входе и на выходе.** Шаблонный плагин, объявленный возвращающим `typedesc`, может стоять в позиции типа, и его выход перепроверяется как тип:

```nim
type Q = distinctBase(MyOtherInt)
var y: genericHead(Foo[int])[float]
```

Внутри обобщённого тела плагин выполняется **один раз**, с *типовой переменной* в качестве аргумента, а не на каждое инстанцирование; его выход затем участвует в обычной подстановке (`pointerBase(ptr T)` → `T`). Плагин, которому нужно *решение* по конкретному типу, возвращает `deferExpansion()` как весь выход:

```nim
if mentionsTypevar(defs, arg):
  return deferExpansion()
```

Компилятор оставляет вызов как `(at <template> <args>…)`; инстанцирование подставляет и перепроверяет, спрашивая плагин уже с конкретными типами:

```nim
proc unwrap[T](x: T): distinctBase(T) =
  result = distinctBase(T)(x)

echo unwrap(MyInt(12))      # плагин спрошен с MyInt  -> int
echo unwrap(MyFloat(2.5))   # ... и с MyFloat           -> float
```

Отсрочка — жёсткая ошибка, если ни один аргумент не содержит обобщённого параметра (иначе плагина спрашивали бы вечно). Пока отложенный тип не разрешён, он так же применим, как голая типовая переменная: его можно объявить, передать, преобразовать и вернуть, но `echo` значения такого типа и доступ к полю в обобщённом теле не работают.

### 13.6. Модульные плагины

Получает **весь модуль** после семантического анализа и обязан вернуть полный модуль с преобразованиями:

```nim
{.plugin: "deps/mmoduleplugin".}

echo "this should not be erased"

block:
  echo "should be erased"
```

Например, убрать все `block` верхнего уровня:

```nim
import plugins

proc transform(n: NifCursor): NifBuilder =
  result = createTree()
  let info = n.info
  var body = firstChild(n)
  result.withTree StmtsS, info:
    while body.hasMore:
      if body.kind == TagLit and body.stmtKind == BlockS:
        skip body  # убрать
      else:
        result.takeTree body

var inp = loadPluginInput()
saveTree transform(inp)
```

Плагин можно скрыть внутри импортируемого модуля:

```nim
# deps/mhiddenplugin.nim
template eraseToplevelBlocks* =
  {.plugin: "mmoduleplugin".}

# user.nim
import deps/mhiddenplugin
eraseToplevelBlocks()  # раскрывается в {.plugin: "mmoduleplugin".} и вызывает плагин
```

### 13.7. Типовые плагины

Привязан к номинальному типу и вызывается для **каждого модуля**, использующего тип — аналог term rewriting macros Nim 2. Получает два входа: `loadPluginInput()` (AST модуля) и `loadTypeDefinitions()` (определения типов, вызвавшие плагин):

```nim
# listener.nim
type
  Listener* {.plugin: "mtypeplugin".} = object
    i*: int
    s*: string

# user.nim
import listener

template onChanged(x: var Listener, field: untyped, name: string): untyped =
  echo name, " changed to ", field

var p = Listener(i: 1, s: "a")
p.i = 2   # печатает: i changed to 2
p.s = "b" # печатает: s changed to b
```

Плагин перехватывает присваивания полям `Listener` и вставляет вызовы шаблона `onChanged`. Другое применение — оптимизация шаблонов выражений: тип `Matrix` с плагином `avoidtemps` переписывает `a*b + c - d` в операции на месте без временных матриц:

```nim
type
  Matrix {.plugin: "avoidtemps".} = object
    a: array[4, array[4, float]]

let e = a*b + c - d
# переписывается в:
var e = a
e *= b
e += c
e -= d
```

### 13.8. API плагинов (`import plugins`)

**Чтение входа.** `proc loadPluginInput*(filename = paramStr(1)): NifCursor` возвращает курсор в корне дерева NIF. Типовые плагины используют `loadPluginInput()` для модуля и `loadTypeDefinitions()` для определений.

**`NifCursor`** — подсчитываемый по ссылкам курсор только для чтения по замороженному дереву NIF; движется только вперёд. Дочерние курсоры ограничены счётчиками переходов `nifcore`; значения «закрывающий токен» нет. Все входы и билдеры в одном процессе плагина делят предзаполненный пул литералов и тегов, поэтому `SymId` напрямую сравнимы между основным входом, входом определений типов и сгенерированными билдерами, а ординалы enum Nimony отображаются прямо в `TagId`. `SymId` и `TagId` — локальные числовые дескрипторы пула; для текстовых имён используйте `symText` и `tagText` (`$id` намеренно не поиск текста).

| Процедура | Результат / смысл |
| --- | --- |
| `inc(n)` | сдвинуться на один токен |
| `skip(n)` | пропустить токен или всё поддерево |
| `kind(n)` | `NifKind`: `TagLit`, `Symbol`, `Ident`, `StrLit`, `IntLit`... |
| `info(n)` | `LineInfo` — положение в исходнике |
| `stmtKind`, `exprKind`, `typeKind`, `otherKind`, `pragmaKind` | вид узла в соответствующем классе или страж |
| `tagId(n)`, `tagText(n)` | сырой `TagId` / имя тега |
| `symId(n)`, `symText(n)`, `identText(n)` | дескриптор / текст символа / текст идентификатора |
| `stringValue(n)`, `intValue(n)`, `uintValue(n)`, `floatValue(n)`, `charLit(n)` | значения литералов |
| `eqIdent(n, name)` | совпадает ли токен с `name` (идентификаторы и символы) |
| `isValid(info)`, `filePath(info)`, `lineCol(info)` | настоящее ли положение; путь файла; `SourcePos(line, col)` с 1 |

**`NifBuilder`** — move-only синоним `nifcore.TokenBuf`; копировать нельзя. `snapshot(tree)` даёт подсчитываемый курсор; изменение билдера после снимка прозрачно отделяет хранилище токенов.

| Процедура | Описание |
| --- | --- |
| `createTree()`, `snapshot(tree)`, `isEmpty(tree)` | пустое дерево; курсор только для чтения; пусто ли |
| `openTree(t, tag, info)` / `closeTree(t)` | начать / закрыть помеченное дерево (тег enum или строка) |
| `addIdent`, `addSymDef`, `addSymUse`, `genSym()` | идентификатор; определение / ссылка на символ; свежий локальный `SymId` |
| `addStrLit`, `addIntLit`, `addUIntLit`, `addFloatLit`, `addCharLit` | литералы |
| `addDotToken`, `addEmptyNode` | токен-точка; пустой заполнитель |
| `takeTree(t, n)` | скопировать текущее поддерево `n` в `t`, продвинув `n` |
| `addSubtree(t, n)` | то же без продвижения |
| `addTree(t, child)` | добавить целый дочерний билдер, не потребляя его |

`genSym()` использует стандартную подсказку NIF `.unusedname` входного файла:

```nim
let temp = genSym()
result.withTree LetS, info:
  result.addSymDef temp, info
  result.addEmptyNode3(info)
  result.takeTree value
result.withTree CallS, info:
  result.addIdent "echo"
  result.addSymUse temp, info
```

**Запись выхода:**

```nim
proc saveTree*(tree: sink NifBuilder)                  # пишет в paramStr(2)
proc saveTree*(tree: sink NifBuilder; filename: string)
proc renderTree*(tree: var NifBuilder): string         # отладочное представление (без line info)
```

**Чтение файлов (`dependsOn`).** Выход плагина кэшируется по контрольной сумме его *входного дерева*, поэтому плагин, читающий что-то ещё (схему, шаблон, таблицу констант), иначе запомнился бы навсегда. `dependsOn` сообщает о чтении, и компилятор перезапустит плагин (и перепроверит модуль) при изменении файла:

```nim
proc dependsOn*(path: string)

proc tr(n: NifCursor): NifBuilder =
  let schema = getCurrentDir() / "schema.json"
  dependsOn schema
  ...
```

Вызывайте для каждого открываемого файла. Пути делаются абсолютными относительно рабочего каталога плагина (это рабочий каталог компилятора). Ограничения: записывается только существующий путь, поэтому *создание* файла, который плагин искал и не нашёл, ничего не инвалидирует (удаление записанного — пересборка); имя **каталога** отслеживает лишь добавление/удаление его прямых записей — для содержимого называйте каждый файл. Внутри пути возвращаются ведущим деревом `(dependency …)` рядом с подсказкой gensym; компилятор снимает оба до включения в модуль и записывает список в `.s.deps.nif` модуля.

**Сообщения об ошибках.**

```nim
proc errorTree*(msg: string): NifBuilder
proc errorTree*(msg: string; info: LineInfo): NifBuilder
proc errorTree*(msg: string; at: NifCursor): NifBuilder
proc errorTree*(msg: string; at, orig: NifCursor): NifBuilder
```

Возвращают узел `ErrT`, который компилятор сообщит как ошибку компиляции. `info` даёт только положение; `at` — положение и встроенный исходный контекст; `orig` позволяет различать положение диагностики и контекст.

**Разбор Nim-кода: `nimparser`.** Если проще написать Nim, чем строить дерево, текст можно разобрать. `nimparser` — отдельный модуль рядом с `plugins`, чтобы лишь импортирующие его плагины тянули парсер Nim:

```nim
import plugins, nimparser

proc tr(n: NifCursor): NifBuilder =
  var code = parseStmt("echo " & $2 & " * 21", n.info)
  result = createTree()
  result.takeTree code

proc parseStmt*(code: string; info = NoLineInfo): NifCursor
proc parseExpr*(code: string; info = NoLineInfo): NifCursor
```

`parseStmt` возвращает курсор на `(stmts ...)`; `parseExpr` — ровно на одно выражение, остальное отвергает. Дерево — то, что парсер пишет для `.nim`-файла, его можно вставить в выход как есть; каждый узел позиционирован в `info`. Синтаксическая ошибка возвращается деревом ошибки в `info`. `std/macros` предлагает те же две процедуры, возвращающие `NimNode`.

**Валидация.** Компилятор проверяет код плагина; недопустимый — отвергается. Детали пока в разработке и намеренно не документированы.

### 13.9. Типичная структура плагина

**Replacer API (рекомендуется).** Тип `Replacer` связывает входной курсор и выходной билдер в один объект со сбалансированными операциями: каждая операция потребляет вход и порождает выход атомарно, так что рассогласование курсора и билдера невозможно:

```nim
import plugins

proc trAux(r: var Replacer) =
  if r.isAtom:
    keep r, Any             # листовые токены проходят насквозь
  else:
    case r.stmtKind
    of SomeStmtToTransform:
      # ... своё преобразование ...
    else:
      loopKeepTag r:       # спуститься и рекурсировать
        trAux r

var r = loadReplacer()
loopKeepTag r:             # войти в верхний (stmts ...) и рекурсировать
  trAux r
saveReplacer(r)
```

Основные операции:

- `keep r, Kind` — скопировать одного потомка как есть, проверив вид;
- `drop r, Kind` — пропустить потомка без вывода, проверив вид;
- `replace r, Kind, node` — пропустить потомка вида `Kind`, вывести замену (`NifCursor` или одолженный `NifBuilder`);
- `keepTag r:` — спуститься в составной узел (копировать тег, обработать потомков, закрыть);
- `loopKeepTag r:` — копировать тег, обойти всех потомков, закрыть;
- `peek r:` — анализ с заглядыванием без потребления (курсор восстанавливается);
- `getCursor(r)` / `setCursor(r, c)` — снимок/восстановление курсора для анализа.

Аннотации вида обязательны: `keep r, Expr`, `drop r, Type`, `keep r, AsgnS`. `Any` — когда потомок может быть чем угодно; конкретные теги (`AsgnS`, `MutT`) — когда грамматика фиксирует потомка. `r.dest` даёт прямой доступ к билдеру:

```nim
r.dest.withTree CallS, info:
  r.dest.addSymUse sym, info
  r.dest.addStrLit "hello"
```

**Низкоуровневый API.** `NifCursor` и `NifBuilder` остаются для плагинов, строящих выход с нуля:

```nim
import plugins

proc transform(n: NifCursor): NifBuilder =
  result = createTree()
  var n = n
  if n.stmtKind == StmtsS:
    n = firstChild(n)
  result.withTree StmtsS, n.info:
    while n.hasMore:
      result.takeTree n

var inp = loadPluginInput()
saveTree transform(inp)
```

Ключевые операции: `takeTree` — провести узлы без изменений; `skip` — удалить узлы; `withTree` или `openTree`/`closeTree` — построить новые; `addSubtree` — продублировать узлы.

**Шаблоны обхода и преобразования.** `into`/`loopInto` — для чистого анализа; `keepTag`/`loopKeepTag` копируют тег узла в выход:

| Шаблон | Тип | Назначение |
| --- | --- | --- |
| `hasMore(n)` | `NifCursor` | истинно, пока в ограниченном курсоре есть значения |
| `into n:` | `NifCursor` | войти в `TagLit`, выполнить тело для потомков, выйти |
| `loopInto n:` | `NifCursor` | войти в узел, обойти всех потомков, выйти |
| `linearScan n:` | `NifCursor` | просканировать составные узлы-потомки, затем пройти поддерево |
| `keepTag r:` | `Replacer` | копировать тег в выход, выполнить тело, закрыть дерево и продвинуться |
| `loopKeepTag r:` | `Replacer` | копировать тег, обойти всех потомков, закрыть дерево и продвинуться |

### 13.10. `bindSym` в плагинах

Плагины могут использовать `bindSym` для гигиенических ссылок на символы, как макрос. Вариант плагина принимает билдер первым аргументом и добавляет символы прямо в него: `proc bindSym(t: var NifBuilder; name: string; rule = brClosed)`.

```nim
import std / syncio          # делает `echo` видимым в месте определения плагина
import plugins

proc tr(n: NifCursor): NifBuilder =
  result = createTree()
  let info = n.info
  result.withTree StmtsS, info:
    result.withTree CallS, info:
      result.bindSym "echo"               # гигиенично; обходит `echo` вызывающего
      result.takeTree firstChild(n)

var inp = loadPluginInput()
saveTree tr(inp)
```

`bindSym` здесь — магия времени семантики: когда Nimony компилирует исходник плагина, он разрешает литерал `"echo"` в области определения модуля плагина и испускает либо один атом Symbol, либо поддерево `(cchoice …)`/`(ochoice …)`. Когда компилятор пользователя читает выход, Symbol обходит поиск в области вызывающего, поэтому `proc echo(x: string) = discard` у вызывающего не перенаправит ссылку плагина. Второй аргумент — правило `brClosed` / `brOpen` / `brForceOpen` (см. 11.7).

### 13.11. Импортные плагины

`import` можно сочетать с прагмой плагина, чтобы загрузить модуль, NIF которого выдан плагином:

```nim
import (path/foo) {.plugin: "v2".}
```

Используется для слоёв совместимости, переводящих между разными форматами NIF; позволяет импортировать код на чужом языке. Эти плагины не следуют правилам выше: строка — **не** путь к `.nim`-файлу и компилятор её не собирает. Она называет уже собранный исполняемый файл, ищется сначала относительно текущего каталога, затем в каталоге `bin` инструментария. Плагин запускается как `<plugin> <path/foo.nim> <nimcache/<plugin>/<module>.s.nif>` и сам обязан заполнить `nimcache/<plugin>` проверенным NIF **и** индексными файлами. Плагин получает не код Nim, а только путь `path/foo`. Плагин `v2` (`src/v2`) — пример в дереве; он обращается к компилятору Nim 2 для перевода модулей Nim 2. Собирается `nim c src/v2/v2.nim`.

## 14. Passive-процедуры (CPS)

Passive-процедуры — механизм Nimony для структурной конкурентности и асинхронного ввода-вывода **без** колбэков, future и «цветных» функций. Процедура с аннотацией `.passive` преобразуется компилятором в конечный автомат через CPS (Continuation Passing Style) в проходе Hexer (`src/hexer/cps.nim`). Тот же проход обслуживает итераторы.

**Пояснение (суть в трёх фразах).** Passive-процедура может «встать на паузу» и быть продолжена позже. Вызов passive-процедуры из обычного кода по умолчанию выполняется до конца (трамплин крутит продолжения, пока они не закончатся), поэтому снаружи вызов синхронен. Планировщик можно заменить и получить миллионы лёгких кооперативных потоков (пикопотоков).

### 14.1. Основные типы

```nim
type
  ContinuationProc* = proc (coro: ptr CoroutineBase): Continuation {.nimcall.}
  Continuation* = object
    fn*: ContinuationProc
    env*: ptr CoroutineBase
  CoroutineBase* = object of RootObj
    caller*: Continuation
```

`Continuation` — пара (указатель на функцию, указатель на окружение). Когда `fn` равен `nil`, сопрограмма закончена. Поле `caller` связывает с вызывающей сопрограммой, чтобы по завершении passive-процедуры выполнение вернулось к вызывающему.

Не все продолжения свободно перемещаются между потоками. Продолжения от `delay(call)` могут планироваться на другом потоке при условии проверки «отправляемости» (sendability) захваченного окружения. Продолжения от `delay()` захватывают продолжение кода после ближайшего `suspend()` и **привязаны к потоку**: они должны возобновляться на том же потоке.

**`delay(call)` и параметры, ссылающиеся на вызывающего.** Продолжением, которое создаёт `delay(call)`, владеет планировщик, а не код, который его построил, поэтому параметры вызываемой не должны быть алиасами фрейма-строителя. Параметры `var`, `out`, `lent` — как раз такие: фрейм сопрограммы хранит их как голый указатель в вызывающего. В форме «spawn»

```nim
submit(delay(handle(c)), -1)     # `handle` выполнится позже, возможно на другом потоке
```

вызывающий давно ушёл дальше (переприсвоил `c` или вернулся и выполнил деструкторы) до того, как цепочка его прочитает. Сбой — чтение освобождённой памяти, поэтому `delay` отвергает такую вызываемую сразу:

```
Error: `delay` hands `handle` to a scheduler, so its continuation can outlive this
frame; parameter `c: var HttpConnection` would alias a location that is already gone.
Take it as `sink` instead
```

Ответ — `sink`: он переносит владение во фрейм сопрограммы, что делает его время жизни самодостаточным. Правило специфично для `delay`: обычный passive-вызов приостанавливает вызывающего, чей фрейм жив всё время жизни вызываемого, так что `var`-параметры там допустимы.

### 14.2. Как писать

Passive-процедура выглядит как обычный последовательный код:

```nim
proc myecho(x: string) {.passive.} =
  echo x

proc greet(name: string) {.passive.} =
  for i in 0..<3:
    myecho "hello " & name
```

Вызов одной passive-процедуры из другой — точка приостановки: компилятор делит вызывающего на состояния вокруг каждого такого вызова. Программисту об этом думать не нужно.

### 14.3. Конвейер компиляции

1. **NJ (граф потока управления):** тело процедуры понижается до IR NJ со структурированным потоком управления (`loop`, `ite`, охранные флаги `mflag`/`vflag`).
2. **CPS-преобразование** (`src/hexer/cps.nim`): граф NJ делится в точках приостановки (вызовы других passive-процедур) на функции-состояния. Локальные переменные поднимаются в размещённый в куче объект окружения сопрограммы.

### 14.4. Входная функция и функции состояний

Для passive-процедуры `foo(x: int)` компилятор порождает:

- тип сопрограммы `FooCoroutine = object of CoroutineBase` с поднятыми локальными;
- **функцию-обёртку** `foo_init`, которая выделяет фрейм через `allocFrame` и делегирует входной функции; сигнатура `foo_init(x: int, result: ptr int, caller: Continuation)`. Обёртка важна для вызовов методов, где конкретный тип неизвестен при компиляции;
- **входную функцию** `foo`, которая принимает заранее выделенный фрейм, инициализирует окружение (`this[] = FooCoroutine(...)`) и выполняет первое состояние;
- функции состояний `s0`, `s1`, ..., каждая из которых выполняет код до следующей точки приостановки и возвращает `Continuation` на следующее состояние (или на `caller`, когда закончено).

### 14.5. Трамплин

Запуск passive-процедуры — простой цикл:

```nim
var c = c
while not stopping(c):
  c = scheduler(c)
```

Каждый вызов `scheduler(c)` выполняет один переход состояния (`advance(c)` ровно один). Планировщик по умолчанию — `trivialTick`, просто вызывающий `c.fn(c.env)`. Цикл останавливается, когда у продолжения нет следующего шага: сопрограмма закончилась *или запаркована*.

`complete(c)` выполняет `c` (свежее из `delay(call)`) **до завершения**, включая парковки; именно во что превращается вызов из обычного, не-passive кода. Он делает себя `caller` сопрограммы (`system.Join` на своём стеке) и крутит цикл выше; если сопрограмма запаркована, затем ждёт, пока последнее состояние сопрограммы не выполнит этот `Join` — на любом потоке, который её возобновил. С планировщиком по умолчанию это ведёт себя как обычное синхронное выполнение, а когда вызываемая паркуется на вводе-выводе, обычный вызывающий ждёт, как при блокирующем вызове.

### 14.6. Пользовательские планировщики

```nim
type Scheduler* = proc (c: Continuation): Continuation {.nimcall.}

proc setScheduler*(handler: Scheduler)
```

Свой планировщик может интегрироваться с пулом потоков или мостом к циклу событий ввода-вывода. Чередование несвязанных продолжений относится к границам постановки в очередь/возобновления (например `submit` пула потоков), а не к трамплину, работающему поверх незавершённых стековых фреймов обычных процедур.

**Контракт планировщика.** Когда сопрограмма **паркуется** (`suspend()` возвращает `Continuation(fn: nil, env: frame)`) или **уступает** другой работе, планировщик позволяет текущему трамплину остановиться:

1. **Сохранить** продолжение, которое должно возобновиться позже (например в слоте IoRing через `delay()` или в очереди запуска пула потоков).
2. **Вернуть** запаркованное продолжение (или дать `trivialTick` его пропустить), чтобы трамплин обнаружил парковку через `parked(c)` и вышел.
3. **Возобновить** позже с чистой точки входа (например `submit(cont)` на рабочем потоке пула или цикл выше на захваченном продолжении).

Парковка никогда не завершает вызов, сделанный из обычной процедуры: тот вызывающий продолжает ждать (а при работающем пуле потоков ещё и работает за рабочий поток — `setPassiveWaitHook`), пока не выполнится последнее состояние вызываемого. Поэтому обычная процедура между двумя passive-вызовами держит свой аппаратный стековый фрейм, пока вызываемый запаркован, как при блокирующем вызове.

Планировщик **не должен** отправлять несвязанные продолжения внутри трамплина. Патологический пример — планировщик, который при каждом `suspend()` берёт следующее продолжение из общей очереди и скармливает его тому же циклу: каждая пройденная связка «passive → regular → passive» держит живым фрейм обычной процедуры, и тысячи таких чередований могут переполнить аппаратный стек, хотя глубина passive-в-passive ограничена только кучей. Рабочий пул потоков этого избегает: берёт один шаг продолжения на извлечение из очереди, не идёт через `setScheduler` и не ставит повторно после `suspend()`.

**Практическое правило: при приостановке или передаче — поставить в очередь и вернуться**; чередовать на границах `submit()`, где стеки чисты. На горячих путях помечайте обычные процедуры между двумя приостанавливающими passive-вызовами тоже `{.passive.}`, чтобы цепочка оставалась на размещённых в куче фреймах, а парковка освобождала поток, а не блокировала его.

### 14.7. Граница «язык / планировщик»

Passive-процедуры задают языковой механизм приостановки и продолжения. Активный планировщик решает, как чередуются готовые продолжения и как внешние события их возобновляют.

*Семантика языка:* вызовы passive-процедур — точки приостановки для passive-вызывающих; `delay(call)` захватывает дочернее продолжение и может требовать проверки sendability; `delay()` захватывает продолжение кода после ближайшего `suspend()` и хранит привязку к потоку; обычные процедуры могут вызывать passive-процедуры, компилятор доводит их до завершения через активный планировщик.

*Политика планировщика/рантайма:* при `suspend()` или уступке — поставить продолжение в очередь и вернуться, чтобы стековые фреймы свернулись до несвязанной работы; справедливость и стратегия очереди; work stealing и размещение в пуле потоков; детали ввода-вывода (`epoll`, `kqueue`, `io_uring`...); тайм-ауты, повторы, регистрация, политика пробуждения; интеграция с реактором, исполнителем или своим рантаймом.

### 14.8. Интеграция с вводом-выводом

Фундаментальный примитив ввода-вывода — passive-процедура, приостанавливающая сопрограмму и регистрирующая интерес к файловому дескриптору:

```nim
proc ioWait(fd: cint) {.passive.} =
  let c = delay()        # захват: продолжение кода после suspend()
  ioRing.store(fd, c)    # зарегистрировать в цикле событий
  suspend()              # остановить трамплин; ioRing возобновит c, когда fd готов
```

Операции верхнего уровня строятся поверх `ioWait`:

```nim
proc readLine(fd: cint): string {.passive.} =
  ioWait(fd)  # приостановиться, пока fd не станет читаемым
  result = ""
  var ch: char = '\0'
  while true:
    let n = posixRead(fd, addr ch, 1)
    if n <= 0 or ch == '\n':
      break
    result.add ch
```

Прикладной код читается как блокирующий ввод-вывод:

```nim
proc handleClient(fd: cint) {.passive.} =
  while true:
    let line = readLine(fd)
    if line.len == 0: break
    echo "echo: " & line
```

Ключевая мысль: `readLine` выглядит как блокирующая реализация. Механику приостановки берёт на себя компилятор: никаких колбэков, `await` и future-типов.

**Мост IoRing** (планировщик связывает passive-процедуры с циклом событий ОС): (1) passive-процедура вызывает `ioWait(fd)`; (2) `ioWait` кладёт текущее продолжение в слот IoRing для этого fd и паркуется через `suspend()` — `Continuation(fn: nil, env: this)`; (3) IoRing опрашивает (`epoll`/`kqueue`/`io_uring`) готовые дескрипторы; (4) когда fd готов, IoRing достаёт сохранённое продолжение и возвращает его в пул (`submit`), возобновляя сопрограмму с того места, где она остановилась. Один поток так обслуживает тысячи соединений, а каждый обработчик — простой последовательный цикл.

### 14.9. Примитивы: `delay`, `suspend`, `advance`

- `delay(passiveCall())` захватывает passive-вызов как `Continuation`, не выполняя его (как `toTask` для сопрограмм). Поскольку продолжение может уйти на другой поток, компилятор проверяет, что захваченное окружение «отправляемо» (например уникально или атомарно подсчитывается по ссылкам).
- `delay()` без аргумента захватывает **продолжение кода после ближайшего `suspend()`** — «остаток меня с этого места». CPS-преобразование заменяет его на `Continuation(fn: s_next, env: this)` на функцию состояния после `suspend()`. Форма привязана к потоку. Всегда используется вместе с последующим `suspend()`, между ними — код настройки (например регистрация в бэкенде ввода-вывода).
- `suspend()` паркует сопрограмму, возвращая `Continuation(fn: nil, env: this)`. Это останавливает трамплин, но сохраняет идентичность сопрограммы, так что планировщики различают **запаркованную** (`fn == nil`, `env != nil`) и **завершённую** (`fn == nil`, `env == nil`). Всегда в паре с предшествующим `delay()`, захватывающим точку возобновления. Код между `delay()` и `suspend()` — **окно настройки**: выполняется синхронно до приостановки и не должен содержать вызовов других passive-процедур.
- `advance(c)` делает один переход состояния; полезно для ручного чередования сопрограмм.
