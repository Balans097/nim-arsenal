## Термины

- **NIF** — текстовый формат дерева в виде вложенных скобок: `(tag child child …)`. Все промежуточные представления программы в Nimony хранятся в файлах NIF.
- **Leng** — «низкоуровневый» диалект NIF, близкий к C: типы с известным размером, явные указатели, нет дженериков и замыканий. Из Leng генерируется C, LLVM IR, машинный код, wasm или JavaScript.
- **asm-NIF** — диалект NIF, описывающий ассемблерные инструкции с типами; его выдаёт `arkham` и принимает `nifasm`.
- **Модуль** — один `.nim`-файл. Почти каждая стадия обрабатывает модули по отдельности и пишет по файлу на модуль.
- **nimcache** — каталог промежуточных файлов (по умолчанию `nimcache/`, меняется `--nimcache:`).
- **Бэкенд** — способ получить исполняемый файл из Leng: C (`nimony c`), LLVM (`l`), нативный (`n`), wasm (`w`), JavaScript (`j`).
- **hexer** — стадия, которая «опускает» проверенный NIF до Leng (разворачивает итераторы, замыкания, деструкторы и т. п.). В этом дереве исходников hexer не отдельная программа, а часть `shoggoth`.
- **Плагин** — программа, которую компилятор запускает во время семантического анализа, чтобы переписать фрагмент кода (например, цикл `||` из `std/parfor`).
- **Mtime** — время последнего изменения файла. `nifmake` решает, пересобирать ли цель, только по mtime.

## I. Конвейер компиляции

Команда `nimony c prog.nim` не делает работу сама. Она строит файл-описание графа сборки `*.build.nif` и отдаёт его `nifmake`, а тот запускает остальные утилиты в нужном порядке и параллельно, где это возможно.

```
prog.nim
  │  nifler2 (или nifler)  --portablePaths --deps parse
  ▼
<mod>.p.nif   <mod>.p.deps.nif            разбор: дерево без смысловой проверки + список import/include
  │  nimsem m
  ▼
<mod>.s.nif   <mod>.s.idx.nif             семантически проверенный NIF + интерфейсный индекс
  │  shoggoth c                           («hexer»: опускание до Leng)
  ▼
<mod>.x.nif                               Leng + секция для анализа живого кода
  │  shoggoth dl   (один раз на все модули)  → <mod>.live.nif
  │  shoggoth de   (параллельно по модулям)
  ▼
<mod>.c.nif                               Leng после удаления мёртвого кода
  │  shoggoth opt   (только при --opt:speed / --opt:size)
  ▼
<mod>.oc.nif                              оптимизированный Leng
  │
  ├── C / LLVM:   lengc c | llvm  →  .c / .ll  →  компилятор C  →  niflink  →  exe
  ├── нативный:   arkham  →  <mod>.asm.nif  →  nifasm (он же компоновщик)  →  exe
  └── wasm / JS:  jorogumo w | j  →  .wasm / .js   (утилита из nativenif, в вашем списке её нет)
```

Расширения в таблице — то, что пишут сами утилиты (имена взяты из `src/nimony/deps.nim`):

| Файл | Кто пишет | Что внутри |
|---|---|---|
| `.p.nif` (`.pc.nif` для `nimony doc`) | `nifler`, `nifler2` | разобранный модуль; в `.pc.nif` сохранены `##`-комментарии |
| `.p.deps.nif` | `nifler`, `nifler2` | список `import` / `include` модуля |
| `.s.nif` (`.sc.nif` для doc) | `nimsem m` | модуль после проверки типов и разрешения имён |
| `.s.idx.nif` | `nimsem` | интерфейс модуля; зависимые модули читают его вместо тяжёлого `.s.nif` |
| `.x.nif` | `shoggoth c` | Leng до удаления мёртвого кода |
| `.live.nif` | `shoggoth dl` | глобальный набор живых процедур для одного модуля |
| `.c.nif` | `shoggoth de` (или `d`) | Leng, готовый к кодогенерации |
| `.oc.nif` | `shoggoth opt` | оптимизированный Leng |
| `.asm.nif` | `arkham` | типизированный ассемблер для `nifasm` |
| `*.build.nif` | `nimony` | описание графа сборки для `nifmake` |
| `.cfg.nif` | `nifler config` | вся конфигурация проекта |
| `.docidx` | `dagon module` | боковой индекс документации модуля |

Где какая утилита вызывается — см. «Вызывается из» в каждом подразделе.

|---|---|---|---|

| `nifler` | парсер Nim → NIF (на базе парсера Nim 2) | `.nim` → `.p.nif`; `config` | `nimony`, `pnak` |

| `shoggoth` | hexer + удаление мёртвого кода + оптимизатор | `.s.nif` → `.x.nif` → `.c.nif` → `.oc.nif` | `nimony` |
| `lengc` | кодогенератор C / C++ / LLVM IR | `.c.nif` → `.c` / `.cpp` / `.ll` | `nimony` |
| `arkham` | кодогенератор машинного кода | `.c.nif` → `.asm.nif` | `nimony n` |

| `niflink` | компоновщик C-бэкенда | манифест → exe / lib | `nimony c` |
| `nifmake` | система сборки (граф, mtime, параллельность) | `.build.nif` → результат | `nimony`, `hastur` |
| `dagon` | генератор HTML-документации | `.sc.nif` → `.html` + `.docidx` | `nimony doc` |

| `pnak` | менеджер зависимостей | `.nimble` / `pnak.nif` → `deps/`, `nimony.paths` | вы |

## III. Утилиты

### 1. `nimony` — драйвер компилятора

**Назначение.** Единственная утилита, которую вы запускаете для компиляции. Разбирает командную строку, настраивает конфигурацию, строит граф сборки и запускает `nifmake`.

**Вызов.** `nimony [опции] команда файл`

**Команды.**

| Команда | Что делает |
|---|---|
| `c prog.nim` | полная сборка через C |
| `l prog.nim` | через LLVM (компоновщик по умолчанию `clang`) |
| `n prog.nim` | нативный бэкенд: `arkham` + `nifasm`; статический исполняемый файл без libc |
| `w prog.nim` | wasm: один модуль `.wasm` (через `jorogumo w`) |
| `j prog.nim` | JavaScript: один самодостаточный `.js` (через `jorogumo j`) |
| `check prog.nim` | только проверка ошибок; вместе с `--usages` / `--def` — для редакторов |
| `m файл.nim [проект.nim]` | компиляция одного модуля до hexer |
| `doc prog.nim` | генерация документации через `dagon` (нет в справке, есть в коде) |
| `s файл.nif` | скрытая служебная команда (сборка NIF-файла без парсинга) |

Лишнее число аргументов — ошибка: для `c`, `check`, `doc` допускается один файл, для `m` — до двух.

**Основные опции.**

| Опция | Смысл |
|---|---|
| `-d:СИМВОЛ`, `--define` | определить символ условной компиляции |
| `-d:release` | оптимизация по скорости, проверки времени выполнения включены |
| `-d:danger` | оптимизация по скорости и выключение всех проверок |
| `-p:ПУТЬ`, `--path` | добавить путь поиска модулей (в `.args`-файле запрещено — используйте `nimony.paths`) |
| `-f`, `--forcebuild` | пересобрать принудительно |
| `--ff` | принудительная полная пересборка |
| `-r`, `--run` | запустить программу после сборки |
| `--mm:СТРАТЕГИЯ` | управление памятью: `atomicArc` (по умолчанию), `arc`, `orc`, `yrc`, либо путь к своему рантайму |
| `--bits:N`, `--cpu:`, `--os:` | размер `int` (64/32/16) и целевая платформа (кросс-компиляция) |
| `--app:console\|gui\|lib\|staticlib` | тип приложения; нативный бэкенд умеет только `console` и `gui` |
| `--opt:speed\|size\|none` | уровень оптимизации C-компилятора (`-O3` / `-Os` / `-O0`; по умолчанию `-O1`) |
| `--boundchecks:on\|off` | проверки границ |
| `--cc:КОМПИЛЯТОР`, `--linker:` | компилятор C (имя или путь) и компоновщик |
| `--passC:`, `--passL:` | передать флаги компилятору C / компоновщику |
| `-o:ПУТЬ`, `--out:` | путь выходного файла; `--outdir:DIR` — каталог |
| `--nimcache:ПУТЬ` | каталог промежуточных файлов |
| `--silentMake` | не печатать вывод `nifmake` |
| `--parallelBuild:N` | не более N одновременных процессов (0 = по числу ядер) |
| `--profile`, `--report`, `--stats` | профиль времени команд, машиночитаемый отчёт, число строк и модулей |
| `--usages:файл,строка,столбец`, `--def:…` | найти использования / определение символа (столбец 1-based, как в редакторах) |
| `--layout:FILE` | нативный бэкенд, bare-metal: описание платы (память, стек, куча) |
| `--browser` (или `--target:browser`) | JS: код для браузера вместо node |
| `--inlineframes:on\|off` | помечать развёрнутые шаблоны, чтобы отладчик показывал их кадрами |
| `--novalidate` | не запускать `validator` для плагинов |
| `--verbose` | при сбое анализа контрактов вывести итоговое IR |
| `--compat`, `--noSystem`, `--isSystem`, `--isMain` | служебные режимы модулей |
| `--version`, `--help` | |

**Аргументы запускаемой программы.** При `-r` всё, что стоит после имени файла проекта, передаётся самой программе, а не компилятору:

```
nimony c -r prog.nim --verbose input.txt     # --verbose и input.txt получит prog
```

**Библиотека времени выполнения по умолчанию свободна от libc.** Для всех бэкендов по умолчанию включены собственный аллокатор (`nimNativeAlloc`) и ввод-вывод на системных вызовах (`nimNativeIo`). Вернуть libc можно так: `-d:useLibc` (оба), `-d:useMimalloc` (только аллокатор), `-d:useLibcIo` (только ввод-вывод). Нативный бэкенд (`n`) вообще не связывает libc и добавляет `nimNoLibc`; исключение — Linux с `-d:useLibc`: тогда объект `nifasm` дособирает системный компоновщик. Бэкенды `w` и `j` сами задают `--cpu:wasm32 --os:standalone --bits:32`.

**Файлы конфигурации.** Если в базовом каталоге проекта найден `nimony.args`, его содержимое обрабатывается как опции командной строки (раньше самой командной строки). Пути поиска задаются отдельным файлом `nimony.paths` (его генерирует `pnak`).

**Примеры.**

```sh
nimony c prog.nim                      # сборка через C
nimony c -d:release -o:prog prog.nim   # релизная сборка, выходной файл prog
nimony n -r prog.nim                   # нативная сборка (без C и libc) и запуск
nimony check prog.nim                  # только проверка
nimony check --def:prog.nim,12,5 prog.nim   # где определён символ в строке 12, столбце 5
nimony doc prog.nim                    # документация в htmldocs/
```

**Замечания.**
- Значение `--out` вместе с `--outdir`: как в Nim, `--out:dir/name` кладёт каталог в `outDir`; задавайте `--outdir:` после `--out:`, чтобы наслоить.
- Справка называет путь по умолчанию `<nimcache>/<бэкенд>/<хеш модуля>/<имя>.exe` и одновременно говорит, что `--outdir` по умолчанию — текущий каталог. Фактическое место проверьте на своей сборке.

### 2. `nifler` — парсер Nim → NIF

**Назначение.** Читает `.nim` и пишет NIF. Без проверки типов и поиска символов. Использует парсер самого Nim 2 (`compiler/parser.nim`, зафиксирован в `src/nifler/nimparser/upstream.commit`).

**Вызов.** `nifler [опции] команда файл [выход]`

**Команды.**

| Команда | Результат |
|---|---|
| `p`, `parse файл.nim [out.nif]` | NIF-файл (по умолчанию рядом с исходником, расширение `.nif`) |
| `deps файл.nim [out.deps.nif]` | только файл зависимостей (`import` / `include`) |
| `config проект.nim [out.cfg.nif]` | NIF со всей конфигурацией проекта (`.cfg.nif`) |

**Опции.**

| Опция | Смысл |
|---|---|
| `--portablePaths` | пути в позициях строк не зависят от ОС (в коде это уже режим по умолчанию) |
| `--deps` | вместе с `parse` ещё и `<имя>.deps.nif` |
| `--docs` | сохранить `##`-комментарии как метаданные деклараций (для `nimony doc`) |
| `-f`, `--force` | не пропускать, даже если результат свежий |
| `--version`, `--help` | |

**Инкрементальность.** Если выходной файл уже есть и новее исходника (а при `--deps` — и файл зависимостей новее), разбор пропускается. Для `config` проверяется, не менялись ли исходные файлы конфигурации.

**Вызывается из.** `nimony` (когда нет `nifler2`, а также всегда для `nimony doc` с `--docs`), `pnak` (чтение `.nimble`).

**Примеры.**

```sh
nifler --portablePaths --deps parse prog.nim nimcache/prog.p.nif
nifler config prog.nim                  # → prog.cfg.nif
```

### 3. `nifler2` — парсер второго поколения

**Назначение.** То же, что `nifler`, но сам написан на Nimony и не зависит от компилятора Nim 2: лексер `nimlexer`, парсер генерируется из грамматики `nimgrammar.nim` плагином `deps/parsegen`. `nimony` предпочитает `nifler2`, если он собран (`tooldirs.parserTool`); перед первой сборкой парсит им `nifler`. Результат для `.p.nif` и файлов зависимостей совпадает побайтно с `nifler`.

**Вызов.** `nifler2 [опции] команда файл [выход]`

| Команда | Результат |
|---|---|
| `p`, `parse файл.nim [out.nif]` | NIF-файл |
| `deps файл.nim [out.nif]` | только файл зависимостей |
| `t`, `tree файл.nim` | распечатать дерево в stdout (для отладки) |

**Опции.** `--deps` — дополнительно `<out>.deps.nif`. `--portablePaths` и `-f`/`--force` принимаются, но ничего не меняют (пути всегда записываются относительно текущего каталога, выход всегда перезаписывается). Любая другая опция — ошибка.

**Чего нет по сравнению с `nifler`.** Команды `config` и опции `--docs`; поэтому `nimony doc` и конфигурация проекта по-прежнему идут через `nifler`.

**Фильтры исходника.** Если первая строка файла `#? stdtmpl | standard` (и аналоги `strip`, `replace`), текст преобразуется до разбора — как в Nim. Ошибки лексера и фильтров собираются и завершают процесс кодом 1; синтаксическая ошибка завершает процесс сразу.

**Пример.**

```sh
nifler2 p prog.nim nimcache/prog.p.nif
nifler2 t prog.nim | less
```

### 4. `nimsem` — семантический анализ

**Назначение.** Принимает разобранные модули (`.p.nif`) и выдаёт проверенные (`.s.nif`) вместе с интерфейсным индексом (`.s.idx.nif`). Выполняет разрешение имён, проверку типов, раскрытие шаблонов и макросов, анализ контрактов, запуск плагинов и вычисления времени компиляции. Умеет отвечать на запросы IDE.

**Вызов.** `nimsem [опции] команда аргументы`

| Команда | Что делает |
|---|---|
| `m input.nif [...]` | проверить один или несколько модулей; имена выходов и индексов выводятся из имени входа (`.p.nif` → `.s.nif`, `.pc.nif` → `.sc.nif`) |
| `x файл.nif` | сгенерировать `.idx.nif` из NIF-файла |
| `e файл.nif [зависимости.nif …]` | выполнить NIF-файл (вычисления времени компиляции); перед этим собирает `std/writenif.nim` через `nimony c` |
| `idetools файл1.nif [файл2.nif …]` | перечислить использования или определения; нужна `--usages` или `--def`, иначе ошибка «no --track information provided» |
| `plugin плагин.nim исполняемый` | собрать плагин (ровно два аргумента); в сборку входит `validator` (этой команды нет в справке, она описана в коде) |

**Опции.** Те же общие, что у `nimony` (`-d`, `-p`, `--mm`, `--bits`, `--cpu`, `--os`, `--app`, `--base`, `--nimcache`, `--compat`, `--noSystem`, `--isSystem`, `--isMain`, `--novalidate`, `--verbose`, `--flags`, `--version`, `--help`), и дополнительно:

| Опция | Смысл |
|---|---|
| `-f`, `--forcebuild`, `--ff` | принудительная пересборка; в вычисления времени компиляции не передаётся |
| `--keepsemtree` | сохранить несжатое семантическое дерево (`.sem.nif`) — оно нужно `validator` |
| `--parallelBuild:N`, `--inlineframes`, `--cycles` | как у `nimony` (`--cycles` служебная) |

**Вызывается из.** `nimony` (в графе сборки команда называется `nimsem`; для `check` добавляется `idetools`, для плагинов — `pluginbuild`).

**Примеры.**

```sh
nimsem m nimcache/prog.p.nif
nimsem --usages:prog.nim,12,5 idetools nimcache/prog.s.nif
```

Вручную запускать `nimsem` обычно не нужно: все нужные флаги выставляет `nimony`.

### 5. `shoggoth` — средняя часть компилятора (hexer + оптимизатор)

**Назначение.** Одна программа с несколькими подкомандами: опускание проверенного NIF до Leng (hexer), поиск и удаление мёртвого кода, необязательный оптимизатор деревьев Leng, а также инструмент «паттерн по образцу».

**Вызов.** `shoggoth [опции] команда аргументы`

| Команда | Что делает |
|---|---|
| `c файл.nif` | один семантически проверенный модуль → Leng (`.x.nif`) |
| `d файл1.nif файл2.nif …` | удаление мёртвого кода для набора файлов одним вызовом, без разделения на `dl` и `de` |
| `dl файл1.x.nif …` | вычислить глобальный набор живого кода; пишет по `.live.nif` на модуль |
| `de файл.x.nif файл.live.nif` | вывести живой код одного модуля как `.c.nif`; модули независимы, `nifmake` запускает их параллельно |
| `opt [--outdir:DIR] [--verify] [--stats] [--vectorize[:sse]] вход.nif [выход.nif]` | оптимизировать модули Leng; без `выход.nif` переписывает входной файл на месте |
| `pat [--from:NIF] [--keep] [--shoggoth] файл.nim [подстрока]` | скомпилировать `.nim` и напечатать процедуры Leng (для написания правил оптимизатора по образцу) |

**Опции (команды `c`, `d`, `dl`, `de`).**

| Опция | Смысл |
|---|---|
| `--bits:N` | разрядность `int` (64/32/16) |
| `--cpu:be\|le` | **порядок байт** (big/little endian), а не архитектура процессора |
| `--os:ИМЯ` | на кодогенерацию влияет только различие «Windows / не Windows» (у точки входа Windows нет `argc/argv/envp`) |
| `--outdir:DIR` | куда писать результаты (`d`, `dl`, `de`) |
| `--isMain` | отметить файл как главный модуль |
| `--native` | кодогенерация для нативного бэкенда (`arkham` + `nifasm`) |
| `--crt` | нативная программа линкуется с libc (точка входа `main`) |
| `--app:console\|gui\|lib\|staticlib` | тип приложения |
| `--flags:ФЛАГИ` | включённые проверки времени выполнения (пустой `--flags` = ни одной) |
| `--version`, `--help` | |

**Опции `opt`.** `--outdir:DIR` (каталог выходных файлов), `--verify` (проверить результат), `--stats` (по строке на файл: число процедур и тел), `--vectorize` (128-битная векторизация для AArch64) и `--vectorize:sse` (для x86-64). Векторизацию `nimony` включает сам, но только для нативного бэкенда на `arm64` / `amd64`.

**Опции `pat`.** `--nimony:ПУТЬ` (какой `nimony` вызвать), `--nimcache:`, `--from:NIF` (взять готовый файл вместо компиляции), `--keep` (оставить временный каталог), `--shoggoth` (собрать с `--opt:speed`).

**Вызывается из.** `nimony` (в графе сборки: `hexer`, `dce`, `dceLive`, `dceEmit`, `optimize`).

**Пример.**

```sh
shoggoth c --bits:64 --cpu:le --os:linux nimcache/prog.s.nif
shoggoth opt --stats --verify nimcache/c/prog.c.nif nimcache/c/prog.oc.nif
shoggoth pat prog.nim myproc          # покажет только процедуры, в имени которых есть myproc
```

### 6. `lengc` — кодогенератор C / C++ / LLVM IR

**Назначение.** Переводит Leng (`.c.nif` или `.oc.nif`) в код на C, C++ или в текстовый LLVM IR.

**Вызов.** `lengc [опции] команда файл [файл2 …]`

| Команда | Что делает |
|---|---|
| `c файл.nif …` | в C (`<nimcache>/<имя>.c`) |
| `cpp файл.nif …` | в C++ (`.cpp`) |
| `llvm файл.nif …` | в LLVM IR (`.ll`) |
| `n файл.nif` | скрытая: ассемблер через встроенный нативный путь; без сборки с `enableAsm` выдаёт «wasn't built with native target support» |

Последним в списке называется главный модуль: он получает признак «main» и по его имени называется результат.

**Опции.**

| Опция | Смысл |
|---|---|
| `-r`, `--run` | запустить сборку и программу |
| `--compileOnly` | только сгенерировать код; сборку делает `nifmake` / `niflink` |
| `--isMain` | с `--compileOnly` считать файл главным |
| `--cc:gcc\|clang` | компилятор C (по умолчанию `gcc`, на macOS `clang`) |
| `--opt:none\|speed\|size` | уровень оптимизации |
| `--lineDir:on\|off` | директивы `#line` |
| `--bits:N` | разрядность `int` (64/32/16) |
| `--nimcache:ПУТЬ` | каталог результатов (по умолчанию `nimcache`) |
| `--app:console\|gui\|lib\|staticlib` | тип приложения |
| `-o:`, `--out:` | имя результата (нет в справке) |
| `--version`, `--help` | |

**Вызывается из.** `nimony c` и `nimony l`; он сам запускает `lengc <c\|llvm> --compileOnly --bits:N … файл`.

**Пример.**

```sh
lengc c --compileOnly --bits:64 --nimcache:nimcache a.c.nif b.c.nif main.c.nif
```

### 7. `arkham` — нативный кодогенератор

**Назначение.** Переводит один Leng-модуль (`.c.nif`) в типизированный асм-NIF (`.asm.nif`) для выбранной платформы. Не использует C-компилятор и ассемблер; результат принимает `nifasm`. Репозиторий: `nim-lang/nativenif`, каталог `src/arkham`. Версия `0.1.0`.

**Вызов.** `arkham [опции] файл.c.nif`

| Опция | Смысл |
|---|---|
| `-o:ФАЙЛ`, `--output:` | выходной файл (по умолчанию `<вход>.asm.nif`) |
| `--os:СИМВОЛ` | `linux`, `windows`, `macosx`, `embedded` (также `freebsd`); по умолчанию — хост |
| `--cpu:СИМВОЛ` | `amd64`, `arm64`, `arm32`, `avr`, `riscv32`; по умолчанию — хост |
| `--layout:ФАЙЛ` | только bare-metal: плата — области памяти, секции, стеки и куча (дерево `(layout …)`); пересылается в асм-NIF, чтобы `nifasm` разместил сегменты по тому же описанию |
| `--crt` | linux/amd64, windows/amd64: программа линкуется с C-рантаймом системным компоновщиком; точка входа вызывается как `main`, `importc` привязывается к libc |
| `-a:АРХ`, `--arch:` | устаревшая объединённая форма: `arm64`, `x64`, `linux_arm64`, `win_x64`; нельзя смешивать с `--os`/`--cpu` |
| `-h`, `--help` | |

Если указана только половина пары `--os`/`--cpu`, вторая берётся от хоста. Неизвестная опция — ошибка (молча её не пропускают, чтобы переименованный флаг не «работал» незаметно).

**Поддерживаемые сочетания.**

| ОС / процессор | Примечание |
|---|---|
| `linux/amd64` | |
| `windows/amd64` | PE |
| `linux/arm64` | |
| `macosx/arm64` | |
| `freebsd/amd64` | принимается кодом, в справке не перечислено |
| `embedded/arm32` | bare-metal Cortex-M4 |
| `embedded/avr` | bare-metal avr5 |
| `embedded/riscv32` | bare-metal RV32IMAFD |

**Вызывается из.** `nimony n` (команда `arkham` в графе сборки; цель передаётся строго как `--os:` и `--cpu:`, плюс `--layout:` и `--crt`, если нужны).

**Пример.**

```sh
arkham --os:linux --cpu:amd64 -o:prog.asm.nif nimcache/native/prog.c.nif
```

### 8. `nifasm` — ассемблер и компоновщик

**Назначение.** Проверяет типы асм-NIF, кодирует инструкции и сам записывает готовый статический образ ELF, Mach-O или PE. Внешний компоновщик не нужен. Принимает `.asm.nif` главного модуля; зависимые модули находит сам по суффиксу имени на диске (сначала `<суффикс>.asm.nif`, затем `<суффикс>.nif`). Версия `0.1.0`.

**Вызов.** `nifasm [опции] файл.nif`

| Опция | Смысл |
|---|---|
| `-o:ФАЙЛ`, `--output:` | выходной файл (по умолчанию имя входа без расширения; для `--emit-obj` — `.o`) |
| `-c`, `--emit-obj` | записать перемещаемый объект `.o` для системного компоновщика вместо готового exe |
| `--symmap` | вывести в stderr виртуальный адрес каждой процедуры (в статическом ELF нет таблицы символов) |
| `--no-debug-info` | не писать имена процедур и таблицы раскрутки (`.symtab` + `.eh_frame` в ELF, `LC_SYMTAB` + `__eh_frame` в Mach-O, `.pdata` + `.xdata` в PE) |
| `--listing:ФАЙЛ` | TSV по одной строке на инструкцию: адрес, длина, глубина вложенности, процедура, узел NIF; для привязки профиля выполнения к исходной конструкции |
| `--flash:АДРЕС`, `--flash-size:N` | Cortex-M: база и размер области кода и констант (по умолчанию `0x00000000`, 4M) |
| `--ram:АДРЕС`, `--ram-size:N` | Cortex-M: база и размер SRAM (по умолчанию `0x20000000`, 64K) |
| `--stack-top:АДРЕС` | Cortex-M: начальное значение MSP; должно лежать внутри ОЗУ (по умолчанию — верх ОЗУ) |
| `-v`, `--version`, `-h`, `--help` | |

Размеры принимают суффиксы `K`, `M`, `G`; адреса — префикс `0x`. Пример для STM32F407: `--flash:0x08000000 --flash-size:1M --ram-size:128K`.

**Вызывается из.** `nimony n`: либо как компоновщик (главный `.asm.nif` → exe), либо с `--emit-obj` в сочетании с системным компоновщиком (когда нативная программа линкуется с libc и внешними объектами).

**Замечание.** Справка `nifasm` говорит, что `--emit-obj` работает «только на macOS arm64», но `arkham --crt` и исходники `nimony` (`nativeSysLink`) используют его и для Linux (`-no-pie -pthread`). Доверяйте поведению вызывающих утилит.

### 9. `niflink` — компоновщик C-бэкенда

**Назначение.** Читает **манифест компоновки** — небольшой NIF-файл, который пишет `nimony` — и выполняет всё хвостовое: компилирует C-исходники, линкует объекты в исполняемый файл или разделяемую библиотеку либо архивирует их в статическую.

**Вызов.** `niflink манифест.nif [выход]`. Явный `выход` перекрывает `(output …)` из манифеста; пути вообще нет — ошибка.

**Манифест.**

```
(link
  (apptype "console")                ; console | gui | lib | staticlib
  (linker "gcc")                     ; драйвер, которым компилировались объекты
  (output "путь/к/app")
  (file "a.o"  (kind "obj"))         ; линкуется как есть
  (file "b.c"  (kind "csrc"))        ; сначала компилируется (cc -c), затем линкуется
  (file "g.o"  (kind "obj") (flags "-lvulkan"))   ; флаги этого файла, сразу после него
  (file "k.spv" (kind "artifact"))   ; для C-компоновщика не нужен, пропускается
  (flags "-lm"))                     ; глобальные флаги
```

**Поведение.**
- Драйвер берётся из манифеста; если не указан — из переменной `CC`, иначе `cc` (на Windows `gcc`).
- `apptype "staticlib"`: запускается `ar rcs` (переменная `AR`), только объекты.
- `apptype "lib"`: добавляется `-shared`.
- Слишком длинная командная строка уходит во временный файл: `@response-файл` на Linux и Windows (обратные слэши заменяются на прямые), shell-скрипт на macOS.
- На Windows с `clang` добавляется `-fuse-ld=lld`.

**Вызывается из.** `nimony c` и `nimony l` (звено «link»), если модуль `{.build.}` не подставил свой компоновщик.

### 10. `nifmake` — система сборки

**Назначение.** make-подобная утилита, на которой держится параллельная и инкрементальная сборка Nimony. Либо выполняет граф зависимостей сама, либо переводит его в `Makefile`. Алгоритм по статье о системе сборки Tup: частичное построение графа по изменившимся файлам, добавление зависимостей, топологическая сортировка (с обнаружением циклов), выполнение.

**Вызов.** `nifmake [опции] команда [файл]`

| Команда | Что делает |
|---|---|
| `run файл.nif` | выполнить граф сборки |
| `makefile файл.nif` | сгенерировать `Makefile` |
| `help`, `version` | |

**Опции.**

| Опция | Смысл |
|---|---|
| `-j`, `--parallel[:N]` | параллельное выполнение (`run`); `:N` ограничивает числом процессов, без значения — по числу ядер |
| `--makefile:ИМЯ` | имя создаваемого Makefile (по умолчанию `Makefile`) |
| `--force` | пересобрать всё |
| `--rerun` | выполнить каждую команду независимо от свежести, но оставить времена изменения самим утилитам; для случаев, когда результаты устарели по причине, которую mtime не выражает (например, поменялись опции компиляции) |
| `--verbose` | подробный вывод |
| `--base:DIR` | каталог для файлов `.args`; без опции `.args` не обрабатываются |
| `--progress[:LO:HI]` | индикатор процентов на интерактивном терминале; `LO:HI` вписывает шкалу в поддиапазон, чтобы несколько сборок подряд давали одну сплошную шкалу 0–100 % |
| `--profile` | время и пиковую память выполненных команд — в stderr |
| `--report` | в stdout одна строка вида `nifmake-report nimsem=2 hexer=1 total=3`; пустой отчёт означает «всё актуально» (используется тестами инкрементальности) |

**Формат файла сборки.** Заголовок `(.nif27)`, внутри `(stmts …)`:

```nif
(.nif27)
(stmts
  (cmd :nifler "bin/nifler" "--portablePaths --deps parse" (input) (output))
  (do nifler
    (input "src/main.nim")
    (output "nimcache/main.1.nif")))
```

- `(cmd :имя "программа" …)` — шаблон команды. В нём:
  - `(input)`, `(input N M)` — входные файлы с индексами; отрицательный индекс считается от конца, `(input +0 -1)` — все; перед индексами можно поставить строку-префикс, после — суффикс;
  - `(output …)` — то же для выходов;
  - `(args)` — аргументы, переданные в `(do …)` через `(args "…")`;
  - `(argsext)` — расширение файла с дополнительными аргументами (по умолчанию `.args`, для компоновщиков обычно `.linker.args`).
- `(do имя …)` — правило сборки: `(input "файл")` и `(output "файл")` здесь определяют **рёбра графа** (не путать с одноимёнными тегами в `cmd`, которые лишь подставляют имена в командную строку).
- `(inputsof команда [".суффикс"])` — добавить как входы все выходы всех узлов с этой командой (с необязательным отбором по суффиксу). Нужно, когда утилита читает результат фазы целиком (например, `lengc` загружает любой модуль, где определён внешний символ).
- `(atomic)` — писать выходы во временные файлы рядом и подменять после успеха; нужен для общих объектов, которые могут собирать одновременно несколько сборок.

**Планирование.** Узел запускается, как только готовы *его собственные* входы; нет пакетов по глубине графа. Поэтому объявленные входы определяют порядок, а не только актуальность: утилита, читающая необъявленный файл, раньше «выживала» лишь благодаря удачному порядку.

**Пример.**

```sh
nifmake -j run nimcache/prog.build.nif
nifmake --makefile:build.mk makefile nimcache/prog.build.nif
```

### 11. `dagon` — генератор документации

**Назначение.** Бэкенд документации (аналог кодогенератора, но для документации). Читает `.sc.nif` (результат проверки с сохранёнными комментариями) и пишет по одному файлу на модуль — HTML или дерево NIF той же структуры.

**Вызов.** `dagon [опции] команда аргументы`

| Команда | Что делает |
|---|---|
| `m`, `module вход.sc.nif выход.html выход.docidx` | документация одного модуля (ровно три аргумента) |
| `link выход.html файл.docidx …` | объединить боковые индексы в общую страницу `theindex.html` |

**Опции.**

| Опция | Смысл |
|---|---|
| `--format:html\|nif` | формат результата `module` (по умолчанию `html`) |
| `--projectRoot:DIR`, `--stdlibRoot:DIR` | исходники под этими корнями получают зеркальные относительные пути; прочее попадает в `_external/` |
| `--outdir:DIR` | корень документации (по умолчанию `htmldocs`); нужен для вычисления относительных ссылок между страницами |
| `--version`, `--help` | |

**Вызывается из.** `nimony doc`; формирует сам правила `module` по каждому модулю и завершающий `link`. Результат — страницы вида `htmldocs/std/system.html` и общий индекс.

**Пример.**

```sh
nimony doc prog.nim          # обычный путь; dagon запускается автоматически
dagon --outdir:htmldocs module nimcache/prog.sc.nif htmldocs/prog.html nimcache/prog.docidx
```

### 12. `validator` — проверка плагинов и проходов

**Назначение.** Проверяет исходники компиляторных проходов и плагинов на структурную корректность: NIF, который строит процедура, должен соответствовать грамматике из `doc/tags.md`, а обход входного дерева — быть «учтён» (каждый параметр `var Cursor` израсходован, продвижение в каждой ветви согласовано с выводом, каждый цикл по курсору заведомо продвигается). Работает над семантически проверенным модулем, то есть с разрешёнными символами, а не с написанием.

**Вызов.** `validator [--strict] [--nimcache:DIR] [--dump] [--dumptrees] <файл.nim | модуль.s.nif> [tags.md]`

| Опция | Смысл |
|---|---|
| `--strict` | добавочные проверки для исходников проходов компилятора (исчерпывающий `case` по виду тега, «голые» `skip` / `inc` курсора); для плагинов не нужен — им идиоматично `else: takeTree n` |
| `--nimcache:DIR` | кэш, в который писал `nimony check`; **обязателен**, если передан `.nim`-файл |
| `--dump` | показать, что фронтенд «понял» в модуле |
| `--dumptrees` | показать все построенные деревья (первое, что стоит смотреть при ложном срабатывании) |

Второй позиционный аргумент — путь к `tags.md`. Если не указан, ищется `<каталог утилиты>/../doc/tags.md`, затем `<каталог>/../../doc/tags.md`, затем `doc/tags.md`.

**Соответствие исходника и NIF.** По `.nim` ищется соответствующий `.s.nif` через файлы `*.build.nif` в кэше (они авторитетны); берётся несжатый `.sem.nif`, если модуль собран с `--keepsemtree`. Для `include`-файлов используется модуль, который их включает.

**Код возврата.** `1`, если найдены ошибки.

**Вызывается из.** `nimsem plugin` при сборке плагина; отключается `nimony --novalidate`.

**Пример.**

```sh
nimony check --keepsemtree --nimcache:/tmp/vc src/myplugin.nim
validator --nimcache:/tmp/vc src/myplugin.nim
validator --strict --nimcache:/tmp/vc src/nimony/mypass.nim
```

### 13. `hastur` — тестер и сборщик тулчейна

**Назначение.** Строит утилиты тулчейна, прогоняет тесты, проверяет самосборку, ведёт «золотые» результаты. Большинство команд ожидает запуска из корня репозитория `nimony`.

**Вызов.** `hastur [опции] команда [аргументы]`. Аргументы, не относящиеся к `hastur`, пересылаются компилятору Nimony.

**Команды.**

| Команда | Что делает |
|---|---|
| `build [цель]` | собрать выбранные утилиты (по умолчанию `all`). Цели: `all`, `nimony`, `nifler`, `nifler2`, `lengc`, `shoggoth`, `nifmake`, `validator`, `dagon`, `pnak`, `arkham`, `nifasm`, `jorogumo`, `native`, `nifbench`. `all` добавляет `arkham` + `nifasm`, если рядом лежит `../nativenif`, и сообщает, если нет; `native` (`arkham` + `nifasm` + `shoggoth`) просит их явно и при отсутствии выдаёт ошибку |
| `tiers [native]` | скомпилировать каждый модуль из списка bootstrap-зависимостей; `native` — через `nimony n`. Не останавливается на первой ошибке и в конце выдаёт по строке на каждую диагностику с модулями, которые к ней привели |
| `boot [опции]` | самосборка всего тулчейна (`nimony`, `nimsem`, `shoggoth`, `lengc`): `bin0/` — копия собранного хостовым Nim, `binN/` — результат перекомпиляции `binN-1/`; результаты остаются на месте, в `bin/` ничего не устанавливается. На linux/amd64, linux/arm64, windows/amd64 и macOS/arm64 стадии собираются нативным бэкендом, если собраны `arkham` и `nifasm` |
| `selfcheck` | полная проверка регрессий компилятора: пересборка тулчейна, `tiers`, затем `boot --valgrind` (release) |
| `<каталог>` | прогнать дерево тестов от каталога (каждая папка — либо `setup.nim`, либо встроенный runner Nimony, рекурсивно) |
| `all` | весь набор: тесты + примеры |
| `native` | отобранный набор нативных регрессий через `nimony n` |
| `nativevalgrind` | нативные тесты с `-d:valgrind` под memcheck (пока Linux/AArch64) |
| `wasmdiff` | сравнение нативного бэкенда (эталон) и `jorogumo w` на `tests/ithaqua/*.nim`; нужен `node` и `../nativenif` |
| `lengc` | тесты Leng |
| `test <файл\|каталог>` | один тест или плоский каталог тестов |
| `joined <каталог>` | прогнать объединяемые тесты каталога **одной** программой (так их запускает пул вручную) |
| `bug [файл]` | собрать `nimony` + `shoggoth` и скомпилировать файл (по умолчанию `bug.nim`) для заполнения `nimcache/` |
| `rep` | повторить последнюю неудачную команду сессии |
| `record <файл> <tout>` | записать результат как часть набора тестов |
| `update deps` | перезакрепить `src/nativenif.commit` на то, что сейчас в `../nativenif` |
| `update parser` | перезакрепить `src/nifler/nimparser/upstream.commit` на вершину `devel` Nim |
| `install` | записать скрипты активации (добавляют каталоги тулчейна в `$PATH`); на Windows ещё скачать MinGW + LLVM и DLL |
| `clean` | удалить все сгенерированные файлы |
| `sync [новая-ветка]` | удалить текущую ветку и подтянуть последнее из удалённого репозитория |

**Опции.**

| Опция | Смысл |
|---|---|
| `--overwrite` | перезаписать результаты выбранных тестов (подразумевает `--joined:off`) |
| `--ast`, `--codegen` | отслеживать ещё и содержимое AST / кодогенератора |
| `--forward:ОПЦИЯ` | передать опцию компилятору Nimony (можно в любом месте командной строки) |
| `--debug` | собрать фронтенд-утилиты без оптимизации (по умолчанию `-d:release`); для gdb |
| `--release` | для тулчейна ничего не меняет; для `boot` дополнительно собирает вывод самосборочного `nimony` с `--opt:speed` |
| `--no-release` | `boot` на уровне оптимизации по умолчанию |
| `--jobs:N\|auto` | до N тестов параллельно (`auto` = число ядер) |
| `--parallelBuild:N` | не более N процессов сборки (0 = по числу ядер) |
| `--joined:on\|off` | компилировать простые тесты каталога одной программой (по умолчанию `on`); упавшая группа перезапускается тест за тестом |
| `--native:on\|off` | на Windows тесты, за которые «ручается» `hastur native`, собираются `nimony n` (по умолчанию `on`) |
| `--cachedir:ПУТЬ` | вместо `nimcache/` |
| `--bindir:ПУТЬ` | брать тулчейн из этого каталога (подразумевает `--no-build`) |
| `--no-build` | пропустить подготовительный шаг `setup.hastur` |
| `--skip:КАТАЛОГ` | исключить каталог из обхода (повторяемо); для разделения набора между CI-раннерами |
| `--native-debug` | собрать `arkham` + `nifasm` без оптимизации |
| `--boot-backend:auto\|c\|native` | каким бэкендом `boot` собирает стадии |
| `--valgrind` | для `boot`: сборка с `-DMI_TRACK_VALGRIND=1` и smoke-тест под valgrind (принудительно C-бэкенд) |
| `--prefill:DIR`, `--scratch` | служебные: для рабочих процессов пула (затравка кэша и приватный кэш) |
| `--version`, `--help` | |

**Файлы в каталоге с тестами (все необязательны).**

| Файл | Назначение |
|---|---|
| `setup.nim` | собственный runner, владеющий каталогом и поддеревом; импортирует `src/hastur/kit`; код возврата — вердикт |
| `setup.hastur` | подготовка для встроенного runner: по команде `hastur` в строке (например, `build nimony`) перед тестами ниже |
| `<тест>.nojoin` | исключить тест из объединённой программы |
| `hastur.mode` | категория каталога: `nosystem`, `track`, `compat`, `valgrind`, `opt`, `skip` |

**Параллельный пул (`parallel.nim`).** При `--jobs:N` каждая единица работы (файл, объединённая группа или каталог с `setup.nim`) выполняется отдельным дочерним `hastur` с собственным кэшем `nimcache/.par/<номер>`. Единицы идут «самые долгие первыми» — по времени прошлых запусков из `nimcache_static/hastur.times`, а для новых — по оценке из числа тестов; наборы `setup.nim` ставятся в самое начало. Общий затравочный кэш (`warmup`) собирается один раз, а `static.o` mimalloc — заранее и последовательно, чтобы воркеры не писали его одновременно.

**Примеры.**

```sh
hastur build                       # всё, что нужно тулчейну
hastur build nimony                # пересобрать одну утилиту
hastur --jobs:auto all             # весь набор на всех ядрах
hastur test tests/nimony/foo.nim   # один тест
hastur --overwrite test t.nim      # обновить эталон
hastur boot                        # самосборка
hastur update deps                 # перезакрепить nativenif
```

### 14. `pnak` — менеджер пакетов

**Назначение.** «Pnakotic Nimony Archive Kontrol»: клонирует зависимости проекта (из git) и записывает пути к ним в `nimony.paths`. Зависимости читаются из файла `.nimble` (через `nifler`) или из замка `pnak.nif`.

**Вызов.** `pnak [опции] [команда] [аргументы]` (без команды — `fetch`)

| Команда | Что делает |
|---|---|
| `fetch [.nimble]` | клонировать или обновить замыкание зависимостей и переписать `nimony.paths`. `pnak.nif` рядом с проектом (или в текущем каталоге) предпочтительнее `.nimble` |
| `pin [.nimble]` | построить полное замыкание и записать в `pnak.nif` каждую прямую и косвенную зависимость с точным коммитом; файл затем работает как замок |
| `search <слова>` | поиск пакетов в `packages.json` и на GitHub |
| `refresh` | заново скачать `packages.json` в кэш |
| `translate <пакет> <версия>` | пройти историю `.nimble` пакета и вывести SHA последнего коммита, у которого `version = "…"` равна указанной |

**Опции.**

| Опция | Смысл |
|---|---|
| `--depsdir:DIR` | куда класть клоны (по умолчанию `deps`) |
| `--cfg:ФАЙЛ` | какой `nimony.paths` править (по умолчанию рядом с `.nimble`; можно указать и `nim.cfg`) |
| `--nocfg` | не генерировать `nimony.paths` / `nim.cfg` |
| `--offline` | не обращаться к сети (только кэшированный `packages.json` и существующие клоны) |
| `--deep` | всегда клонировать с полной историей (по умолчанию неглубоко, а при закреплённом коммите — автоматически полностью) |
| `-j`, `--parallel:N\|auto` | до N клонирований одновременно (по умолчанию 1) |
| `--nimony` | только для `search`: ограничить темами GitHub `nimony` / `nim3` и записями `packages.json` с теми же тегами |
| `--version`, `--help` | |

**Как выбирается версия.** Для каждого пакета берётся либо конкретный коммит, либо `HEAD`. Побеждает требование, **ближайшее к корню** проекта по глубине зависимости: если `A` (глубина 1) хочет `C@abc`, а `D` (глубина 2) — `C@def`, то и для `A`, и для `D` будет `C@abc`. Ограничения версий в `requires` игнорируются.

**Строки `requires` в `.nimble`.** `requires "<git-url>[#<коммит>] [ограничение]"` или `requires "<имя>[#<коммит>] [ограничение]"`. URL используется как есть; голое имя разрешается через официальный `packages.json` (скачивается один раз в пользовательский кэш и обновляется раз в 7 дней), с учётом `alias`; если не нашлось — поиск на GitHub по `language:nim` с единственным совпадением без учёта регистра. Строка `requires "nim ..."` относится к компилятору и игнорируется.

**Ссылки-файлы.** В каталоге зависимостей элемент может быть не каталогом, а текстовым файлом: первая непустая строка — путь (абсолютный или от каталога зависимостей) к месту, где пакет лежит на самом деле. Это аналог `.nimble-link`, удобно при работе над несколькими пакетами сразу. Для ссылки `pnak` не клонирует и не переключает коммит, а читает `.nimble` этого пакета и прописывает его путь.

**`nimony.paths`.** После разрешения `pnak` пересоздаёт управляемый блок с директивами `--path:`; остальное содержимое файла сохраняется (границы блока — комментарии-метки).

**Вывод.** Сообщения идут в stderr, чтобы данные `translate` (SHA) можно было безопасно брать через `$(…)`.

**Требования.** Нужны `git` и собранный `nifler` (`hastur build nifler`).

**Примеры.**

```sh
pnak                                  # fetch: клоны в deps/, пути в nimony.paths
pnak --parallel:auto fetch
pnak pin                              # записать pnak.nif (замок)
pnak search --nimony json
echo "requires \"https://github.com/foo/bar#$(pnak translate bar 1.2.0)\""
```

## V. Расхождения справки и кода

В процессе сверки справок (`--help`) утилит с их исходниками обнаружено следующее; полезно знать, чтобы не удивляться.

1. **`nifasm --emit-obj`**: в справке «только macOS arm64»; на практике этот режим используют и для Linux, когда нативная программа линкуется с libc (`nimony`: `nativeSysLink`, `arkham --crt`).
2. **`arkham`**: сочетание `freebsd/amd64` принимается, но в справке не перечислено.
3. **`lengc`**: команда `n` и опции `-o`/`--out` в справке отсутствуют; `-r` описана как «запустить make и программу», тогда как `nimony` всегда вызывает его с `--compileOnly`.
4. **`nifler`**: `--portablePaths` в коде и так включён по умолчанию.
5. **`nimsem`**: в справке нет команды `plugin`, опций `--forcebuild`/`-f`/`--ff` и `--keepsemtree`.
6. **`nimony`**: нет в справке команд `doc` и `s`, а также опций `--native`, `--target`, `--passC`, `--passL`, `--keepsemtree`.
7. **`nifler2`** не реализует `config` и `--docs`; для `nimony doc` и конфигурации по-прежнему нужен `nifler`.
8. **`shoggoth --cpu:be|le`** — порядок байт, а не архитектура; в этом он не похож на `--cpu` у `nimony` и `arkham`.
9. **`nimony -o`**: справка одновременно указывает два «умолчания» выходного файла (внутри nimcache и в текущем каталоге); проверьте, куда на самом деле пишется ваша сборка.

## VI. Практические рецепты

**1. Обычная сборка и запуск.**

```sh
nimony c -r prog.nim
nimony c -d:release -o:prog prog.nim
```

**2. Нативная сборка без C и libc (нужны `arkham` и `nifasm` в `bin/`).**

```sh
hastur build native      # если ещё не собраны
nimony n -d:release -o:prog prog.nim
```

**3. Посмотреть, что реально запускает `nimony`.**

```sh
nimony c --report prog.nim      # сколько раз выполнялась каждая команда
nimony c --profile prog.nim     # время и память по командам
```

Сам граф лежит в `nimcache/` в файле `*.build.nif`; его можно прочитать и выполнить отдельно: `nifmake -j run nimcache/prog.build.nif`.

**4. Проверить, не пересобирается ли лишнее.**

```sh
nimony c --silentMake --report prog.nim
nimony c --silentMake --report prog.nim   # пустой отчёт = всё актуально
```

**5. Редакторная навигация.**

```sh
nimony check --def:prog.nim,12,5 prog.nim
nimony check --usages:prog.nim,12,5 prog.nim
```

**6. Документация проекта.**

```sh
nimony doc prog.nim             # результат в htmldocs/
```

**7. Проверить собственный плагин.**

```sh
nimony check --keepsemtree --nimcache:/tmp/vc src/myplugin.nim
validator --nimcache:/tmp/vc src/myplugin.nim
```

**8. Подтянуть зависимости и закрепить их.**

```sh
pnak --parallel:auto            # fetch
pnak pin                        # pnak.nif — замок
```

**9. Собрать тулчейн и прогнать все тесты.**

```sh
hastur build
hastur --jobs:auto all
```

**10. Кросс-сборка для платы (bare-metal).**

```sh
nimony n --os:embedded --cpu:arm32 --layout:board.nif prog.nim
```
